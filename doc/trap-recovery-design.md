# トラップ復帰の設計 — 固まらない基板へ

状態: 設計 (2026-11-19)。IwaC チャット経由でユーザーから
「全部対応したい」と受けた 4 件を、OS 側の段立てに落とす。
実装は段ごとの合図待ち。

## 背景 (実際に起きたこと)

- 2026-11-18、IwaC 分割セルフホスト段4 の実機確認中、
  misaligned アクセスが M シムに届き、シムが
  "not emulated" と出して M モードで停止。基板全体が
  死んだ (カーネルに制御が戻らない)。
- 2026-11-10 の nami でも同じ型: nori のデータ配置で
  int64 グローバルが奇数アドレスに乗り、misaligned store
  (mcause=6) で M シムが停止した。QEMU は misaligned を
  許容するので virt では再現しない。実機だけの落とし穴。
- 現状の M シム (boards/k210/mshim.c) の分岐:
  違法命令 (cause 2) のうち time / cycle / instret の
  csrr だけエミュレーションし、それ以外と misaligned
  (cause 4 / 6) はすべて「印字して停止 (wfi ループ)」。

狙いは「1 つのプログラムの失敗で基板全体が死なない」こと。
手を 4 つの層に分ける。

## 段1: M シムで misaligned load/store をエミュレーション

perf_read の cycle / instret と全く同じ場所・同じ手口。
cause 4 (load misaligned) / 6 (store misaligned) の命令を
解読し、バイト単位のアクセスに分解して実行、load は
フレームの rd スロットへ結果を書き、mepc を進めて戻る。
プログラムからは何事も無かったように見える。

実装の要点:
- 命令は 4 バイトとは限らない。圧縮命令 (c.ld / c.sd /
  c.lw / c.sw / c.ldsp / c.sdsp 等) も misaligned の
  発生源になるので、2 バイト命令の解読も要る。
  対象は整数の load/store。アドレス計算は命令の
  rs1 + 即値 (フレームから読む)。
- 実アクセスの経路が論点。候補:
  (a) mstatus の MPRV を使い、MPP=S にして S モードの
      ページ変換を借りる (バイト load/store を M から実行)。
  (b) sptbr から Sv39 表をシムが自分で辿って物理アドレス
      化し、物理へバイトアクセス。
  推奨は (a) (表辿りの重複実装を持たない)。(a) が K210 の
  ドラフト仕様で期待どおり効くかは実機スパイクで先に確かめる。
- 浮動小数点の FLD / FSD が misaligned の場合: 戻し先が
  FP レジスタになる。整数バイト load で値を組み立てて
  fmv.d.x で入れる手はあるが、段1 では整数だけにし、
  FP は段2 (プログラム終了) に回すかを実装時に判断する。
- 本当に悪いアドレス (未マップ) への misaligned は
  エミュレーションのバイトアクセス自体が fault する。
  M モードで二重に fault すると救えないので、対象は
  「変換が成功するアドレス」に限る (MPRV 経由なら変換
  失敗は S 側の access fault として返る形にできるか、
  ここもスパイクで確認する)。

検証: わざと misaligned な ld/sd をする検証プログラム
(misalign.elf) を作る。virt では QEMU が許容して素通り
(それで PASS)、実機では修正前は基板が止まり、修正後は
"misalign ok" が出る。test-k210.py に K28 として追加。

**検出の記録 (2026-11-19、ユーザーの追加指示)**:
エミュレーションしたら、そのことを後から分かるように
カーネルログ (dmesg) に残す。M シムは klog を直接触ら
ない: シムは自分の小さな記録領域 (先頭 8 件の詳細
{cause, pc, addr} と累計カウンタ) に書き、カーネルが
trap 入口のついでに drain して klog へ移す
(board_drain_trap_log、traplog.h)。段2 の転送も同じ
記録経路に乗せる。

## 段2: エミュレーションできないトラップはプログラムだけ終了

段1 で扱えないトラップ (FP の misaligned、想定外の
違法命令など) がユーザープログラムから来たら、基板を
止めずに S モードのカーネルへ転送し、既存の fault 分離
(落ちた走者だけ status -2 で終了して Nish に戻る) に
乗せる。Unix の SIGBUS 相当。

- 前提の確認が要る: K210 のドラフト仕様では misaligned が
  medeleg に関わらず M に来る (現行シムの前提)。転送は
  シムが scause / sepc / stval を仕立て、stvec へ mret
  する形を候補にする。カーネルの trap 入口が期待する
  形 (sscratch のフレーム) と合うかはスパイクで確かめる。
- 対象は U モード由来のトラップだけ。S モード (カーネル
  自身) の fault は今までどおり停止が正しい (OS のバグを
  握りつぶさない)。
- virt には不要 (OpenSBI + 通常の委譲で最初から S に届く)。

## 段3: ウォッチドッグで自動リセット

段1・段2 をすり抜けて基板が止まっても、最終的には
自動で戻るようにする。

- K210 の WDT を使う。SDK で確認した形 (DesignWare WDT):
  WDT0 = 0x50400000、cr (0x00: bit0 enable、bit1 RMOD は
  0 = リセット)、torr (0x04: TOP を両ニブルへ)、
  crr (0x0C: 0x76 を書くと餌やり)、ccvr (0x08: 現在値)。
  タイムアウトは 2^(16+TOP) サイクル。pclk の実値は
  実機で ccvr の減り方から測って TOP を決める。
- 餌やりは時計タスクの起床 (1 秒周期) に相乗りさせる:
  スケジューラが生きている証拠になる場所。タイムアウトは
  5〜10 秒。audio_write のような長いカーネル処理中も
  時計タスクは回る (sched_poll の流儀) ので誤発しない。
- 有効化は sched_start の後 (起動途中では止まらない)。
- 発火すると SoC リセット → フラッシュ済み OS で再起動
  して Nish に戻る。SRAM ブートの実験セッションが止まった
  場合も、フラッシュ側の OS に戻るだけ (非破壊の帰結)。
- 検証は手動手順 (K スイートには入れない: 通常スイートの
  途中で基板がリセットされると後続が壊れるため)。
  WDT_TEST ビルドを SRAM ブートし、"wdt: started" の
  pclk 実測と "wdt: TEST stop feeding" を見て、タイム
  アウト後にフラッシュ済み OS の起動がログに現れることを
  確認する。

## 段4: Hatoba 側の検出と自動復帰 (連携)

- OS 側の契約は 2 つだけ: (1) M シムの停止印字は
  "mshim:" で始まる行として残す (既存)。(2) 起動したら
  必ず Nish プロンプトまで行く。
- 検出 (シリアルログの "mshim:" 出現、tick / 応答の停止)
  と、リセット → 必要なら SRAM 再フラッシュ → 中断した
  コマンドの再送、は Hatoba 側の実装。進め方は Hatoba
  チャット側と相談して決める (この doc は OS 側の契約の
  記録に留める)。

## 進め方と注意

- 段1 → 段2 → 段3 の順を推奨 (段1 が段4 実機ブロッカーの
  直接の解消、段2 は段1 の残り、段3 は独立)。
- 触る場所: 段1・段2 は boards/k210/mshim.c (+ 検証用
  misalign.c と登録)、段2 は trap.c の fault 経路にも
  触れる可能性がある。oled-ssd1306 ブランチも trap.c を
  触っているので、マージ順で小さな競合がありうる
  (触る領域は syscall 追加と fault 経路で別)。
- 各段とも branch を切って、virt 全件 + 実機 (K28 等) で
  確認してから main へ。
