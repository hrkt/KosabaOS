# synth — シンセ音源アプリの設計メモ (段1)

状態: 段1 実装 (2026-11-25、branch `synth-app`)。
コマンド名は **synth**。nami と同じく IwaC の C サブセットで
書き、iwac --kosaba --elf → nori でビルドする
(`arch/riscv64/synth/build-synth.sh`)。OS 側 build.sh は
成果物があるときだけ -DSYNTH_EMBED で取り込み、拡張子なしの
"synth" で登録する (nami と同じ流儀)。

## 使い方

- `run synth` / `run synth fm` — FM デモ曲 (32ステップ×0.25秒=8秒)
- `run synth psg` — PSG で同じデモ曲 (ノイズのハット付き)
- `run synth play fm` / `run synth play psg` — 対話モード
  - 鍵盤: 下段 `z s x d c v g b h n j m ,` と上段
    `q 2 w 3 e r 5 t 6 y 7 u i` が半音ずつ上がる 2 オクターブ
  - `o` / `p` で基準音 (既定 C4) をオクターブ上下、ESC / Ctrl-C で終了
- `run synth midi <path>` — MIDI バイト列ストリームを読んで鳴らす
  (下の SMF プレーヤーの節)。FM はマルチティンバー版で
  `[pool 1-32] [2op|4op] [dbg]` の追加引数あり
  (下のマルチティンバーの節)
- プリセット (FM / PSG 各 16) は `run synth fm <番号>` 等の
  引数、対話モードの `[` / `]` キー、MIDI のプログラム
  チェンジでロードできる (下のプリセットの節)
- エフェクトは全モード共通の引数 `[nofx] [rev|dly|cho]
  [fxchain] [fxdbg]` と、対話モードの `R` / `D` / `C` /
  `X` キーで切り替える (下のエフェクトラックの節)
- 終了時に `synth: samples=<総数> fnv=<16進16桁>` と
  `synth: done` を印字する。virt では dmesg の
  `audio: close ... samples= / fnv=` 行と照合できる (wavgen の流儀)
- 戻り値: 0=正常、1=オーディオを開けない/書き込み失敗、2=引数不正

## 段1 の音源仕様

- 出力: 44100Hz・モノラル 16bit、audio syscall 40〜42 のみ
  (新 syscall なし)。書き込みは 1024 サンプル塊、部分受け付けは再送
- 共通ボイス: 4 ボイス、ラウンドロビン割り当て。簡易 ADSR
  (attack 約2.5ms、decay で sustain 61% へ、gate が切れたら
  release 約25ms)。状態は 1 ボイス 16 ワードで g_vs (下記) に持つ
- FM: 2 オペレータ。搬送波の位相を変調波 (周波数比 3.5) で変調。
  正弦波は 256 点 Q15 テーブル + 線形補間、位相は 1 周=65536 の
  固定小数点。変調の深さは専用エンベロープで減衰する
  (ベル / エレピ寄り)。音程表は MIDI 36〜96 の位相増分を
  ホストで計算し、関数内で代入で埋める (初期化子は使わない)
- PSG: 矩形波 (デューティ 50%)。ノイズは 16bit LFSR を
  1 チャンネルとして同じボイス枠で扱う
- ミキサー: 全ボイスを整数で加算し ±30000 でクリップ

## 割り切り (段1)

- 端末にはキーアップが無いので、対話モードでもキーを押すと
  gate (約0.36秒) 分だけ鳴って自動で release に入る。
  本当のゲート (押している間鳴る) は MIDI 入力待ち
- 現行の audio リングは 8192 フレーム (約186ms) なので、
  対話モードの発音遅延はその分ある。低遅延化は OS 側
  realtime-prep (doc/realtime-audio-design.md) の段2 の仕事で、
  synth 側は現行の口のまま追随する
- 実効レートは K210 で 44010Hz のため音程は約 -0.2% 低い
- ワード単位の状態はファイルスコープの int32 配列に置いて
  直接アクセスする。バイト列 (曲データ・プリセット記録・
  名前・出力バッファ) は char 配列 (経緯は下の
  「直接アクセス化 (バイトパックを外した)」の節)
- main に大きなローカル配列 (正弦波表など) を置くと IwaC の
  フレーム生成が壊れることを実測した (フレーム 1504 バイトで
  プロローグの `addi sp,sp,-N` の符号が反転して +N になり、
  スタック上端の外へ書いて即フォールト。nami の main は
  フレーム 80 バイト)。ローカルはスカラだけに保つこと。
  IwaC 側で直すべき問題として切り分ける

## SMF プレーヤー (smfplay)

Standard MIDI File を再生する別プログラム `smfplay`
(`arch/riscv64/synth/smfplay.c`、synth と同じく IwaC 製、
build-synth.sh が一緒にビルドし、OS 側は素材があるときだけ
拡張子なしの "smfplay" で取り込む)。

- 役割分担: smfplay は**仮想 MIDI デバイス**。SMF を解析し、
  テンポマップに従って実時間に刻みながら (uptime=31 で読み、
  sleep_ms=34 で待つ)、生の MIDI バイト列を送り先へ出す。
  synth は届いたバイト列をそのまま解釈して鳴らす
  (実鍵盤と同じ経路)
- **デルタ先送りをしない理由**: ファイル内のデルタタイムは
  SMF 形式そのものなので解析には使うが、送り先へデルタを
  渡して受け手に数えさせる形は取らない。本物の MIDI の線に
  タイミング情報は無く、バイト列が演奏時刻に届くこと自体が
  実物だからで、先送りすると時計の仕事が synth 側へ移り、
  実経路のジッタも検証できなくなる
- 送り先は `send_event()` の関数境界の向こう。本命は OS 側
  realtime-prep 段4 の L2 入力キュー + 注入 syscall で、
  来たらそこへ差し替える。暫定経路は 2 つ:
  - `run smfplay <file.mid>` — イベントを時刻つきログに
    出す (検証用)
  - `run smfplay <file.mid> file <path>` — 生バイト列を
    その時刻にファイルへ書いていく。終わりに終了マーカー
    として private SysEx `F0 7D 00 F7` を書いて閉じる
    (実キューが来るまでの暫定約束)
- synth 側の受け手は `run synth midi <path> [fm|psg]`:
  ファイルをバイト列ストリームとしてポーリング読み
  (未着分は sleep_ms で少し待って再試行) し、逐次解釈する。
  ノートオン/オフは本物のゲート (オフで release)、
  プログラムチェンジは GM 番号からエンジン内のプリセットを
  引く (下のプリセットの節)、CC 120/123 は全音止め。
  終了マーカーで余韻 11025
  サンプルを描いてから閉じる。同時実行 (smfplay を
  ジョブで流しながら synth が読む) も virt で確認済み。
  描画ペースは 2026-11-26 に演奏時計駆動へ変更した
  (下の「ライブモードのリアルタイム化」の節)
- 対応範囲: format 0 / 1 (全トラックを時刻順にマージ、
  テンポは同一 tick なら小さいトラック番号を優先)、
  division は PPQ のみ (SMPTE は断る)、ランニング
  ステータス、テンポ設定メタ FF 51、トラック終了 FF 2F。
  SysEx と他のメタは読み飛ばす。ベロシティの大きさは
  synth 側で使わない (0=オフの扱いだけ守る)
- 制限: ファイルは丸ごと読みで上限 32768 バイト、
  イベント最大 4096、テンポ最大 256、トラック最大 32
- virt 検証 (2026-11-25): テスト曲 (make_test_mid.py、
  format 0/1 両版、テンポ変更 2 回、約 10.3 秒) で
  log モードのイベント時刻が予定と最大 11ms 差で一致、
  ファイル経由のパイプラインと同時実行ライブ再生の
  両方で synth の samples/FNV が audio close 行と一致

## プリセット (FM / PSG 各 16)

FM と PSG に 16 個ずつプリセット音色を持ち、ロードできる。
General MIDI (GM) の楽器分類を参考に、異なるファミリーから
拾った。定義は synth.c の `fill_presets()` にあり、1 件
20 バイトのバイトパックでファイルスコープの char 配列
(g_pfm / g_pps) に置く。名前 (16 バイト枠) も別表に持つ。
発音時、trig が現在のプリセットの実効パラメータをボイス
ごとの作業領域 (g_vp) へ写し、mix_sample はそれで回る。

エンジン拡張は最小限に絞った: エンベロープの 4 値
(attack / decay / sustain / release) とレベルをボイスごとに
持つこと、FM の変調比と変調の深さ・変調 env の減衰率、
PSG のデューティ可変・ノイズ混合・オクターブシフト。
フィードバックやビブラートは入れていない (必要になったら
プリセット形式の空きバイトで足せる)。op モード
(2op / 4op) は後の節で足し、+18 バイトを使う。

**0 番は段1 の従来音色そのもの** (全パラメータが従来の
固定値と一致)。番号なしで起動した場合のデモの FNV は
従来と変わらない (FM 79b7a119033bb71b / PSG
d8c200d36c6c30cd、virt で再確認済み)。

## マルチティンバー (FM) と DVA

MIDI モードの FM は 8 パートのマルチティンバーにした
(デモ / 対話モードと PSG の MIDI モードは従来通り
単一パート・モノラル)。狙いは音を鳴らすこと自体に加えて、
後の「負荷計測」の節の通り負荷テストの道具にすること。

- パート: MIDI ch 1..8 がそのままパート 1..8。各パートは
  プリセット (プログラムチェンジはそのチャンネルだけに
  効く)、ボリューム (CC7)、パン (CC10) を個別に持つ。
  ch 9 以降は無視する
- 出力はステレオ (audio_open 44100 / 2ch)。パンは線形
  (L ゲイン = (127 - pan) / 128、R ゲイン = pan / 128) で
  ボイスごとに掛け、ミックス後に ±30000 でクリップ
- ボイスプール: 全パート共有で最大 32 ボイス。起動引数
  `run synth midi <path> fm <pool 1-32>` で上限を絞れる
  (負荷スイープ用)。ボイス状態は所属 ch・ノート・位相・
  env 段階・発音順 seq を char 配列にバイトパック
- DVA の割り当て規則 (ノートオン時):
  1. 同じ (ch, note) が鳴っていればそれを再トリガ
  2. 空きボイス
  3. release 中の最も古いボイスを奪う
  4. 全体で最も古いボイスを奪う (steal)
  パートごとの同時発音上限は 8 で、上限に達したパートは
  自パートの最も古いボイスを奪う。ノートオフは
  (ch, note) が一致するボイスだけを release に入れ、
  CC 120/123 はそのチャンネルのボイスだけを止める
- デバッグ: 引数に `dbg` を付けると割り当てのたびに
  `synth: alloc v=<n> ch=<c> note=<n> [steal]` を印字する

パートの初期プリセット (GM 的な既定割り当て):

| パート (ch) | プリセット | 想定 |
| --- | --- | --- |
| 1 | 0 Grand Piano | 主旋律 |
| 2 | 9 Electric Bass | ベース |
| 3 | 10 Strings | 和音 |
| 4 | 1 Electric Piano | 副旋律 |
| 5 | 6 Acoustic Guitar | 伴奏 |
| 6 | 11 Trumpet | ブラス |
| 7 | 12 Flute | 木管 |
| 8 | 15 Synth Pad | パッド |

対象外: ch 10 のドラム (下の将来課題)、PSG の
マルチティンバー。(パートごとのエフェクトセンドは
後の「エフェクトラック」の節で実装した)

## FM の 4 オペレータ化

負荷ノブ兼音質として、FM に 4op モードを足した。
アルゴリズムは 2 種に絞る (フィードバックは入れない):

- モード 1 (直列スタック): op1 -> op2 -> op3 -> carrier。
  変調比は全 op 共通、深さは内側ほど浅く (1/4、1/2、1) して
  破綻を避ける。変調 env は 2op と共有
- モード 2 (2+2 ペア): 既存の 2op を 2 本混ぜる。2 本目は
  変調の深さ半分、キャリアを僅かにデチューン (+1/256)
  して厚みを出す

プリセットの +18 バイトが op モード (0=2op / 1=スタック /
2=ペア)。4op のプリセットは FM 1 (E.Piano, スタック)、
6 (A.Guitar, スタック)、7 (E.Guitar, ペア)、8 (A.Bass,
スタック)、9 (E.Bass, ペア)、11 (Trumpet, ペア)、
14 (Synth Lead, ペア)。ベル系 (2/3/4/13) は 2op のまま。
**0 番 Grand Piano は従来音色の保存のため 2op のまま**
にしてあり、デモの FNV は不変 (79b7a119033bb71b)。
負荷スイープ用に、MIDI モードでは引数 `2op` / `4op` で
全ボイスの op モードを上書きできる (4op はスタック固定)。

## 負荷計測 (perf_read)

マルチティンバー版 MIDI モードは描画コストを自己計測し、
終了時に `synth: perf ...` の形で印字する:

- 描画チャンク (512 フレーム) の前後で perf_read (33 番、
  0=サイクル / 1=命令数) を読み、チャンクごとのコストを
  積算する。印字は総サイクル、命令数、平均 cycles/frame、
  最悪チャンクのコスト、同時発音数のピーク
- 予算: 512 フレームは 44100 Hz で約 11.6 ms 分。最悪
  チャンクの予算比 (%) = 最悪コスト / (較正した
  cycles/ms × 11.609)。cycles/ms は起動時に uptime と
  perf_read の差分 (100 ms の sleep を挟む) で較正する
- virt の数字の読み方: QEMU の cycle カウンタはホストの
  進み方に引きずられるので、サイクル数と予算比は目安。
  命令数 (ins/frame) は決定的で、構成比較はこちらが正。
  実機 K210 (390 MHz) の予算は 390e6 / 44100 =
  約 8843 cycles/frame で、実機で「間に合ったか」の
  最終判定は audio close 行の under (無音ブロック数)
- ストレス曲: make_test_mid.py の SONG5.MID。ステージ
  ごとに同時発音が 4 -> 8 -> 16 -> 24 -> 32 と増える
  (各 1920 tick = 2 秒、境界 tick 0/1920/3840/5760/7680、
  smfplay の log と突き合わせ可能)。全 8 パート使用、
  ステージ境界でプログラムチェンジ、最終ステージは
  ch 1 に 16 分音符の連打入り

virt 実測 (2026-11-25、SONG5 をファイル先行書式で再生。
イベントが先行して届くため同時発音は上限に張り付き、
負荷は上限側の見積もりになる):

| pool | op | 平均 cycles/frame | ins/frame | 最悪チャンク予算比 | ピーク |
| --- | --- | --- | --- | --- | --- |
| 4 | 既定 | 7,872 | 10,027 | 78% | 4 |
| 8 | 既定 | 14,259 | 17,001 | 193% | 8 |
| 16 | 既定 | 20,680 | 22,834 | 212% | 16 |
| 32 | 既定 | 36,150 | 38,622 | 428% | 32 |
| 32 | 2op 固定 | 30,625 | 33,262 | 353% | 32 |
| 32 | 4op 固定 | 43,677 | 46,704 | 769% | 32 |

読み取れること: ins/frame は pool にほぼ比例して増え、
4op は 2op の約 1.4 倍。K210 の予算 (約 8843
cycles/frame、IPC を 1 と仮定) と比べると、現行の
IwaC 生成コードでは 4 ボイス級が実時間の目安で、
16/32 ボイス全開は実機では間に合わない見込み。
ただしこれは virt の命令数からの推算で、実機の負荷は
未検証 (under と耳の確認は実機セッション待ち)。

## エフェクトラック (マスターのセンド/リターン)

マスター段にセンド/リターン型のエフェクトラックを付けた。
エフェクトは共通の枠組み (モジュール登録表) で管理し、
あとから増やせる構造にしてある。置き場所は synth 内蔵の
ミキサー (マルチティンバーのパート集計点) のマスターで、
FM / PSG 両エンジン共通にかかる。

### モジュール登録表

登録表 (synth.c の `fx_init` が `g_fxmeta` に組む) の並びが
そのままチェーンモードの直列順になる:

| 順 | モジュール | センド CC | 既定 ON | 既定センド | wet トリム |
| --- | --- | --- | --- | --- | --- |
| 0 | Chorus | CC93 | OFF | 32 | 1.0 |
| 1 | Delay | CC94 | OFF | 32 | 1.0 |
| 2 | Reverb | CC91 | ON | 40 | 0.75 |

- センドはパート (MIDI ch 1..8) ごとに独立。MT モードでは
  パートのドライ和 × センド/127 がモジュールごとのバスに
  なる。モノラルモード (デモ / 対話 / 単一パート MIDI) は
  全体で 1 系統のセンド (既定値は登録表どおり。モノラル
  MIDI では CC91/93/94 で書き換わる)
- CC94 は GM には無い番号で、GS/XG のバリエーション
  (ディレイ系) センドの慣例から採った
- 既定はリバーブのみ ON。CC91 が来ない曲 (レパートリー等)
  でも残響が薄く聞こえるよう、リバーブの既定センドは 40

### ルーティング

```
パラレル (既定):
  part1..8 --dry--+----------------------------------> master
                  +-- send(cho) --> [Chorus] --wet---+
                  +-- send(dly) --> [Delay]  --wet---+--> master
                  +-- send(rev) --> [Reverb] --wet---+

チェーン (fxchain):
  part1..8 --dry-------------------------------------> master
                  +-- send(cho) --> [Chorus] --+
                  +-- send(dly) --> [Delay]  --+ (直列)
                  +-- send(rev) --> [Reverb] --wet---> master
```

チェーンの割り切り: 信号は登録表の順に直列を通り、各段の
入力は「前段の出力 + その段へのセンドバス」。センドは
各段への注入量として働き、戻りは最終段の出力だけになる
(途中の段の出力は直接マスターへ戻らない)。OFF の段は
素通りする。リバーブだけ ON のチェーンはパラレルと
等価になる。

### 各モジュールの回路

- **Chorus**: 変調ディレイ。基準遅延 20ms (882 サンプル) を
  LFO 0.6Hz で ±264 サンプル (約 ±6ms) 変調。読みは隣接
  2 サンプルの平均 (安い補間)。wet は遅延信号そのもので、
  ドライとの干渉がコーラス感になる
- **Delay**: フィードバックディレイ。遅延 13230 サンプル
  (300ms、120 BPM の 8 分音符相当)、帰還 11468/32768
  ≒ 0.35
- **Reverb**: Freeverb 系。ダンピング付き (帰還路の 1 次
  ローパス、係数 1/4) コムフィルタ 8 本の並列 → オール
  パス 4 段直列。コム長は 1116/1188/1277/1356/1422/1491/
  1557/1617、オールパス長は 556/441/341/225 (右 ch は
  +23 ずらし)。入力ゲイン 1/4、コム帰還 26214/32768
  ≒ 0.80 で、ダンピングと合わせて発散しない

### 操作

- 起動引数 (全モード共通、位置は自由):
  - `nofx` — 全エフェクト OFF。**従来 FNV が完全一致**する
    (回帰確認用)
  - `rev` / `dly` / `cho` — 挙げたものだけ ON (1 つでも
    挙がれば、まず全 OFF から始める)
  - `fxchain` — チェーンモード (既定はパラレル)
  - `fxdbg` — MT モードでチャンク (512 フレーム) ごとの
    出力エネルギー絶対値和を印字する (検証用)
- 対話モードのキー: `R` = リバーブ、`D` = ディレイ、
  `C` = コーラス の個別 ON/OFF、`X` = チェーン切替。
  小文字 r/d/c は鍵盤の音に割り当て済みなので大文字にした。
  切り替えるたびに状態を印字する

### モジュール境界 (将来の asm 差し替えを意識した形)

各モジュールの処理は、nami で手書き asm 核を C 参照実装と
FNV 一致させて差し替えた前例と同じく、モジュール単位で
アセンブラ実装に差し替えられる境界にしてある:

- 境界を越えるのは「入力フレーム列・出力・自分の状態
  ブロック・パラメータ」だけ。処理関数 (`fx_proc_*`) は
  synth 本体の状態 (ボイス、パート等) に触れない
- インタフェース: 入力は `g_fxin` (ワード 0=L、1=R、
  呼び出し側がセンドバスや前段出力を入れる)、出力は
  `g_fxout` (同形式)、引数はチャンネル数 nch (1=モノラル
  は L のみ処理)。パラメータは登録表 (下記) と関数内の
  定数。1 フレームごとに 1 回呼ばれる
- 状態ブロックのレイアウト (asm 化する人はこれだけ見て
  書けるように残す)。遅延ラインは 1 サンプル = 1 ワード
  (int32 配列の要素。値は int16 相当の範囲で、書き込み時
  に ±32767 へクランプ)。添字は要素単位で、下表の件数・
  位置はそのまま要素数・要素位置:

| モジュール | 状態ブロック | レイアウト |
| --- | --- | --- |
| 共通 | `g_fxmeta` | 8 ワード/件: +0 センド CC、+1 既定 ON、+2 既定センド、+3 wet トリム (256=1.0) |
| Chorus | `g_cho` | 4096 ワード。ch × 2048 のリング (長さ 2048) |
| Chorus | `g_fxpos` [24+ch] | 書き位置 (0..2047) |
| Chorus | `g_fxctl` [7] | LFO 位相 (32bit 蓄積、増分 58426/サンプル = 0.6Hz) |
| Delay | `g_dly` | 32768 ワード。ch × 16384 のリング (長さ 16384、遅延 13230) |
| Delay | `g_fxpos` [26+ch] | 書き位置 (0..16383) |
| Reverb | `g_rvb` | 25450 ワード。ライン配置は `g_fxoff` / `g_fxlen` (ch × 12 件: comb 8 + allpass 4、先頭位置と長さ) |
| Reverb | `g_fxpos` [ch*12+line] | 各ラインの書き位置 |
| Reverb | `g_fxdamp` [ch*8+comb] | コムのダンピング状態 |

- モジュールの追加手順: (1) `fx_proc_*` 関数を 1 つ書く
  (入力 `g_fxin`、出力 `g_fxout`、状態は自分の int32 配列)、
  (2) `fx_init` の登録表に 1 行足す (名前・CC・既定 ON・
  既定センド・トリム)、(3) `fx_proc` の振り分けに 1 行
  足す、(4) 起動引数の短縮名 (`fx_arg`) と必要なら対話
  キーを足す。登録表の並びがチェーンの直列順になる点に
  注意

### 検証 (virt、2026-11-25)

- **nofx で従来 FNV 完全一致**: デモ FM 0 番
  79b7a119033bb71b、PSG 0 番 d8c200d36c6c30cd、PSG midi
  bff2aa200110ea6b (いずれも従来どおり)。既定 (リバーブ
  ON) のデモ FNV は FM ba27ee8dff52f58e / PSG
  539925fc45923392 に変わる
- **リバーブの残響**: SONG7B (単音 + 無音) のチャンク
  エネルギーで、nofx はノート終了直後から全チャンク 0 に
  なるのに対し、ON では 158,274 → 142,710 → 109,201 →
  … → 9,817 と尾を引いて減衰する (11025 サンプルの
  余韻区間いっぱい残る)
- **CC91 の効き**: SONG7BZ (CC91=0) はリバーブ ON でも
  FNV 09275569734ef25a で nofx と完全一致 (センド 0 の
  パートは wet が出ない)。SONG7B (CC91=127) は
  ee9e5043d3408bdb に変わり、CC91=127 で wet が増える
- **ディレイの繰り返し**: SONG6B (CC94=127) で、ノートの
  チャンクエネルギー列が +13230 サンプル (300ms) ごとに
  そっくり繰り返し、ピークが約 0.35 倍ずつ減衰する
  (1.92M → 0.66M → 0.22M → 0.077M 相当)。nofx では
  ノート終了後ずっと 0
- **コーラスの時間変調**: SONG8 (CC93=127、4 秒の持続音)
  の定常区間のチャンクエネルギー変動係数は nofx の
  0.013 に対しコーラス 0.445 (最大/最小 6.6 倍)。
  ドライと変調ディレイの干渉が LFO で揺れている
- **チェーン**: SONG9B (CC91=127 + CC94=127) で rev 単体 /
  パラレル / チェーンの FNV が全て異なり、チェーンでは
  ディレイの繰り返しがリバーブを通って拡散して戻る
  (繰り返し位置のチャンクエネルギーが rev 単体の
  9,817 に対し 85,930)。なお SONG5 (描画 13,824
  フレーム) ではチェーンと rev 単体が一致するが、これは
  「ディレイ 13230 + 最短コム 1116 = 14,346 フレーム」
  より描画窓が短く、繰り返しがコムを通って出てくる
  前に終わるため (故障ではない)
- **発散しないこと**: 全エフェクト ON でも出力ピークは
  ドライと同じクリップ上限 30000 以内 (SONG5)。レパー
  トリー完走時のピークは K.545 = 16,813 / K.331 =
  17,479 で、帰還系の暴走はない
- **レパートリー (既定 = リバーブ ON、同時実行)**:
  K.545 は samples=2,800,640 / fnv=68845b43d46d237c、
  K.331 は samples=2,287,616 / fnv=14f64dd8073ce5f3、
  いずれも audio close 行と一致して完走
- **負荷 (SONG5、pool 32、13,824 フレーム、QEMU icount
  で測定)**: nofx 49,531 ins/frame に対し、リバーブのみ
  103,449、全 ON パラレル 111,627、全 ON チェーン
  110,553。チェーンとパラレルはほぼ同じ (各モジュール
  を 1 回ずつ通るのは共通)。コストの支配要因はフィルタ
  演算そのものではなく、バイト合成アクセサ (rd32/wr32/
  fx_rd16/fx_wr16) の呼び出し単価で、ボイス側と同じく
  nori の配置ずれ対策の代償。マスター 1 回分なので
  ボイス数には比例しないが、この時点の IwaC 実装では
  リバーブ 1 台で pool 32 のボイス群と同桁のコストが
  かかった (この後、直接アクセス化で解消。下の節)

### 実装上の注意 (iwac の命令表上限)

FX 追加で synth 全体の生成コードが iwac の命令表上限
(24,576 命令 / TU) に達し、main の末尾が無言で切れる
事象が出た。対策として `fill_sine` を 1/4 波 (65 件の
代入) + 対称展開 (鏡像と符号反転の 2 ループ) に圧縮して
命令数を空けた (表の値は従来と同一で、デモ FNV が
不変なことで確認済み)。synth に大きな機能を足すときは
命令数の残量に注意すること。

## 直接アクセス化 (バイトパックを外した)

前提: IwaC v63 (main `7a3c2e5`) で nori のデータ配置が
直り、グローバル配列の先頭・配列領域の基底と締めが
一律 8 バイト境界に揃うようになった (IwaC 側
doc/data-align.md)。これにより、従来 nori の配置ずれ
(配列が `0x4020003d` のような境界外れに乗り、int32
アクセスが全て misaligned のトラップエミュレーションに
なる) を避けるために必要だった「char 配列 + rd32/wr32
のバイト合成」が不要になった。

このリファクタ (エフェクトラックとは別コミット) で、
ワード単位の状態を全て int32 配列の直接アクセスへ
置き換えた: 正弦波表・音程表・ボイス状態 (単音/MT)・
ボイス実効パラメータ・パート・制御ブロック・FX の
登録表/実行時状態/バス類と、FX 遅延ライン (1 サンプル
= 1 ワード化。要素の添字と意味は不変)。バイト列その
もの (曲データ、プリセット記録 = 20 バイト詰め、名前、
出力バッファ) は char 配列のまま。アクセサ関数
rd32/wr32/fx_rd16/fx_wr16 は呼び出しが無くなり削除した。

前提の裏取り: ビルドに使う iwac/nori は v63 のソース
から再ビルドしたものを使い、iwac の中間オブジェクト
(.eo) のシンボル表で主要な int32 配列 (g_sine / g_vs /
g_vp / g_cho / g_dly / g_rvb / g_mv / g_mvp / g_part
ほか) のオフセットが全て 8 の倍数であること、最終
ELF のデータ基底が 0x40200000 (ページ境界) である
ことを readelf で確認した。

互換 (出力ビット不変) の確認範囲 — リファクタ前
(バイトパック版) と後で全て完全一致:

- デモ全 32 プリセット (FM/PSG × 16、nofx)
- SONG2 (MT 2 パート)、SONG4 (DVA)、SONG5 (プール
  4/8/16/32 の各 FNV も一致)、SONG7B / SONG7BZ、
  SONG9B (nofx / パラレル / チェーンの 3 構成)
- PSG モノラル MIDI (SONG0)、デモ既定 (リバーブ ON)
- レパートリー 2 曲: ライブ実行は読み側のポーリング
  間隔で総サンプル数が変わるため、先行書式 (ファイル
  先行) で前後比較した。K.545 は samples=83,968 /
  fnv=cd586920e1c36e1e、K.331 は samples=99,328 /
  fnv=7c2bccabbf374613 で前後一致 (先行書式では曲が
  読みチャンク単位に圧縮されるため、サンプル数は
  ライブ実行時と違う。値そのものは前後比較専用)

負荷 (SONG5、QEMU icount、ins/frame。前 → 後):

| 条件 | 前 (バイトパック) | 後 (直接アクセス) | 比 |
| --- | --- | --- | --- |
| pool 4, nofx | 12,751 | 3,249 | 3.9 倍 |
| pool 8, nofx | 19,052 | 4,303 | 4.4 倍 |
| pool 16, nofx | 30,482 | 6,230 | 4.9 倍 |
| pool 32, nofx | 49,531 | 9,399 | 5.3 倍 |
| pool 32, リバーブのみ | 103,449 | 19,136 | 5.4 倍 |
| pool 32, 全 ON パラレル | 111,627 | 20,752 | 5.4 倍 |
| pool 32, 全 ON チェーン | 110,553 | 20,864 | 5.3 倍 |

ボイスの限界コスト (pool 4→32 の傾き) は約 1,314 →
約 220 ins/voice/frame で約 6 倍。ベンチの純粋な
ボイスループ (2,100 → 約 200、約 10 倍) より改善幅が
小さいのは、アプリ側にはストリーム読み・ミックス・
カーネル側の固定費があるため。FX の増分 (リバーブ
のみ − nofx) も 53,918 → 9,737 ins/frame に下がった。
synth.elf は 91,944 → 75,560 バイト (生成命令数の
減少分)。

## ライブモードのリアルタイム化 (2026-11-26)

### 解析: 現行ループの何が壊れているか

ライブモード (run_midi / run_midi_mt) の主ループは
「読む → 解釈する → 512 フレーム描く → 書く」の固定
量子で、経過時間を一切見ていない。1 反復で作る量が
常に 512 フレーム (11.6ms 分) なので、生産速度は
512 / (反復の壁時間) で決まる。実測では反復周期が
約 42〜49ms (virt ライブ K.545: 3,119 反復 / 132 秒、
PCM カバー率 27.4%。実機でも 25.6% と同水準) で、
生産速度は約 11〜12k frames/s = 実時間の約 1/4
しかない。残りは装填遅れ (late) として DAC が飢える。

周期が 5ms の sleep 指定どおりにならない出所は、
前面 synth とジョブ smfplay の間の CPU の受け渡しが
量子化されていることにある (trap.c の SYS_SLEEP_MS
と 100ms tick の job_round_robin)。特にジョブ側の
sleep は、他に実行可能な走者がいないと自走者の起床
時刻までカーネル内でポーリングし続け、その間は前面
の期限切れの sleep が再確認されない。書き手の
イベント周期 (K.545 で相異なる tick 1,028 個 / 132 秒
≒ 平均 129ms) や tick 境界に引きずられて、実効周期
は数十 ms になる。

ただし本質は周期の内訳よりも、**遅れた分を取り戻す
項がループのどこにも無い**ことにある。1 回の反復が
遅れれば、その分の PCM は永久に欠落する。イベント
の適用も反復の頭でまとめて行われ、次の 512 フレーム
から効くので、到着時刻の量子化は「反復周期 (数十 ms)
+ チャンク 11.6ms」になり、左右パートの相対タイミング
も楽譜どおりに保たれない (実機の「噛み合わない」
聴感と整合する)。対照的にデモモードは連続描画で
実機でもクリーンで、壊れているのはライブループの
構造だけである。

### 設計: 演奏時計駆動のライブループ

ゴールは、静的な所与の MIDI 信号への最適化では
なく、**人が MIDI 鍵盤で弾いても違和感なく弾ける
こと**。ファイルの先読み・事前描画で帳尻を合わせる
方向は取らない。入力はストリームとして届いた分
だけを扱い、未知のタイミングの入力に低遅延・低
ジッタで追随するループにする。

- **演奏時計**: 起動時の uptime を起点に、「その
  時刻までに描くべきフレーム数 due = 経過 ms ×
  実効レート / 1000」を毎反復計算し、生産目標を
  due + LEAD とする。スケジューラに CPU を奪われ
  ても、戻った時点で due まで小ブロックを連射して
  取り戻す (catch-up)。遅延は PCM の欠落ではなく
  ジッタとして吸収される
- **時計のレートは実効 44010Hz** (K210 の I2S 実測)。
  要求レート 44100 で時計を作ると消費より 0.2%
  速く作り続け、先行が膨らんで数分でリング (8192
  フレーム) が満ち、遅延が最大化する。将来 OS の
  realtime-prep 段3 (音声時計の公開) が来たら
  時計の出所をそちらへ差し替えるのが本筋で、計算
  は live の目標計算 1 か所に閉じてある
- **ブロック 128 フレーム (約 2.9ms)**: 入力
  ポーリングはブロックごとに行い、ノートオンは
  次のブロックから反映される。イベント適用の
  量子化誤差は最大 128 フレーム。全イベントが
  単一ストリームに到着順に乗るので、パート間の
  相対タイミングはこの量子化の範囲で保存される
- **先行目標 LEAD = 256 フレーム (約 5.8ms)**:
  リングを満杯まで溜めない。リング滞留はそのまま
  鍵盤→音の遅延になるので、枯らさない最小限に保つ
- **遅延予算**: synth 側はポーリング+ブロック
  量子化 ≤ 2.9ms + 先行 5.8ms ≒ 9ms 以内。OS 側の
  既存分 (DMA 初回装填が 1024 フレーム溜まるまで
  待つ位相オフセット約 23ms、DMA ブロック、FIFO
  約 0.18ms) は realtime-prep 段2 の領域で今回は
  変えない。先行を小さく保ってあるので、段2 が
  来れば synth 側の変更なしに効く形にしてある
- **入力源の境界**: 読み取りは従来どおり「fd への
  read が 0 を返したら未着」という境界のまま。
  OS 段4 の L2 キューへ差し替える場合も、ポーリング
  1 か所を替えるだけで済む
- **終了処理**: 終了マーカー (F0 7D 00 F7) から
  11025 フレームの余韻、新着なし 30 秒でも終了、
  という従来の意味は保つ。余韻も演奏時計の実時間
  ペースで描く

### 検証 (virt、2026-11-26)

ライブ同時実行 (smfplay が実時間ペーシングで供給し、
synth が追随) の PCM カバー率 (synth の生成フレーム数
÷ 楽譜長×44,100):

| 曲 | 変更前 | 変更後 |
|---|---|---|
| K.545 | 27.4% | 99.3% |
| K.331 | 49.2% | 99.1% |

変更後の FNV は両曲とも audio close の FNV と一致。
100% に届かない約 0.7〜0.9% は、時計レート 44010 と
物差し 44100 の差 (0.2%) と、同時実行ハーネスで
synth の時計開始が smfplay の開始よりわずかに遅れる
開始オフセットによる。実鍵盤の用途では時計は synth
起動が起点でよい。負荷 (perf avg、cycles/frame) は
K.545 14,997 → 15,272、K.331 16,234 → 16,634 と
同水準 (virt の計測ノイズの範囲。maxchunk はマシン
全体カウンタでホスト側の競合に振れるため参考値)。

遅延の実測 (一時パッチによるプローブ、コミット
しない): 演奏開始 3000ms の位置に単発のノートオンを
注入し、到着を解釈した時点の描画位置と、振幅が
2000 を超える最初のサンプルの位置を比べた。到着
91,708 フレーム → 発音 91,766 フレーム、差 **58
フレーム (約 1.3ms)** で、ブロック量子化 (≤128
フレーム) の範囲内。鍵盤→音の synth 側予算は
「量子化 ≤ 2.9ms + 先行 256 フレーム約 5.8ms ≒
9ms 以内」で、これに OS 側の DMA/FIFO 分が乗る
(初回装填の 1024 フレーム待ちは realtime-prep
段2 の領域)。virt の時間は実機換算ではないので、
実機での遅延確認は段2 と合わせて今後の課題。

回帰: デモ nofx の FNV は FM 0 / FM 1 / FM 15 /
PSG 0 / PSG 14 で従来値と完全一致 (デモ・対話
モードと PCM 生成の数式には触っていない)。
test.sh は ALL PASS (43 件)。

## 段立て全体

- **段1 (今回): FM + PSG** — 上記。共通ボイス/ミキサー/ADSR の枠を作る
- **段2: Roland LA 音源風** — 短い PCM アタック (打鍵・撥弦の
  頭だけ) + 減算合成のサステイン部、という LA 合成の骨格。
  アタック素材の持ち方 (埋め込み表か /sd のファイルか) が論点
- **段3: PCM 風** — サンプルそのものをオシレータとして使う
  (ループ再生、ピッチシフトは再サンプリング)。素材は /sd 前提
- **段4: アナログシミュレーション** — 鋸波/パルス + ローパス
  フィルタ + レゾナンス、オシレータのドリフトとデチューンで
  「揺れ」を作る。フィルタは 1 サンプル毎の固定小数点演算が本命
- **その先: ミキサー / エフェクト / MIDI 入力** — エフェクト
  (リバーブ / ディレイ / コーラス) は synth 内蔵のラックと
  して実装済み (「エフェクトラック」の節)。残るは OS 側
  realtime-prep 段4 の MIDI 入力 (DIN/UART) に接続して
  鍵盤で弾くこと。複数プログラムのミキシングは当面せず、
  音源+ミキサー+エフェクトを synth 1 本に内蔵する形で足りる
- **ch 10 = PCM ドラム (将来課題、未実装)** — GM ドラム
  チャンネルは YAMAHA V50 の PCM リズムへのオマージュとして
  PCM ドラムにしたい (ユーザーの案)。今は実装しない。
  段3 (PCM 風) の素材の持ち方と合流する想定
