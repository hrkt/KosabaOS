# 移植可能性の基準（マルチアーキテクチャ方針）

状態: 基準として明記（2026-11-08、ユーザーの方針）。
x86 系への移植そのものは、OS の骨格が出来てからの話でよい。
ただし後から「全然無理」とならないよう、今の設計で移植可能性を
閉じないこと。これがこの文書の基準である。

対象アーキテクチャの置き場は当初からの約束どおり
`arch/riscv64/`・`arch/arm64/`・`arch/x86_64/` と分け、
共通コードは `arch/` の外に置く。ボード差分はボード層へ、
CPU 差分はアーキ層へ隔離する規律を、新しいコードでも崩さない。

## 番どころ（RISC-V 都合を共通コードに漏らさない）

1. **ページングの段数**: 現行の Sv39 は 3 段だが、x86-64 は
   4 段（5 段もありうる）、Arm も段数は構成次第。共通コードに
   「ページ表は 3 段」という前提を書かない。段数とページ表
   エントリの形式に触るのはアーキ層（vm の下側）だけに閉じる。
2. **トラップフレームの形**: レジスタの集合と並びはアーキテクチャ
   専用。フレームの構造はアーキ層に閉じ、共通コードは必要な
   フィールドへのアクセスだけを使う。共通の構造体に RISC-V の
   レジスタ名を持ち込まない。
3. **例外・割り込みの原因番号**: scause の値のようなアーキ固有の
   番号を共通コードに直接書かない。共通コードが見るのは
   「タイマ」「外部」「フォルトの種別」といった意味まで。
4. **特権モードと CSR の名前**: mstatus や sptbr のような
   RISC-V の語彙はアーキ層とボード層（M シム等）の中だけ。
   共通コードは「割り込みを許可する」「ページ表を切り替える」
   といった操作の名前で話す。
5. **時刻の読み方**: time CSR のような読み口の形はアーキ差分。
   共通コードは uptime や time_read のような意味の API を使う
   （段1 sleep の起床時刻を生カウントで持つ場合も、数え方自体は
   アーキ層の内側に置く）。

## 線引き

- 移植可能性を閉じないことは、「今すぐ汎用化する」ことではない。
  実ターゲットが 1 つしかない段階で抽象化を先行させない
  （実需主義は従来どおり）。基準は、新しく書くコードが将来の
  移植先を不必要に塞がないこと、その一点に限る。
- 迷ったら「この前提は RISC-V だけのものか？」と問い、
  そうなら置き場をアーキ層へ移すか、前提であることを
  その場所にコメントで明示する（無言で漏らさない）。
- コンパイラ側（IwaC / Asari）のアーキ対応は射程が別であり、
  この文書の対象外（IwaC 側の doc/asari.md を参照）。
