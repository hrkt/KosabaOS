## 全体の形

層を 4 つに切る。下の 2 つが「デバイス」、上が「意味」:

    trap.c の open/read (名前の接頭辞で振り分け)
      ├─ RAM FS (fs.c、既存)
      └─ FAT32 ドライバ (fat.c、共通コード)
            │ read_block(lba, buf, count)
          ブロックデバイス (blkdev.h、共通の抽象)
            ├─ SD カード (boards/k210/sd.c: SPI + SD プロトコル)
            └─ RAM イメージ (boards/virt/ramdisk.c: テスト用)

- ボード差分は一番下だけ (マルチボード前提どおり)。
  FAT はどちらのボードでも同じコード
- fat.c は fs.c のブロックチェーンと同じく「位置指定読み
  (read_at)」を中心に組む。開いたファイルの状態は
  {先頭クラスタ, サイズ} だけで、読み位置を持たない。
  位置は呼び手 (fd テーブル) が持つ。RAM FS と対称になる

## ブロックデバイス (blkdev.h)

    struct blkdev {
        const char *name;          /* "sd" / "ramdisk" */
        uint64_t block_count;      /* 総ブロック数 */
        int (*read)(struct blkdev *dev, uint64_t lba,
                    unsigned char *buf, uint32_t count);
    };

- ブロックの大きさは 512 バイト固定とする (SD の物理
  ブロックも FAT のセクタも、相手にする範囲では 512。
  変える必要が出たらその時にフィールドを足す)
- read は count ブロックまとめて読んでよい口にするが、
  中で 1 ブロックずつ回してもよい (SD の CMD18 / CMD17 の
  選択はドライバ内部の話)
- 成功 0、失敗は負数。buf は count × 512 バイト必要
- カーネルはボードから blkdev を 1 つ受け取る
  (board_blkdev())。無い / 初期化できない場合は NULL で、
  「SD は無い」として起動を続ける

## SD ドライバ (boards/k210/sd.c)

### 配線と FPIOA (2026-11-05、段1 スパイクで確定)

TF スロットのネット名は回路図上 "SPI0_" だが、実際に
MaixPy が使うのは **SPI1** で、信号の並びも当初の想定と
違う (MaixPy の sdcard.h が正本。段1 でこれに気づくまで
全滅した)。FPIOA でこう載せる:

    IO26 ← SPI1_D0 (MOSI / CMD)
    IO27 ← SPI1_D1 (MISO / DAT0)
    IO28 ← SPI1_SCLK (CLK)
    IO29 ← GPIOHS (CS / DAT3、手動制御)

- CS をハードウェア SS ではなく GPIO にする: SD の SPI
  モードは「CS を落としたままコマンドとデータを一続きに」
  「電源投入直後は CS を上げたまま 74 クロック以上」など
  CS の細かい作法が多く、手で握れる方が素直 (MaixPy も
  GPIOHS29 で CS を握っている)
- 入力ピン (MISO) の FPIOA には IE_EN が必須。GPIOHS で
  入力を読む場合は GPIOHS の INPUT_EN (+0x04) も要る
  (どちらも段1 で実測して判明)

### SPI の設定

- K210 の SPI1 を標準 (Motorola) モード、8 ビット、
  モード 0 (CPOL=0, CPHA=0) で使う
- クロックは初期化中 400kHz 以下、初期化後に上げる
  (目安 12.5MHz 起点で実測。MP3 の所要は最大 40KB/s
  なので、速さは余りまくる側)
- 転送はポーリングで回す (このカーネルの流儀に合わせる。
  512 バイト読みは 12.5MHz で約 0.33ms、割込みや DMA を
  引くほどの長さではない)

### SD の初期化シーケンス

1. CS を上げたまま 74 クロック以上を送る
2. CMD0 (CRC 0x95) → R1 が idle (0x01)
3. CMD8 (引数 0x1AA、CRC 0x87) → R7 で電圧とチェック
   パターンを確認。応答すれば SDv2 系
4. CMD55 + ACMD41 (HCS ビット付き) を、ready になるまで
   繰り返す (タイムアウト約 1 秒)。CMD8 が駄目なカードは
   HCS なしで試す
5. CMD58 で OCR を読み、CCS (容量の種別) を見る。
   CCS=1 ならブロックアドレス、0 ならバイトアドレス
   (その場合は CMD16 でブロック長 512 に固定)
6. CMD9 (CSD) から容量を計算して block_count にする

- 全ての待ちにタイムアウトを付け、「カードが無い / 応答が
  ない」を必ず有限時間で諦める。起動経路に置かない
  (後述の遅延マウント) ので、起動が止まる経路にはならない
- 読み: CMD17 (1 ブロック) / CMD18 (複数) + CMD12。
  データ開始トークン 0xFE をタイムアウト付きで待ち、
  512 バイト + CRC16 (読み捨て) を受ける
- アドレス引数は CCS で切り替える (ブロック番号そのまま
  / バイト換算 = 番号 × 512)

### 実装時の確認点

- LCD ドライバ (boards/k210/lcd.c) は SPI0 を使う。SD は
  SPI1 なのでコントローラの共有は起きない (2026-11-05 に
  確定)。FPIOA のピンも重ならない (LCD は IO36〜39)

## FAT32 ドライバ (fat.c / fat.h、共通コード)

### 守備範囲 (段3 の割り切り)

- FAT32 のみ、読み取り専用
- ディレクトリはパスでたどれる: 名前は '/' 区切りのパス
  として解釈し、ルート (mount 点の下) から要素ごとに
  ディレクトリを下りていく (例: `/sd/music/live/song.mp3`
  のうち、fat 側が受けるのは `music/live/song.mp3`)。
  パスは mount 点を外した時点で常にルート起点
  (相対解決と cwd はカーネルのパス解決の仕事で、
  fs-design.md 段4 側)。深さに上限を置く (8 階層)。
  '.' は読み飛ばし、'..' は扱わない (親へ戻りたければ
  パスを書き直す)
- 名前は 8.3 形式だけ (大文字小文字を区別しない ASCII
  比較)。LFN エントリは読み飛ばす (表示も照合もしない)
- 同時に意味を持つのは「マウント済みの 1 ボリューム」だけ

### マウント

最初の `/sd` 配下へのアクセスのときに遅延して行う
(起動時には触らない。カード無しでも起動が速いままになる):

1. ブロック 0 を読む。オフセット 82 の "FAT32   " が
   あればスーパーフロッピー形式 (BPB がブロック 0)、
   なければ MBR のパーティション表エントリ 1 の
   開始 LBA を BPB の場所とする
2. BPB から拾うもの: セクタあたりバイト数 (512 で
   なければ失敗とする)、クラスタあたりセクタ数、
   予約セクタ数、FAT の数、FAT32 の FAT サイズ、
   ルートディレクトリの先頭クラスタ
3. 計算で出すもの: FAT 開始セクタ、データ開始セクタ、
   総クラスタ数
4. FAT32 かどうかの判定は BPB の形 (FAT サイズ 32 が
   非 0 でルートクラスタを持つ) で行う。公式の
   「クラスタ数による種別判定」は使わない: 小さい
   テストイメージ (後述) が作れなくなるため。実カードの
   FAT32 は普通この形をしている

### API (fs.c と対称な形)

    struct fat_file {
        uint32_t first_cluster;
        uint64_t size;
    };

    int      fat_mount(struct blkdev *dev);
    int      fat_find(const char *path, struct fat_file *out);
    uint64_t fat_read_at(struct fat_file *f, uint64_t pos,
                         unsigned char *dst, uint64_t n);
    int      fat_list(const char *dir_path, int index,
                      char name[13], uint64_t *size_out,
                      int *is_dir);

- fat_find はパスを受け、要素ごとにディレクトリを
  下りて、最後の要素のファイル {先頭クラスタ, サイズ} を
  返す。途中要素がファイルだったり、要素が無ければ失敗
- fat_list はパスで指定したディレクトリの一覧
  (index 番目のエントリの 8.3 名と、ファイルなら
  サイズ、ディレクトリなら is_dir を返す)。段4 で
  Nish の ls から使う口として用意する
- ディレクトリたどりの内部は「ディレクトリの先頭
  クラスタを返す解決」と「その鎖のエントリ走査」の
  2 部品に分ける。ディレクトリ自体もクラスタ鎖なので、
  ファイル読みの鎖たどりをそのまま使う。ただし
  ディレクトリにはサイズが無いので、走査は鎖の終わり
  か 0x00 エントリまで
- fat_read_at は RAM FS の fs_read_at と同じ約束:
  末尾で clamp、範囲外は 0 を返す

### 読みの内部

- 位置 → クラスタ: pos / (クラスタあたりセクタ数 × 512)。
  先頭クラスタから FAT の鎖をたどる。FAT セクタは
  1 セクタ分だけキャッシュする (連続読みでは同じ
  FAT セクタを何度も引くため、これで十分効く)
- クラスタ内はセクタ単位で blkdev から読む。データ用の
  バウンスも 1 セクタ (512 バイト)。部分読みはバウンス
  経由、セクタ丸ごとの部分も最初はバウンス経由でよい
  (速度は余っている。最適化は実測してから)
- 鎖の終わりは 0x0FFFFFF8 以上。不良クラスタ
  (0x0FFFFFF7) や範囲外の値は「そこで EOF / エラー」
  として扱い、暴走しない
- ディレクトリ読み: 対象ディレクトリのクラスタ鎖を
  32 バイトエントリで走査。0x00 で終わり、0xE5 は
  削除済みで飛ばす、属性 0x0F (LFN) とボリュームラベルは
  飛ばす。ディレクトリ属性のものは、一覧では is_dir の
  印を付けて返し (下りる先として必要)、fat_find の
  途中要素としてはそのクラスタへ下りる

### 状態とメモリ

- BPB 由来の値 + FAT セクタキャッシュ 512 + データ
  バウンス 512 + 数十バイト。合計 1〜2KB 程度で、
  K210 の SRAM 予算に痛みはない
- fat_file が読み位置を持たないので、複数の fd で
  同時に対象にしても壊れない (読み自体はトラップ
  ハンドラ内で直列化される)

## 段4 との境界 (ここで決めておくこと)

- 名前空間は UNIX 型の単一の木 (fs-design.md 段4)。
  カーネルのパス解決が cwd を使って絶対パスに直し、
  正規化したうえで振り分ける。fd テーブルに「相手は
  RAM か SD か」の印を足す。
  SYS_OPEN: 解決済みパスが `/sd/` で始まれば mount 点を
  外して fat_find、そうでなければ従来どおり fs_find。
  SYS_READ: 印を見て fs_read_at / fat_read_at を
  使い分け、どちらもカーネルの小さいバウンス経由で
  copy_to_user する (今の SYS_READ の形を両対応にする)
- これにより Nish の cat は無変更で SD のファイルも
  表示できる (open/read の syscall を使うため)。
  ls の SD 対応 (readdir の扱い) は段4 で別に決める
- SD 上のプログラムの exec は v1 の対象外 (ELF ローダは
  RAM FS のファイルを相手にしている)。要るようになったら
  「read_at を関数として渡せる形にローダを一般化する」
  が筋、とだけメモしておく
- 新しい syscall は増やさない (sd-roadmap どおり)

## テストの設計 (virt)

- boards/virt/ramdisk.c: FAT32 イメージを incbin で
  埋め込み、blkdev として出す (埋め込みファイルの
  仕組みをそのまま使う)。QEMU の設定変更は要らない
- イメージの作り方 (ホスト): MBR 付きを正とする。
  dd で空ファイル → パーティションを切る → mkfs.vfat
  -F 32 → mcopy で既知の内容のファイルを入れる。
  道具の顔ぶれ (sfdisk / mtools の有無) は実装時に
  確かめて、手順を test.sh の横に残す
- test.sh に新シナリオ (L): 起動 → `/sd/` のファイルを
  cat して既知の文字列が出ること、一覧にファイル名が
  出ること、無いファイルが -1 になること。イメージには
  サブディレクトリも 1 つ作っておき、`/sd/sub/hello.txt`
  のようなパスの読みと、サブディレクトリの一覧も
  確認する
- 実機側は段1 スパイク (ブロック 0 の 0x55AA) →
  段3 のカーネルデモ (ルート一覧と小さいファイルの cat)
  → test-k210.py への SD シナリオ追加、の順で物証を積む

## 決めごと (この設計の推奨)

1. CS は GPIOHS の手動制御にする
2. FAT32 の判定は BPB の形で見る (クラスタ数の公式判定は
   使わない)
3. マウントは遅延 (最初の `/sd` 配下へのアクセス時)
4. v1 は 8.3 名・読み取り専用。ディレクトリはパスで
   たどれる (2026-11-04 改訂で追加。深さ上限 8、
   '..' は扱わない)
5. SD からの exec は v1 対象外
6. 名前空間は単一の木で、SD の mount 点は `/sd`
   (`sd:` 接頭辞は使わない。fs-design.md 段4 と対)

## 将来: mount / unmount (ユーザーの意向、2026-11-04)

v1 は固定マウントで始める: mount 点 `/sd` と FAT の
対応はカーネルに固定で、mount / unmount の操作は無く、
カードの取り外しも想定しない (この設計の範囲はここまで)。

将来は UNIX のように mount / unmount ができる姿が
望ましい、というのがユーザーの見立て。進めるときの
論点は: mount テーブル化 (パス解決の固定規則を表に
する)、使用中 (開いている fd がある) ボリュームの
unmount の扱い、カード抜き差しの検出、mount 点を
RAM 側の通常ディレクトリとして扱う形 (fs-design.md
段4 のディレクトリとここで合流する)。

未決: Nish の ls で SD をどう見せるか (段4。fat_list が
パス指定できるので `ls /sd/music/` の形は可能)、
LFN を読むだけでも入れるか (実カードのフォルダ名は
LFN が普通で、8.3 の別名表示が実用に耐えるか次第)、
読みの高速化 (CMD18 の複数ブロック読み) が要るか
(実測してから)。
