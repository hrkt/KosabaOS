# KosabaOS のリアルタイム方針 (2026-11-26)

方針の文書。個別の直しや機能 (realtime-audio-design.md
の段1・段2 など) は、この方針の下に置く。

## 目的

KosabaOS は「音を鳴らして、人が聞いておかしくない」
ことを大事にする。シンセを人が鍵盤で弾いて違和感が
ない、再生が途切れない、操作の応答が遅れて感じない。
そのために、OS の設計はリアルタイム OS 寄りの要素に
対応できる形にする。

ここで言うリアルタイムはハードリアルタイム (期限を
絶対に守る保証) ではない。目指すのは:

- 遅延とジッタに **予算** があり、設計が予算から
  逆算されている
- 予算を破ったことが **カウンタで見える** (黙って
  劣化しない)
- 待ちや割り込み停止の区間が **有界** で、無自覚に
  長い区間ができない

## 原則

### 1. カーネルの待ちは、周期仕事を止めない

カーネル内で待つとき (sleep、入力待ち、資源待ち) は、
待ちの間も周期仕事 (オーディオの装填など期限のある
仕事) が回ること。待ちが他者の期限を踏み越えてよい
理由はない。

- 待ちのループは「自分の期限だけを見る」形にしない。
  周期仕事を回し、他の走者の期限が来たら譲る
- 2026-11-26 に特定したジョブ sleep の busy-poll
  (trap 文脈のまま自走者の起床まで回り続け、audio の
  装填も前面の起床確認も止めた) は、この原則への
  違反として直す第一号

### 2. 割り込みを止める区間は短く、長ければ見えるように

trap 文脈や割り込み停止の区間では周期仕事が回らない。
だから:

- その区間は短く保つ (目安: 1ms を大きく超える処理は
  区間の中で周期仕事を回すか、区間の外へ出す)
- 長くなりうる区間には計装を置き、実測で裏を取る
  (audio の late / step_gap_max はこの道具の第一号)

### 3. 周期仕事は割り込み (または専用ハート) 駆動を本線にする

オーディオ装填のような周期仕事を、利用者プログラム
の syscall 文脈 (write の待ちループ等) に依存させ
ない。供給の担い手はタイマ割り込み、デバイスの完了
割り込み、または専用ハート (hart1) のいずれかに置く。
syscall 文脈からの手伝いは補助として残してよいが、
それが止まっても周期仕事が止まらない形にする。
(realtime-audio-design.md 段1 の選択はこの原則で決める)

### 4. 機能ごとに遅延予算を持ち、実測で裏を取る

- 鍵盤 → 音: **目標 10ms、上限 20ms**
  (realtime-audio-design.md 段2)。**最優先の予算**
  (原則 5)。画面更新が遅れても、この予算は守る側に
  倒す。10ms は鍵盤楽器で「遅れを感じない」境目の
  目安 (ハードシンセは数ms 級)。20ms は上限であって
  目標ではない。予算は平均でなく最大値で持つ
  (遅延のばらつき = ジッタも演奏感を壊すため)。
  内訳の目安: OS 側の取り分 (装填オフセット +
  ブロック滞留) を 5ms 以内に抑え、残りをアプリ側
  (入力ポーリング + 描画ブロック + 先行) に渡す
- オーディオ装填: 次ブロックの期限内 (late = 0 が
  平常、という帳簿の読み方)
- 予算はこの文書か各設計メモに数値で書き、実機の
  カウンタで裏を取る。裏が取れていない予算は
  「目標」と明記する

### 5. 優先度を持つ: 音を守り、画面は遅れてよい

仕事には優先の序列がある。競合したら、序列の下の
仕事が遅れる・間引かれる側に倒す。

1. **音の経路** (最優先): オーディオ装填、鍵盤や
   MIDI 入力から発音までの経路。期限は原則 4 の予算
2. **対話**: 前面プログラムの入力応答など、人が
   待っている操作
3. **背景**: 画面の装飾的な更新 (時計帯、セーバー、
   再描画)、急がないジョブの処理

具体的に効く場面:

- 待ちの間に回す周期仕事 (原則 1) は、音の経路を
  先に回す。画面更新は後でよいし、落としてもよい
- 割り込みを止める区間 (原則 2) で画面描画のような
  長い仕事をしない。描画は割り込みが入る文脈へ出す
- スケジューラが番を渡すとき (原則 1, 6) は、期限の
  早さに加えてこの序列を見る

序列はこの3段までで止める。細かい優先度数値や
優先度継承のような仕組みは入れない (原則 7)。

### 6. スケジューラは期限を意識する

100ms tick のラウンドロビンだけに頼らない。寝ている
走者の起床期限が来たら、tick を待たずに番を渡す
(起床駆動)。番の渡し先は原則 5 の序列と期限の早さで
決める。

### 7. やらないこと

- ハードリアルタイムの保証 (最悪実行時間の解析、
  優先度継承など) はしない
- 全面プリエンプション化はしない。協調的な作りと
  ポーリングの流儀は、原則 1〜3 と両立する範囲で保つ
- 「速くする」一般の最適化はこの方針の対象外。
  ここで扱うのは遅延とジッタの有界性だけ

## 既知の論点と、この方針への対応

| 論点 | 原則 | 行き先 |
| --- | --- | --- |
| ジョブ sleep の busy-poll が装填と前面の起床を止める (最大約0.45秒) | 1 | 段1 の前に直す第一号 |
| 装填が syscall 文脈に依存する区間がある | 3 | realtime-audio 段1 |
| 初回装填オフセット 1024 フレーム (約23ms) が 鍵盤→音の上限 20ms を単独で超える | 4 | realtime-audio 段2 (低遅延モード、OS 側の取り分 5ms 以内) |
| 停滞中に DAC が何を出すか未観測 | 2 | 計装か実機観測で一度確かめる |
| MIDI 入力 (UART 受信) | 3, 5 | realtime-audio 段4 (L1 は割り込み受信) |
| 待ちの間の画面更新が音の装填より先に走る | 5 | 周期仕事の順序を音→画面に固定する |

## 進め方

方針に触れる変更は、個別の直しとしてではなく
「どの原則の適用か」を commit や設計メモに書いて
入れる。原則そのものを変えたくなったら、この文書を
先に改める。
