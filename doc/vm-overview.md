# 仮想メモリ — 読んで学ぶためのメモ

これは仕様書ではなく、「仮想メモリ」と一口に言うとき何の話を
しているのかを、KosabaOS の現状に照らして整理する学習用
ドキュメント。VM まわりの言葉で迷ったらここに戻ってくる。

## 仮想メモリには 2 つの顔がある

- **(a) アドレス変換と保護**: プログラムが見ている住所
  (仮想アドレス、VA) と実メモリの住所 (物理アドレス、PA) を
  ずらし、触ってよい範囲を縛る側。対応表がページテーブルで、
  CPU がアクセスのたびに変換する。対応の無い住所や許可の
  ない操作はページフォルトになる
- **(b) 物理メモリの管理**: 実メモリのページを「今必要な
  ところにだけ」配る側。足りなくなったら fault をきっかけに
  増やしたり (demand paging)、使っていないものを二次記憶へ
  追い出したり (swap) する。「仮想メモリ」という言葉で
  こちらの側、特に「RAM より大きく見せる」話を指すことも多い

この 2 つは別々に育てられる。(a) があっても (b) が無ければ、
写像は起動時に固定で貼るだけになる。KosabaOS は今ちょうど
「(a) はある、(b) はこれから」という場所にいる。

## KosabaOS の現状: 変換と保護は動いている

(2026-11-06 に exec 多段化を実施し、物理メモリの管理側も
動き始めた。この文書の後半の記述は実施後の状態に合わせて
更新してある)

担当は `vm.c` (Sv39 ページング)。

- カーネル側は恒等マップ: `root_table[0]` に 0x00000000 の
  1GB (デバイス領域、読み書きのみ)、`root_table[2]` に
  0x80000000 の 1GB (RAM、読み書き実行可) を gigapage で
  貼る。VA = PA なので、カーネルは物理アドレス感覚で触れる
- ユーザー領域は `root_table[1]` の下に別建てで置く:
  コード 0x40000000 (読み + 実行)、データ 0x40200000
  (読み書き)、スタックは領域末尾寄せ (読み書き)。PTE の
  U 旗があるのはここだけで、カーネルのページには無いので、
  ユーザーモードからはカーネルのメモリに届かない。
  コードに書き込み旗が無く、データとスタックに実行旗が
  無いのが W^X の実体
- ユーザー領域の写像は 4KB ページ単位 (`set_user_pte`)。
  ページテーブル自体は `pt_pool` という静的なプール
  (8 枚) から切り出す。VA の並びが固定なのでこれで足りる
- exec のときは、段ごとのページ台帳 (後述) の内容で
  ユーザー領域の下段テーブルを書き換えて TLB を flush
  する (`vm_apply_pages`)。VA は不変で、中身の物理
  ページだけが段ごとに替わる

K210 でも同じ `vm.c` が動く。ただし MMU はドラフト版
Sv39 (特権仕様 v1.9 系) で、ページングの点火は M シム
(boards/k210/mshim.c) が担い、TLB の flush は
`sfence.vma` ではなく `sfence.vm`、ページフォルトは
専用の番号ではなく一般のアクセスフォルトとして届く。
こうした癖はボード層 (`boards/*/board.h` の
`BOARD_SFENCE_VMA` や `BOARD_DRAFT_FAULT_CODES`) が
吸収していて、共通コードは同じままになっている。

## 現状: 物理メモリはページプールから実需割り当て

(b) の側は exec 多段化 (2026-11-06) で入り始めた。

- ユーザープログラムの置き場は固定領域ではなく、プール
  (virt は 0x82200000〜 の約 94MB、K210 はカーネルの後ろ
  5MB) から 4KB ページ単位で借りる。段 (exec の深さ)
  ごとに「どの仮想ページがどの物理ページか」の台帳
  (`vm.c` の `levels`) を持ち、プログラムが終われば
  全部プールへ返す
- コード / データは ELF のセグメントが触るページだけを
  起動時に割り当てる。スタックは小さく始めて (16KB)、
  fault のたびに 1 ページずつ伸ばす。プログラムが数十 KB
  しかなければ数ページで済み、exec の深さは「置き場の
  組数」ではなく「プールの残量」で決まる (暴走防止の
  sanity 上限 16 は別に置いてある)
- fault には「違反の検出」に加えて「スタックを伸ばす」
  という正当な用事が増えた。振り分けは `trap.c`:
  スタック領域への load / store fault は伸長、それ以外は
  違反。K210 では fault がアクセスフォルト (5 / 7) として
  届く癖に合わせて判定する

残る (b) の側の大きなものは二次記憶への追い出し (swap)
で、SD への書き込みが実現したら exec の境界での一括
freeze / thaw として検討する (下の順序の 4)。

## 部品と順序 (1〜3 は実施済み、2026-11-06)

1. **ページアロケータ (page.c)**: 物理メモリを 4KB
   ページ単位で配る係。`page_init` で用意し、
   `page_alloc` / `page_free` で出し入れして、
   `page_free_count` で残りが見える。プールの範囲は
   ボードが決める (`boards/*/board.h`): virt は
   0x82200000 から RAM の末尾 (0x88000000) まで、K210 は
   固定セットを解体して 0x80100000〜0x80600000 の 5MB。
   変換 (`vm.c`) と配布 (`page.c`) を分けておくのは、
   後から利用者が増えても境界が崩れないようにするため
2. **exec 多段化が利用者第一号** (実施済み): exec の
   たびに ELF が実際に要る分だけページを取り、exit で
   全部返す。スタックは小さく始めて fault で下へ伸ばす。
   深さは「固定の小さい上限」ではなく「プールが尽きる
   まで」になった (詳細は `doc/exec-multilevel.md`)
3. **fault の役割の整理** (実施済み): 違反専用だった
   fault に「スタックを伸ばす」用事が増えた。`trap.c` で
   「スタック領域への load / store fault は伸長、
   それ以外は違反 (exec の -2)」と振り分ける。K210 では
   fault がアクセスフォルトとして届く癖を踏まえて判定
   する。カーネル経由のユーザーメモリコピーでも、対象が
   スタックなら伸ばしてから触る
4. **SD への追い出し (swap)**: SD への書き込みが実現
   したら、exec の境界で凍結した親を丸ごと SD に書き出す
   freeze / thaw が次の一手。ページ単位の細かい swap では
   なく一括なのは、出し入れのタイミングと粒度を exec の
   モデルに合わせるため

## 今は考えないもの

利用者がいないので、今は手を付けない。

- **mmap**: ファイルをメモリに写して使うプログラムが
  まだ無い
- **共有メモリ**: 並行に走るユーザータスク自体がまだ無い
- **copy-on-write**: fork が無いので出番がない
- **タスクごとのアドレス空間**: ユーザー空間は今は常に
  1 つだけ。複数のタスクがそれぞれプログラムを持つように
  なったら、そのとき satp の持ち方が論点になる

仕様は実物に引っ張られて育てるのがこの OS の進め方
(`doc/future-notes.md`) で、VM も同じく、exec の実需から
逆向きに育てる。

## 部品の地図

| 部品 | 場所 | 役割 |
|---|---|---|
| 変換と写像 | `vm.c` / `vm.h` | ページテーブル、ユーザー領域の VA 配置、W^X、段ごとのページ台帳と反映 |
| 物理ページの配布 | `page.c` | プールから 4KB ページを出し入れする係 |
| fault の受け口 | `trap.c` | ページフォルトを「伸長」か「違反」かに振り分ける |
| 配置と範囲 | `boards/*/board.h` | 物理配置、領域サイズ、プールの範囲はボードが決める |
