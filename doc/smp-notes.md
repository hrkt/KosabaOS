# SMP（デュアルコア活用）の前提と布石

状態: 検討メモ（2026-11-07 作成）。実装は未着手で、時期も決めていない。
「そのうち hart1 を有効活用したい」という将来に備えて、
今のうちに置いておける設計上の前提と、やってはいけない先行投資を整理する。

## 現状（2026-11-07 時点）

- K210 はデュアルコア（RV64 ×2 hart）。boards/k210/start.S で両 hart が
  起動コードに来て、hart0 以外は駐車する（`bnez t0, park`）。
  カーネルの状態表示にも「hart1 は駐車中」と出る。
- virt も 1 ハート運用（QEMU に複数 CPU の指定なし）。
- つまり「起こす場所」は既に決まっていて、ただ起こしていないだけの状態。

## 今から置ける布石

### 1. per-hart 状態の置き場の約束

カーネルがハートごとの状態（自分のカーネルスタック、実行中タスク、
トラップの退避先）を持つようになったとき、置き場は
「tp レジスタ → ハート別の構造体」に統一する。
約束だけを先に置けば、後で全ファイルを触り直さずに済む。
一番効く布石はこれ。

### 2. 共有データの規律

将来ハート間共有になる候補: ページプール（page.c）、FS 表（fs.c）、
カーネルログ（klog.c）、exec の台帳（vm.c）。
今ロックを入れる必要はないが、次の規律は今から効く:

- その状態を触るのは、持ち主モジュールの関数だけにする
  （概ね今そうなっている形を壊さない）。
- 「割り込みを止めれば安全」という前提の書き方を新しく増やさない。
  単一ハートでは効いても、2 ハートでは排他にならない。

### 3. K210 のキャッシュはハート間でコヒーレントでない

K210 の 2 コアの D キャッシュはハードウェア的に一致が保証されない。
ハート間共有にするデータは、次のどちらかの扱いが要る:

- キャッシュされない領域に置く、または
- 受け渡しの時点で明示的に flush / invalidate する規約にする。

virt（QEMU）では coherent なので、この前提を知らないと
「virt で動いたのに実機で化ける」型の事故になる。
共有になりそうなデータの置き場を選ぶ、という意識だけでも今置く価値がある。

### 4. 起こし方の入口とページ表の前提

- virt: SBI の hart start（HSM）で起こす。
- K210: 駐車中の hart1 を M シム側から起こす。駐車ループの置き場は既にある。
- カーネルのページ表は 1 枚を両ハートで共有する前提とする
  （ハート別に複製しない）。

## やらないこと（今は）

- 本格的な SMP スケジューラ（2 ハートでタスクを回す）の設計。
  実需が出たときに段を作る。候補の絵: hart1 側に時計や再生係のような
  常駐ものを置く（doc/scheduler-plan.md の段2 の先）。
- 先行してロックだらけにすること。使わない同期は複雑さだけが残る。

  スパイクを virt と実機で確認する。
- その先は実需を見てから。この文書の前提が効いているかは、
  そのときに答え合わせをする。
