# リアルタイム音声と MIDI 入力の準備 (設計メモ)

FM 音源アプリを MIDI キーボードからリアルタイムに鳴らす
ために、OS 側が用意するものの段立て。音源アプリ自体の
設計は別チャットの担当で、ここでは扱わない。音楽アプリ
の将来像 (FM/PSG + ミキサー + エフェクト + 外部 MIDI) の
うち、OS の供給経路に関わる部分の準備になる。

## 現状 (2026-11-25)

- 音声出力はファイル再生用に作ってある: リング 8192
  フレーム (約 186ms)、DMA ブロック最大 1024 フレーム、
  開始ゲート 1024 フレーム、装填はポーリング式
  (audio_dma_step は 100µs タイマ割り込みと作り手の
  write 待ちループから回る)。実効レート 44010Hz、
  ストリームは同時に 1 つだけ
- 消費済みフレーム数を知る手段はない (アプリは
  sleep_ms と perf_read で間接的に合わせるしかない)
- MIDI 入力の経路は無い。USB ホストスタックも無い

## 既知の問題: ブロック境界の装填遅れ

syscall の実行中は割り込みが落ちていて audio_dma_step
が回らない。長い syscall (SD 読み等) の間に DMA
ブロックが終わると、次の装填が遅れて I2S FIFO が
枯れる。リングにデータがあるので無音ブロックは
張られず、under カウンタにも乗らない (2026-11-25、
FREE128 実曲再生のブツブツの切り分けで特定)。
バッファを小さくする低遅延モードでは、この遅れが
そのまま音切れになる。低遅延化の前に手当てが要る。

## 段立て

### 段0: 装填遅れの計装 (実施済み 2026-11-26)

ブロック完了の観測が予定 (装填時刻 + ブロック長/レート)
より遅れた分を積算し、close 行に late の合計・最大・
回数を出す。仮説の数字での裏取りと、段1 の方式選択の
材料にする。再生中の挙動は変えない。

実施の形: 予定の計算にはボードの実効レート
(board_audio_actual_rate、K210 = 44010Hz) を使い、
FIFO 残量 (約 180µs) を超えた遅れだけを数える
(late = 回数、late_us = 超過分の合計 µs、late_max =
最大の遅れ µs)。詳細は doc/audio-dma-design.md 追補。

### 段1: 装填経路の手当て

候補 (段0 の数字で選ぶ):

- (a) DMAC の完了割り込みで装填する (ポーリングをやめる)
- (b) hart1 を供給係にする (SMP 設計の本来の形。
  hart0 の syscall 状態と独立に装填が回る)
- (c) 長い syscall の内側に継ぎ目を入れ、区切りごとに
  audio_dma_step を回す (SD 読みの転送ループ等)

### 段2: 低遅延モード

リング長・ブロック長・開始ゲートをストリームごとに
指定できるようにする (口の形は段2 の設計で決める:
audio_open の引数拡張か、open 後の設定 syscall か)。
目安の値:

- リング 1024〜2048 フレーム (23〜46ms)
- ブロック 128〜256 フレーム (3〜6ms)
- 鍵盤を押してから音が出るまで 20ms 以内

既存の再生 (nami 等) は既定値のままで挙動不変にする。

### 段3: 音声時計の公開

消費済みフレーム総数を返す問い合わせを用意し、
アプリの描画ループが DAC 側の進みに同期できるように
する。実効レート (44010Hz) の問い合わせも同じ口に
載せる (音程の −0.2% をアプリ側で補正できるように)。
syscall 番号は doc/syscalls.md に先に書いてから実装
する (デバイスブロックは 50 まで使用済みなので 51 以降)。

### 段4: MIDI 入力 (UART 受信スタック)

MIDI の変換は外部の担当: USB-MIDI や DIN の鍵盤から
受けて UART に流す変換器を RP2040 か Milk-V Duo S の
Arm コアで作る (どちらも後回し)。OS から見えるのは
UART に届くバイト列だけなので、変換器の選択に OS は
依存しない。ボーレートも DIN の 31250 に固定せず、
変換器に合わせるパラメータにする。

UART に届いた後のスタックは3層にする:

- L1 UART ドライバ: 割り込み受信でカーネル内リング
  バッファ (512 バイト程度) へ。MIDI は最大でも
  3125 バイト/秒で、アプリが描画計算に集中している
  間も取りこぼさない。あふれた分はカウンタで数える
- L2 入力キュー: アプリが読む先はこのキュー 1 本に
  統一する。実 UART からのバイト列に加えて、注入
  syscall でバイト列を同じキューへ流し込めるように
  する。アプリからは出所が見えない
- L3 読み口: タイムアウト付きのブロック読み +
  滞留バイト数の問い合わせ。到着時刻 (uptime 換算)
  も一緒に渡せる形にしておく (遅延の計測と、
  アプリ側のスケジューリング用)

注入経路があると、試し鳴らしが全部この 1 本で済む:
コンソールのキーをノートに変換して流す、SD の
ファイルに書いたベタなバイト列を流す、virt の
自動テストから流して出力の FNV を照合する。
実 MIDI の受け口と試し鳴らしの受け口を分けると
検証できない側が腐るので、1 本化が要点。

MIDI メッセージの解釈 (ランニングステータス等) は
アプリ側で、OS はバイト列を渡すだけ。読み口の形
(fd 形式か専用 syscall か) は段4 の設計で決める。

## 対象外 (後回し)

- USB ホスト / USB-MIDI (スタックが丸ごと無い)
- 複数プログラムのミキシング (IPC や共有メモリ。
  当面は音源 + ミキサーを 1 プログラムに内蔵する形で足りる)
- 48kHz 対応
