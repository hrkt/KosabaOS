# 特権モード (U / S / M) — 読んで学ぶためのメモ

これは仕様書ではなく、概念を腹落ちさせるための学習用ドキュメント。
KosabaOS のコードを読むときに「今どのモードで動いている話か」で
迷ったら、ここに戻ってくる。

## 3 つのモード

RISC-V の CPU には「特権モード」という身分の段階があり、
モードごとに「触っていいもの」が決まっている。

| モード | 名前 | 誰が居るか | できること |
|---|---|---|---|
| M | Machine | ファームウェア (OpenSBI など) | 全部。電源 ON 直後はここから始まる |
| S | Supervisor | OS のカーネル | ページング、トラップ処理、デバイス操作 |
| U | User | 普通のプログラム (シェルやアプリ) | S が許可したメモリだけ。危険な命令は使えない |

身分が下がるほど「できること」が減る代わりに、事故を起こしても
上の層を巻き込まない、というのが狙い。U のプログラムが暴走しても
カーネル (S) は無事で、カーネルが暴走してもファームウェア (M) が
残るので、立て直しが利く。

## モードの行き来

- **下りる**: 上のモードが「入口の住所」と「降りた先の状態」を
  設定して専用命令で降りる (S→U は `sret`、M→S も `mret`)。
  一度下りたら、自分の意思では上に戻れない。
- **上がる**: トラップ (例外・割り込み・システムコールの `ecall`)
  でのみ上がる。U で `ecall` すると S のトラップ入口に飛び、
  処理が終わると `sret` で U に戻る。これがシステムコールの実体。
- **S から M への依頼**: S は M の持ち物 (タイマ設定など) を
  直接触れない。代わりに `ecall` で M に頼むのが SBI
  (Supervisor Binary Interface)。KosabaOS の `trap_init` が
  `sbi_set_timer` を使うのはこのため。

## CSR はモードごとに家族がある

モードを制御するレジスタ (CSR) は、頭文字で家族が分かる:

- `s` で始まるもの (stvec, scause, satp, sstatus…) は S モードの道具
- `m` で始まるもの (mtvec, mhartid, mstatus…) は M モード専用。
  S からは読むことすらできない

`satp` (ページテーブルの登録) は S の道具なので、ページングは
「S モードのカーネルが使う仕組み」。M モードではアドレス変換は
原則オフ (ベア) で、そのまま物理アドレスで動く。

## KosabaOS ではどうなっているか

### QEMU virt (今までの形)

```
電源 ON → OpenSBI (M) が準備 → KosabaOS (S) が起動
         → Nish やユーザープログラム (U) を起動
```

起動メッセージの `hello from KosabaOS (S-mode)` はこの S のこと。
カーネルは S にいるので、タイマは SBI 経由、ページングは
satp (Sv39) で自分で有効にしている。

### K210 実機 (step 2 の現在地)

```
電源 ON → ROM が直接 KosabaOS を呼ぶ (M のまま、ファームウェアなし)
```

ファームウェアがいないので、カーネルが M で起きている。
入口 (boards/k210/start.S) が M 専用 CSR の `mhartid` で
hart を振り分け、`mtvec` を事故止めに設定するのはこのため。
タイマも SBI を介さず CLINT を直接叩ける (step 3 の予定)。

### step 4 で決めること (案 a / 案 b)

- **案 a**: カーネルを M モードのまま育てる。QEMU 版 (S) とは
  入口やタイマの扱いが別物になる代わり、間に何も挟まない。
- **案 b**: M に RustSBI を置き、カーネルは S モードのままにする。
  QEMU 版とほぼ同じコードが実機でも動く形。K210 のページングが
  ドラフト版 Sv39 である件の吸収も RustSBI が担う。
