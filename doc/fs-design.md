# ファイルシステム再設計の設計

状態: **確定 (2026-11-04、案A 採用)**。ユーザーの決定:
案A (ブロックチェーン) で固め、段階に分けて実装する。
数字もこの文書どおり (ブロック 4KB、段2 でファイル数 64)。
経緯は doc/future-notes.md の項目1 (create の予約方式)。
ここでは「複数ファイルを扱う道具立て (IwaC の分割コンパイル
+ リンカ等) が OS の上で動き始める」前提で、FS をどう
育てるかを考える。方針は今までどおり、わかりやすさ優先、
互換は実物の利用者を壊さない範囲で保つ。

## いまの FS の実測と、詰まる場所

現行 fs.c の形:

- 名前 → データの表 (最大 **16 ファイル**、名前は 31 文字まで)
- データは大きな arena に**連続**で詰める。create の時点で
  上限いっぱい (virt 4MB / K210 32KB) を予約し、その範囲で
  しか書けない
- 削除は無い。一度作ったファイルの領域は再起動まで戻らない

複数ファイルの道具立てから見た詰まり方:

1. **ファイル数**: IwaC の断片は 7 つ。入力ソース 8 (断片+rt)
   + 中間オブジェクト 7 + リンカ + 出力 + 既存の初期ファイルで
   16 はすぐ埋まる
2. **予約方式**: virt では 4MB 予約なので、大きなファイルは
   実質 2 つまでしか作れない (オブジェクトは数十〜数百 KB
   しかないのに、予約だけは 4MB ずつ取られる)
3. **削除が無い**: 中間ファイルを消せないので、コンパイルを
   繰り返すたびに arena とファイル表が埋まっていく

逆に、今のままで足りている点: 読み書きは逐次でよい
(コンパイラもリンカもファイルを頭から読む)、名前は平坦で
よい ('/' を名前に含めることは今でも可能で、疑似的な
階層は名前で表現できる)、永続化は要らない (RAM のまま)。

## 案A: ブロックチェーン方式 (FAT 風) — 推奨

arena を固定長ブロック (4KB) の並びと見て、ファイルは
ブロックの鎖で持つ。FAT ファイルシステムの古典的な形。

- 構造:
  - `block_next[]` 配列: 各ブロックの「次のブロック番号」。
    特別な値で「空き」と「鎖の終わり」を表す
  - ファイル表の各項は `first_block` と `size` を持つ
    (いまの `data` ポインタ + `capacity` の代わり)
  - virt: 8MB / 4KB = 2048 ブロック (表は 2048 × 4B = 8KB)
    K210: 256KB / 4KB = 64 ブロック
- 動作:
  - create: 空のファイル (ブロック 0 個) を作るだけ。
    予約はしない
  - write: 末尾のブロックに書き、足りなければ空きブロックを
    1 つ取って鎖につなぐ。必要な分だけ育つ
  - read: 鎖をたどりながら読む (fd の読み位置 → ブロック番号
    とブロック内オフセットに換算)
  - unlink (新設): 鎖の全ブロックを空きに戻し、表の項を空ける
- 長所: 断片化しない (どの空きブロックでも使える)。確保と
  解放が単純で、動きを追いやすい。ファイル数の上限と容量の
  上限が分離できる
- 短所: ファイルのデータが連続でなくなるため、「生ポインタで
  読む」前提の読み手を直す必要がある (下記)

### 読み手への影響 (案A の主な作業)

いま `f->data` の生ポインタで読んでいる場所:

- trap.c の read (fd の位置からコピー)
- trap.c の exec と kernel.c の起動 (ELF ローダへ渡す)

対策: FS に `fs_read_at(f, pos, dst, n)` (位置を指定して
読む) を用意し、読み手はこれを使う。ELF ローダはヘッダ等の
小さな読みと、セグメントのコピーを fs_read_at 経由に替える
(大きな受けバッファは持たない)。書き込み側 (fs_write_data)
は内部処理なので、鎖を伸ばす実装に差し替えるだけ。

## 案B: 連続のまま、伸長時に引っ越す方式

create は小さく確保し、足りなくなったら大きな連続領域を
取り直して中身を写す (2 倍ずつ伸ばす等)。

- 長所: 読み手の変更がゼロ (データは常に連続)
- 短所: arena に「穴」ができ、穴の管理 (空きリスト、隣接
  結合) が要る。大きなファイルの引っ越しが繰り返し起き、
  最悪の断片化では「合計は空いているのに連続で取れない」
  が戻ってくる。学びの題材としては malloc の設計そのもの
  になるので、それはそれで面白いが、FS の話からは逸れる

## 段階 (確定)

案A で進める。古典的で、構造が小さい (ブロック表と鎖) まま
容量問題が根本的に解ける。段階は:

- 段1: 内部構造を案A に置き換える。システムコールの意味は
  変えない (互換維持)。test.sh の既存シナリオがそのまま
  回帰確認になる。あわせて IwaC のセルフホスト追試
  (大きなファイルの作成・読み書き) でも確認する
  → **実施済み (2026-11-04)**: fs.c をブロックチェーン式に
  置き換え、読み手は fs_read_at に統一 (ELF ローダ含む)。
  create の予約 (BOARD_FS_CREATE_RESERVE) は廃止。
  virt test.sh 全11シナリオ ALL PASS、セルフホストの
  固定点も新しい FS で一致 (約 3MB のファイルの書き読み)。
  実機 test-k210.py は Hatoba デーモン停止のため後日確認
- 段2: ファイル数を 16 → 64 に、unlink を追加
  (新番号 12、Nish に `rm` コマンド)。割り切り: 開いている
  ファイルは削除できない (-1)。ファイル表は「使用中フラグ」
  方式にして、readdir の数え方をそろえる
- 段3 (必要になったら): ファイルサイズを返す stat、seek。
  リンカが実物として要るようになったら足す

## IwaC 側の設計との接点

- オブジェクト 1 個の大きさは断片あたり数十〜数百 KB の
  見込み → ブロック 4KB の無駄 (末尾の平均 2KB) は無視できる
- ファイル数の見積もり: 段2 の 64 で当面十分
- リンカの読み方は逐次読みでよいはず、という前提。
  もし「サイズを先に知りたい」「途中から読みたい」が
  出てきたら段3 で対応する

## 決まったこと (2026-11-04)

1. 案A (ブロックチェーン、FAT 風) を採用。ブロックは 4KB
2. 実装は段階に分ける (段1 = 内部置き換え、段2 = ファイル数
   64 と unlink)
3. 読み手は fs_read_at (位置指定読み) に統一し、ELF ローダも
   それ経由にする
