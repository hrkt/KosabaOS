KosabaOS ステップ 1〜3 まとめ

アセンブラだけの小さなカーネルが、C で書けるようになり、割り込みを受けられるようになり、 メモリ保護（ページング）まで持つようになった道のりの記録です。 対象は RISC-V (riscv64)、実行環境は QEMU virt です。

動いている間も、裏では2つの仕組みが働いています。 トラップ（タイマ割り込みを受けて 1 秒ごとに tick を出す）と、 ページング（Sv39。すべてのメモリアクセスがアドレス変換を通る）です。

ステップ 1C 言語化

狙い：この先の仕組み（ページテーブルやプロセス管理）はデータ構造の管理が中心で、 アセンブラだけでは辛い。土台を C に移すのが目的でした。

やったこと

  • start.S を「ブート専用」に縮小：スタックを用意し、.bss（初期値ゼロのはずの領域）を実際にゼロで埋め、C の kmain を呼ぶだけにした
  • 本体は kernel.c へ、UART ドライバは uart.c へ。動きはアセンブラ版とまったく同じ（hello と echo）
  • デバイスの読み書きには volatile が必須、という C 側の約束を導入（無いと最適化で状態待ちループが消える）

つまずき：.bss の範囲の印が 2 バイトずれていた

リンカスクリプトで __bss_start をセクションの外に書いたら、住所が .bss の 始まりより 2 バイト手前に確定してしまいました。そのままでは .data の末尾をゼロで潰す恐れがあります。 シンボルの確認（nm）で気づいて、セクションの中に書く正しい形に直しました。 最終的に __bss_start = 0x80200210、__bss_end = 0x80201210 と スタックの範囲ぴったり一致することを確認しています。

合言葉：ビルドの指定は -mcmodel=medany -ffreestanding。 カーネルは 0x80200000 という高い住所に住むので、デフォルトのコードモデルでは住所を扱えません。 また前提の命令セットは RV64G（= I+M+A+F+D）と決めました。実機候補はすべて G 対応で、 掛け算・割り算命令がある前提にできるからです（2026-11-01 の決定事項）。

ステップ 2トラップとタイマ割り込み

狙い：例外（エラー）や割り込み（タイマなど）を「受け取る入口」を作ること。 これはページフォルト処理と、将来のタスク切り替えの土台になります。

仕組み

タイマ割り込み
（1 秒ごと）
→
trap.S
全レジスタを
スタックに退避
→
trap.c
原因を見て処理
（tick を表示）
→
レジスタを復元して
sret で元の処理へ

割り込まれた側（echo のループ）は何も気づきません。実際、キー入力の echo の途中に tick が割り込んでも、文字は正しく続きます。実測のログです：

hello from KosabaOS (S-mode)
tick 1
abctick 2     ← "abc" の echo の直後に tick が割り込んだ様子
tick 3

タイマの予約はファームウェアに頼む

S モードからはタイマを直接設定できないので、OpenSBI の Timer 拡張 （sbi_set_timer、ecall で依頼）に「この時刻になったら割り込んで」 と頼みます。時刻の読み取りは CSR の time から。QEMU virt のタイマは 10MHz なので、1 秒 = 10,000,000 カウントです。

つまずき 3 件（全部テストで発見）

症状原因と対策
CSR 命令がアセンブラに拒否される近年の binutils では CSR 命令は Zicsr 拡張扱い。ビルド指定に拡張を含める必要があった（現在は G 前提で解決）
64 ビット割り算でリンクエラー基本命令だけの前提では割り算命令がなく、libgcc の補助関数が必要だった。G 前提に変えた今は命令で実行される
sbi_set_timer が黙って失敗機能番号を入れるレジスタ a6 を設定していなかった。明示的に 0 を入れて解決。ついでにエラーコードも確認するようにした

例外（想定外のトラップ）は、原因 scause、現場 sepc、 触った住所 stval を表示して止まります。これが次のステップの受け皿になりました。

ステップ 3Sv39 ページング — メモリ保護

狙い：プログラムから見える住所（仮想アドレス）と実際のメモリ（物理アドレス）の 対応表を CPU に渡し、すべてのアクセスを変換経由にすること。対応のない住所や 許可のない操作はページフォルトになり、OS に届きます。これがメモリ保護の心臓です。

対応表は最小形（gigapage 2 本の恒等マッピング）

仮想アドレス物理アドレス許可正体
0x00000000 〜（1GB）同じ読み・書き（実行は禁止）デバイス領域。UART (0x10000000) を含む
0x80000000 〜（1GB）同じ読み・書き・実行RAM。カーネル自身が住む
それ以外—対応なし触るとページフォルト

1GB 単位の大きなページ（gigapage）で対応させる形です。gigapage は Sv39 の仕様の一部で、 数千円台の安いボード（Milk-V Duo など）でも使えます。 仮想 = 物理なので見た目は変わりませんが、全アクセスが変換を通るようになりました。

見える成果：保護が働く瞬間

echo の最中に x キーを押すと、わざと対応のない住所 0x40000000 を 読みにいくデモが動きます。実測のログです：

vm: touching unmapped address 0x40000000 ...
trap: page fault (code=13) trap: exception scause=0x000000000000000d sepc=0x00000000802006e4 stval=0x0000000040000000

code=13 は「読みのページフォルト」、stval には触った住所そのもの （0x40000000）が記録されています。メモリ保護が実際に仕事をした証拠です。

ここまでの到達点と、次

  • KosabaOS は C で書かれ、割り込みを受けられ、メモリ保護が有効なカーネルになった
  • まだ無いもの：ユーザーモード（権限の弱い実行環境）、システムコール、複数のタスク、ファイルシステム
  • 次のステップ 4：ユーザーモードで小さなプログラムを動かし、 ecall によるシステムコール（仕様は自前で決める）で OS に仕事を頼ませる。 将来ここに乗るのが、自作 C コンパイラ IwaC です

詳しい計画は doc/roadmap-multitasking.md、命令やレジスタの早見表は arch/riscv64/instructions.md にあります。
