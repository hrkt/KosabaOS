# 実行時コード生成のドア（MAP_JIT 的な形）— 検討メモ

状態: 検討メモ（2026-11-07 作成）。実装は未着手で、決定でもない。
正本の議論は Ikesu 側 `~/workspace/ikesu/doc/plan.md` の
「検討メモ（2026-11-07）: JIT のドアは、付けるなら MAP_JIT 的に」。
本書はそれを OS 側の設計ノートとして写したもの。

## 背景

- KosabaOS のユーザープログラムは W^X で、生成したコードを実行する
  道がない（Ikesu はこのためインタプリタ方式を採っている）。
- Linux の mprotect は汎用ドアで、どのページでも理由なく W↔X を
  切り替えられる。便利だが、後からセキュリティ側が鍵を付けに来た
  歴史がある（用途を聞かずに開けたドアは閉じにくい）。
- Apple の MAP_JIT は逆に、確保時の用途宣言＋許可制で、最初から
  JIT 専用のドアとして設計されている。付けるならこの形が良い。

## KosabaOS に写す形

既存の部品で組める見立て:

1. **宣言は確保のとき** — ページプール（page.c の台帳）から
   「コード生成用」と宣言して借りる。印の付いたページだけが
   遷移の候補になる。syscall の置き場は 20〜29（プロセスとメモリ）
   ブロックが自然。タスクごとの上限と klog への記録は、
   既存の仕組み（台帳とログ）にそのまま乗る。
2. **遷移は一方向だけ** — RW（生成中）→ RX（実行）の 1 回限りで、
   戻せない。戻せる口があると通常の RWX 運用に堕ちる。
   「書く時期と実行する時期が重ならない」ことを、運用ではなく
   ドアの形そのもので担保する。
3. **中身はカーネルが検証しない** — wasm の正しさの検証は
   Ikesu の仕事のまま。カーネルは印付きページの権限遷移だけを
   知る（層の約束は不変）。

## 割り切り

- Apple のスレッド別の見え方（書く側だけ W に見え、他は X）は
  K210 の MMU ではできない。ページ表の見え方はタスクで 1 つ
  なので、KosabaOS 版は「時間で分ける一方向フリップ」が現実解。
- 実装時の本当の山はキャッシュ。K210 の I キャッシュと
  D キャッシュは非コヒーレントなので、フリップ時に fence.i と
  キャッシュの掃除が必須になる（doc/smp-notes.md の布石 3 と
  同種の論点）。
