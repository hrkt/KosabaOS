# SD カード + MP3 再生へのロードマップ

状態: 確定 (2026-11-04、ユーザーが段取りを承認)。OS 側
(ストレージ側) の計画。
音を出す側 (I2S ドライバとオーディオ syscall、Ikesu と
player.wasm) は Ikesu 計画 (段0〜段6) が持ち、本書は
「SD カードの上の MP3 ファイルを読めるようにする」側だけを
扱う。2 つはユーザープログラムのところで合流する:

    SD の MP3 → (この計画) 読む → プレーヤー (Ikesu 等) が
    デコード → PCM → (Ikesu 計画) オーディオ syscall → 音

## なぜ要るか

- K210 の RAM FS は arena 256KB。MP3 1 曲 (数 MB) は
  そもそも置けない。Ikesu 計画の初版は「短い低ビットレート
  音源を埋め込み」で切り分け済みで、普通の曲は SD 対応が前提
- MP3 は逐次読みで足りる (デコーダは頭から少しずつ読む)。
  丸ごとメモリに載せる必要はなく、位置指定読み
  (fs_read_at と同じ形) で流せばよい

## 段0: 下調べ (実物の確認)

- Maix Dock の TF スロットの配線を回路図 (Sipeed) で確定:
  SPI の系統とピン、FPIOA の割り当て。LCD や Flash と
  バスを共有しているか (チップセレクトの関係) も確認
- MaixPy で SD をマウントし、テストファイルを読めることを
  確認 (カードとスロットが生きていることの物証)。カードは
  FAT32 で用意する
- スピーカー側の部品 (TM8211 + PAM8403 がボード上に在る
  ことは Ikesu 計画で確認済み) は本書の範囲外

### 段0 の途中経過 (2026-11-04、公開資料で確認できた分)

- K210 には SDIO ハードウェアが無い。SD への経路は
  SPI モードのみ (Sipeed Wiki の MaixPy FAQ に明記)。
  本書の前提どおりで問題なし
- Maix Dock (M1) に TF スロットが載っていることは
  複数資料で確認。スロットの配線は PCB 上で固定なので、
  ピンは「回路図か MaixPy の Dock 向け既定値」で確定する。
  最有力は SPI1 系: SCLK=IO27 / MISO=IO26 / MOSI=IO28
  (Sipeed Wiki の SPI 例がこのピン組)。CS は GPIO の
  一本で、番号は回路図で裏取りする
- カードの相性注意 (Sipeed Wiki): SPI モードに正しく
  対応しないカードが市販品にある。Class10 の正規品を
  推奨、128GB まで動作実績ありとのこと
- 残り: 回路図でのピン確定と、MaixPy での実機マウント
  確認 (Hatoba デーモン復帰後、段1の実機確認と一緒に
  まとめて行うと効率がよい)

## 段1: スパイク (カーネルの外で SD を読む)

spike-sd/ に使い捨ての実験コード:

- FPIOA + SPI ドライバ (K210 の SPI を標準モードで)
- SD カードの SPI モード初期化: CMD0 → CMD8 → ACMD41 →
  CMD58 の流れでカードを使える状態にする
- ブロック 0 (512 バイト) を読んで、末尾の 0x55AA と
  MBR の中身を表示する

ここまで来れば「カードと電気的に話せる」ことが確定する。

## 段2: カーネルへ (ブロックデバイスとして)

- SPI + SD ドライバを board 層 (boards/k210/) に置く
- 共通コード側は「ブロックデバイス」の抽象だけを見る:
  read_block(ブロック番号, バッファ) が引ける構造にする。
  virt / テスト用には RAM 上のイメージを相手にする実装を
  用意すると、FAT 側を実機なしで test.sh に載せられる
- カーネルコンソールのデモキーでセクタ読みを確認

## 段3: FAT32 読み取り専用ドライバ

- MBR → パーティション → BPB → FAT の鎖をたどって読む
  (鎖の考え方は RAM FS のブロックチェーンと同じ)
- ルートディレクトリの一覧と、名前でファイルを開いて
  頭から読むところまで。最初は 8.3 形式の名前でよい
  (長い名前 LFN は後で)
- 書き込みはしない (読み取り専用にすると FAT の更新・
  ディレクトリ書き換え・時刻まわりが全部落ちて、桁違いに
  簡単になる)
- カーネルデモ: SD のルート一覧と、小さいテキストの cat

## 段4: syscall への統合

- open / read の名前で振り分ける: 接頭辞 (案: `sd:`) が
  付いた名前は FAT 側、それ以外は RAM FS 側が受ける。
  例: open("sd:music.mp3")
- 読みは位置指定 (read_at 形) で FAT 側が受ける。小さい
  セクタキャッシュ (例 8KB) を挟む。同時に開く SD ファイル
  は当面 1 つでよい (実行モデルが単一プログラムなので)
- Nish からも cat できるようにし、`ls` の扱い (SD 側の
  一覧をどう見せるか) はここで決める

## 段5: 実曲での確認

- 数 MB の MP3 を SD からユーザープログラムが最後まで
  読み切れること (チェックサム等で全バイト確認)
- Ikesu 計画の段6 と合流: SD の MP3 → デコード → 実機の音

## 割り切りと未決事項

- 対象は K210 実機のみ (SD スロットも I2S もボードの話。
  共通コードは FAT とブロックデバイス抽象だけ)
- カードは起動前に挿しておく前提 (抜き差しの検出はしない)
- FAT32 のみ (exFAT は対象外)、読み取り専用
- SPI の速度は MP3 のビットレート (最大でも 40KB/s 程度)
  に対して十分すぎる見込み。下調べで実測する
- 未決: 名前の接頭辞の形 (`sd:` か他の書き方か)、Nish の
  一覧表示との統合の仕方、LFN を入れるかどうか
