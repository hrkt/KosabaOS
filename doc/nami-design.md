# nami — 音声ファイル再生プレーヤーの設計

状態: 設計（2026-11-08、ユーザーが着手と名前を決定）。
コマンド名は **nami**（波＝音の波形。Nish・Ikesu・shirasu の
海の並び）。今回の範囲は **WAV の再生**まで。MP3 は形式の
振り分け口だけ用意し、渡されたら「まだ扱えない」と綺麗に
返して終わる。デコーダ本体は作らない（Ikesu 側の独自
デコーダが別にあり、接続は将来の仕事）。

## なぜ IwaC か

nami は gcc ではなく **IwaC**（自作 C サブセット
コンパイラ）で作る。理由は将来の接続にある: MP3 の
デコーダは Ikesu 側で IwaC によって開発が進んでおり
（独自デコーダ段6）、将来 `play_mp3()` の受け口に
デコーダを差すとき、プレーヤーとデコーダが同一の
ツールチェーン・同一の言語サブセットで揃っている方が
繋ぎ目が小さい。nami はその先行例として、IwaC の
プログラムの作法（段6 の main_kosaba.c が前例）で書く。

## ビルド経路と OS への取り込み

- ソースは `arch/riscv64/nami/` に置く（nami.c、
  wavgen.c、build-nami.sh）
- `nami/build-nami.sh` が IwaC のチェーンを回す:
  `iwac --kosaba --elf nami.c` で ELF オブジェクト
  (.eo) を出し、リンカ **nori** で nami.elf に組む
  （wavgen.elf も同じ）。ツールチェーンの場所は
  環境変数 `IWAC_DIR` で差し替え可能（既定は兄弟
  ディレクトリの `~/workspace/iwac/iwac`、IKESU_DIR
  と同じ流儀）。バイナリが無ければ各 build.sh で作る
- OS 側 (build.sh) は IKESU_EMBED と同じ「素材があれば
  取り込む」方式: nami/nami.elf と nami/wavgen.elf が
  そろっていればステージングして -DNAMI_EMBED で
  埋め込み、無ければ取り込まない。その場合 test.sh の
  シナリオ AC は SKIP になる（シナリオ U の扱いに倣う）

## IwaC サブセットへの適合

nami / wavgen のソースは IwaC の現行 main の範囲で書く。
使うもの: 幅つき整数（int32 / int64）、ファイル
スコープの変数と配列、関数、ポインタと配列の添字、
`#define`、組み込みの `putc` と `syscall3`。
**使わないもの**（サブセットの外、または今回の方針）:

- `switch`（未対応）→ 形式の振り分けは if-else で書く
- 浮動小数点（使わない）→ WAV 再生は整数演算のみ。
  wavgen のサイン波も固定小数点の漸化式で作る
- 文字リテラル（コーパスの作法に合わせ、文字コードを
  数で書く。文字列リテラルは使う）
- 構造体（今回は要らない。fmt の項目は個別の変数で持つ）
- `#include` と libc（宣言は自前。入口は `main(argc,
  argv)` で、戻り値が終了ステータスになる --kosaba の
  約束に従う）

## 既知の問題: nori のデータ配置と alignment

実機 (K210) の検証で踏んだ IwaC 側の問題。nori のリンクは
データ (文字列 → 配列 → グローバル) を詰めて並べるが、
段の開始を 8 バイト境界に揃えない。そのためスカラ型の
グローバル変数が奇数アドレスに置かれることがあり
(実測: wavgen の int64 グローバルが 0x40201091)、K210
では misaligned アクセスとして M シムが止まる。QEMU
(virt) は misaligned を透過処理するので見えない。
これは IwaC / nori 側で直すべき問題として切り分ける。

nami / wavgen での回避策 (当面の作法): ファイルスコープ
にはバイト単位でしか触らない char 配列だけを置き、
スカラ型の状態は関数のローカル (フレームのスロットは
8 バイト単位で揃う) に持つ。wavgen の FNV 状態は
main のローカル、nami の読みの状態は main のローカル
配列をポインタで渡す形にした。

## 使い方と登録

- 起動は `run nami <ファイル>`。埋め込み FS には拡張子なしの
  **"nami"** で登録する（名前解決は完全一致なので、これで
  `run nami` の形がそのまま通る。本体ファイルは nami.elf）
- 引数は既存の argv（argv[1] = ファイルパス）。/sd の
  ファイルも RAM FS のファイルも、open/read の既存 syscall
  経由で同じに扱う（nami 自身を /sd に置いて実行することも
  できる）
- 使う syscall は既存のものだけ: open(4) / read(5) /
  close(6) / audio_open(40) / audio_write(41) /
  audio_close(42)。新 syscall はなし

## 形式の振り分け

拡張子は信用せず、**先頭バイト（マジック）で判別**する。

- `RIFF....WAVE` → WAV として解析する
- `ID3`、または MP3 フレーム同期（0xFF の次に 0xE0 台）→
  MP3 と認識し、未対応として断る
- それ以外 → 「形式が分からない」として断る

振り分けは関数境界として分けておく: `play_wav()` が今回の
実装で、`play_mp3()` は「未対応を出すだけの受け口」。
将来 MP3 を扱うときは、Ikesu 側デコーダの呼び出しを
`play_mp3()` の中身として差し込む（振り分けと表示の
約束は変えない）。

## WAV の対応範囲（v1）

- RIFF/WAVE、fmt チャンク + data チャンク。知らない
  チャンクは読み飛ばす（チャンクは偶数境界にそろい、
  奇数サイズにはパディング 1 バイトが付く約束どおり）
- fmt: **PCM（format 1）・16bit・モノラル/ステレオ**だけ。
  data チャンクの宣言サイズの範囲内だけを再生し、
  後続チャンクを音として読まない
- ストリーミング再生: ファイルをメモリに載せ切らず、
  バッファ（4096 バイト）単位で read → audio_write を
  繰り返す。audio_write の部分受け付けには残りを再送
  して対応する。読みはフレーム境界（blockAlign の倍数）
  に切りそろえる

対象外は綺麗に断る: 8bit / 24bit / 32bit、非 PCM
（float・ADPCM 等）、3 チャンネル以上、fmt が無い・
壊れているファイル。

## サンプルレートの方針

- fmt のレートとチャンネル数でそのまま audio_open する。
  **44100 が本線**
- open が -1 を返したら（K210 のドライバは実レートが
  要求の 1% 以内のときだけ受けるので、48000 は -1 に
  なる）、「このレートは扱えない」と表示して終わる
- **リサンプリングは v1 ではしない**。レート変換が要る
  日が来たら、その時に考える

## 表示と終了ステータス

表示は最小限（人が読める短い行だけ）:

- 再生開始: `nami: <パス>` と、WAV が確定したら
  `nami: 44100 Hz mono, 88200 samples (2 s)` の 1 行
  （秒は整数の割り算）
- 正常終了: `nami: done`

終了ステータス（Nish が `run: exit status N` で出す）:

| status | 意味 | 表示の例 |
| --- | --- | --- |
| 0 | 再生が最後まで済んだ | `nami: done` |
| 1 | ファイルが開けない・読めない・再生中の失敗 | `nami: cannot open <パス>` |
| 2 | 引数が足りない | `usage: nami <file>` |
| 3 | 形式は分かるが v1 の対象外（MP3、非 PCM、16bit 以外、レート非対応） | `nami: mp3 is not supported yet` |
| 4 | 形式が分からない・壊れている | `nami: unknown format` |

再生の途中で失敗したら、開いたオーディオは閉じてから
終わる（close の要約行が dmesg に残る形は崩さない）。

## 検証の物差し

再生後の dmesg の `audio: close rate=<r> channels=<c>
samples=<n> fnv=<16 桁>` が、**再生した WAV の data
チャンクのバイト列**から計算した samples / FNV-1a 64bit
と一致すること（virt・実機共通の強い照合。シナリオ T の
FNV 照合と同じ考え方）。

- virt（シナリオ AC）: ホストで make_test_wav.py が
  テスト WAV（44100Hz・モノラル 16bit・440Hz サイン波・
  振幅 8000・2 秒 = 88200 サンプル）を生成し、
  make_sd_image.py の取り込み口（名前=ホストパス）で
  TEST.WAV として SD イメージに置く。期待値はテスト側が
  そのファイルの data チャンクから計算する
- 実機（シナリオ K22）: カードへ WAV を置く手段として
  wavgen.elf（サイン波 WAV を /sd へ create/write で書く
  小さな生成プログラム。nami と同じく IwaC 製で、
  サイン波は固定小数点の漸化式で作る）を用意する。
  wavgen は自分が書いた PCM の FNV を表示し、nami の
  再生後の close 行と装置の中で突き合わせる（ホスト
  生成のサンプル列と一致する必要はない）
- エラー系もシナリオに入れる: 無いファイル（status 1）、
  WAV でない既存ファイル（status 4）、MP3 を渡す
  （ID3 で始まるファイル、status 3）、引数なし
  （status 2）

音が実際に出るかは、スピーカー未接続のため今回の
検証範囲の外（シリアル側の照合まで）。

## MP3 の対応（2026-11-21、段1: モノラル）

命名の整理（ユーザーの決定）: 独自 MP3 デコーダは nami の
一部として育てる。Ikesu は Wasm ランタイムの名前であり、
ネイティブデコーダは Ikesu ではない。

移設: デコーダ本体 mp3dec.c と表 5 本（hufftab / sfbtab /
powtab / imdcttab / dcttab）を、Ikesu プロジェクトの
native/ からバイト同一のまま arch/riscv64/nami/ へ移した。
デコーダの正しさの実績（ホスト参照との PCM バイト一致、
実機再生）はこのコピーにそのまま引き継がれる。

統合の形: ビルドは連結 1 本の TU（詰め物 → 表 → mp3dec.c
→ nami.c、build-nami.sh）。デコーダのバイト源 dec_read は
nami の reader_read に直結する（どちらも「最大 n バイト
まで入れ、EOF では 0」という同じ契約）。main がマジック
判定で読んだ先頭 4 バイトは、play_mp3 が lseek で先頭へ
巻き戻してからデコーダに渡す。

再生の形: フレーム単位の「デコード → audio_write」の
直列。Ikesu 側では FIFO 飢えを避けるため 2 フェーズ
（全デコード → RAM から再生）が要ったが、カーネルの
リングバッファ（doc/audio-driver-design.md 追補3）が
供給を書き手から切り離したので、直列で足りる。再生中の
SD 読みの間はフィーダが止まる弱点は残るが、MP3 の入力
読みは小さく疎なので影響は WAV より小さい。根本策は
SMP の hart1 供給係（doc/smp-design.md）。

範囲（段1）: MPEG-1 Layer III、モノラルのみ。サンプル
レートはドライバが受ける 44100 のときだけ開ける（他は
status 3）。ステレオはデコード自体が実時間に届かない
ため status 3 で断る（SMP と高速化の後、段3で挑戦する）。
→ ステレオは追補 (2026-11-22) で受け付けるようにした。

状態の置き場: デコーダ状態と読みの状態は struct NamiMp3
（dec + st[3]）に集め、nami.c の g_mpad で 8 バイト境界へ
寄せる。表の境界は build-nami.sh の g_tpad が担う。どち
らも大きさはビルド後の実測で合わせる（Ikesu 側の
main_twophase.c と同じ考え方）。

検証の物差し: virt で TEST.MP3（モノラル）を再生し、
カーネルの `audio: close` 行の fnv が参照値
f5d45f269d5c4911（Ikesu 段7 でホスト参照と一致済み）と
一致すること。実機では耳で確認する。

## 追補 (2026-11-21): 配置ずれとトラップ洪水

実機のストリーミング再生が実時間の約 7 倍遅かった件の
真因は、供給側でも SD でも syscall でもなく、nami.elf
自身の配置ずれによる misaligned トラップの洪水だった。
nori はセクションを詰めて並べるだけで境界に寄せない
ため、文字列プールの大きさが変わると後ろの配置が全部
ずれる。今回ずれていたのは 2 層:

- 表 (.iwac.arrays): 合成フィルタの int32 配列
  synth_d / synth_row が 4 バイト境界から +3 ずれ、
  サンプル単位の読みが全部トラップしていた
  (g_tpad 4 → 5 で解消)
- デコーダ状態 (g_mp3): データ領域の総量が奇数で
  構造体の基底が +1 ずれ、全メンバへのアクセスが
  トラップしていた (g_mpad 9 → 16 で解消)

QEMU (virt) は misaligned を静かに吸収するので virt
検証では一切見えず、実機でだけ M シムの emulation
(+ ログ出力) が 1 曲で数百万回走っていた。切り分けは
dmesg の `trap: misaligned emulated` 行の pc / addr を
.eo のシンボル配置へ突き合わせて行った。

対処: 詰め物を直した上で、build-nami.sh に
check-align.py を組み込んだ。.eo から最終アドレスを
再現し、synth_d / synth_row / cbrt_q24 の 4 バイト
境界と g_mp3 基底の 8 バイト境界をビルド時に検査する。
文字列や表を変えたら、落ちるのはこの検査が先になる。

結果: 実機で under=0、frames=170496 (曲と一致)、
open から close まで約 4 秒 (曲は 3.865 秒) で、
モノラル MP3 の SD ストリーミング再生が実時間に
到達した。

## 追補 (2026-11-22): ステレオ対応

供給側が DMA 化され (doc/audio-dma-design.md)、再生
経路が普通に使えるようになったのを受け、play_mp3 が
ステレオ (channels=2) を受け付けるようにした。デコーダ
コアはもともとステレオをデコードでき、変更は nami の
受け口だけ:

- channels は 1 / 2 を受け、audio_open にそのまま渡す。
  リングと DMA はステレオ前提の形 (1 フレーム = L/R の
  2 ワード) なので、再生経路側の変更はない。書き込み
  ループは従来どおり 1152 × channels サンプル単位
- サンプルレートは 44100 のみ受ける。ドライバが
  44.1kHz 固定のため、48kHz 等は開く前に status 3 で
  きれいに断る (表示 `nami: mp3 rate <n> is not
  supported`)
- channels が 1 / 2 以外も status 3 で断る

文字列が増えて配置がずれたため g_tpad は 5 → 8 に
調整した (check-align.py が検出、境界は全部元通り)。

検証の物差し: Ikesu 側の st44_128j.mp3 (44.1kHz
ステレオ joint 128kbps、4.86 秒、ID3v2 付き)。virt の
SD イメージに素材があるときだけ入り (build.sh が
IKESU_DIR から借りる)、test.sh シナリオ AC が
`audio: close ... channels=2 samples=428544
fnv=f002ac917546f7dd` (Ikesu 段6 の参照値) を見る。
実機では under と壁時間で不足分を測り、チューニングは
その後で効く順にやる。

## 追補 (2026-11-23): デコーダにゼロバンドスキップを取り込み

mp3dec.c を Ikesu 側 main (56e3391) の版に差し替えた。
段4 の IMDCT で、入力 18 個が全ゼロのサブバンドを
「overlap への窓掛け＋状態を 0 に」だけへ畳む近道。
消える項はすべて 0 との積なので出力はビット単位で
不変 (virt で mono/stereo とも FNV 従来値と一致を
確認)。実測 (Ikesu 側 PERFSTG、基板2): 段4 の
cycles −43.9%、デコード全体 −11.8% で、128kbps は
デコード単体で実時間を切った。320kbps は約 1.02 倍
(投影) で、残りは再生経路側の上乗せが候補。

## 追補 (2026-11-23): 合成の窓掛けループ組み替えを取り込み

mp3dec.c を Ikesu 側 main (27f69eb) の版に差し替えた。
synth_granule の窓掛けで、履歴リングの折り返し判定を
タップごとにしていたのを、tau の範囲を 2 つのランに
分けて分岐を消したもの。読む項と加算の順序は従来と
完全に同じで、出力はビット不変 (virt で mono/stereo
とも FNV 従来値と一致を確認)。実測 (Ikesu 側
PERFSTG、基板2): デコード全体 −3.6% で 128kbps は
0.938 倍、320kbps は投影で約 0.99 倍。
