# スケジューラとタイマの計画（置き時計から始める）

状態: 計画（2026-11-06 作成）。段1・段2 を 2026-11-07 に実装
（branch `scheduler`）。段3 も 2026-11-07 に実装
（branch `job-control`、設計は doc/jobs-design.md）。
この文書は「何を、どの順で作るか」の計画書であり、仕様は実装の段ごとに確定させる。

## 背景

RTC から壁時計が読めるようになる（doc/time.md）と、残るのは
「1 秒ごとに画面を更新し続ける実行の形」である。
机の上で時刻を表示し続ける置き時計が、この OS にとって
スケジューラとタイマの最初の実需になる。

これまでと同じく、実物が見えるまで入れない。時計がその実物である。

## 実施の記録（2026-11-07、段1・段2）

計画が書かれてから実施までの間に、前提が 1 つ動いた:
置き時計そのものは段2 を待たずに、カーネルの描画経路
（K210 では M シムの割り込み文脈から lcd_tick_draw）で
先に達成された（2026-11-07、main 281ff86）。その形の弱点は
「入力待ちで割り込みが戻らない間は LCD の秒が止まる」
ことだった（SYS_GETC はトラップの中でポーリングし、その間
タイマ割り込みが取れない。M 側の描画も S 側の再予約に
連鎖していたので一緒に止まる）。

したがって段2 の意味は「時計を初めて動かす」ではなく、
「時計の更新を割り込み文脈の描画から、sleep して起きる
常駐カーネルタスクの仕事へ移す」になった。移した結果、
物差し（入力待ちの間も秒が進む）はシリアル側の証跡で
測れるようになった（test.sh シナリオ W、test-k210.py
シナリオ K16。LCD のピクセルそのものは目視の担当）。

実装の要点（詳細はコードのコメント）:

- 段1: タスクの状態に TASK_SLEEPING を 1 つ足し、起床時刻は
  time CSR の生カウントで持つ（trap.c の tick は割り込みが
  滞る文脈では一緒に滞るので、sleep の物差しにはしない）。
  起床判定は schedule() の入口と trap.c のタイマ割り込み。
  タイマ側は「寝ていたタスクの起床時刻が来たときだけ」
  切り替える（起床駆動）。毎 tick の強制切替はデモの
  第 2 幕だけに残した。ユーザー向け sleep syscall は足して
  いない（段3 の話）。
- 段2: 時計タスク（タスク 3）を kmain の初期化で常駐させ、
  スケジューラは以後ずっと生かす。待ちの側がスケジューラを
  回すのが肝で、SYS_GETC とカーネルコンソールの入力待ちは
  uart_try_getc のポーリングの合間に sched_poll() を呼ぶ
  （トラップ文脈では割り込みを入れられないので、yield()
  ではなく割り込み状態に触らない口を用意した）。M シムの
  割り込み文脈の描画は外し、描画は時計タスクだけが行う。
  起床の記録は klog のログ専用口（lkputs）で残し、ps の
  wakes でも追える。
- 実踏みの注意: タスクの初回入口（トランポリン）は割り込み
  許可を立て直すが、それが安全なのはトラップの入口が
  カーネル側（trap_entry）のときだけ。ユーザー実行中は
  stvec が trap_entry_user で sscratch がユーザーの sp を
  保持しており、そこで許可すると次の割り込みが sp を
  取り違えてユーザーのスタックへ退避を書く。enable_
  interrupts に「入口がカーネル側のときだけ」という番人を
  入れた（test.sh シナリオ W の初期版で実踏みして特定）。

## 現状（2026-11-06 時点、計画当時）

- タイマ割り込みは 100ms ごと。tick（起動以来の秒数）はカーネルが持っている。
- タスクの切替そのものはある（協調＋プリエンプティブのデモ、test.sh シナリオ D）。
  ただしデモの中だけの仕組みで、通常のプログラム実行とはつながっていない。
- exec は「走って、終わる」モデル。子が走っている間、親（Nish）は待つだけ。
- 「寝て、起きる」口がない。何かを周期的にするプログラムは
  ビジーループで回すしかない。

## 原則

- ごく単純に始める。新スケジューラは作らず、既存のタスク切替を育てる。
- 優先度は入れない。ラウンドロビン＋sleep まで。
- 実需（時計）が物差し。時計に要らない仕組みは入れない。
- syscall が要る段では、例によって syscalls.md へ先行追記してから実装する。

## 段立て

### 段1: sleep（寝て起きる口）【済み、2026-11-07】

- タスクが「◯ tick 先まで寝る」と言える仕組み。寝ている間は他のタスクが進む。
- 実装の芯は、タイマ割り込み側で起床時刻を見て起こすこと。
  既存の切替に「起床待ち」の状態を 1 つ足すだけに収める。
- 物差し: 寝ているタスクがある間も Nish（あるいはデモの相手タスク）が
  応答し続け、起床が指定した tick の前後で起きること。
- 実施: task_sleep_ms（ミリ秒指定）として実装。上の
  「実施の記録」に要点。物差しは段2 の時計タスクで
  まとめて測った（シナリオ W / K16 の起床回数）。

### 段2: 部分プロセス第 1 号 = 時計タスク【済み、2026-11-07】

- OS の一部（時刻表示）を、独立した常駐タスクとして動かす。
  これが「部分のプロセスを動かす」の到達点。
- 時計タスクはカーネル内タスクとする（RTC の API がカーネル内にあるため。
  ユーザープログラム化は段3）。RTC（無ければ uptime）を読んで
  LCD を 1 秒ごとに更新する。LCD は時計タスクが占有する
  （シリアルコンソールとは別物なので Nish とは衝突しない）。
- 物差し: Nish でコマンドを打っている間も LCD の秒表示が進み続けること。
  実機（LCD のある Maixduino が本命、Maix Dock でも可）で目視確認する。
- 実施: 前提が動いた経緯と実施内容は上の「実施の記録」に。
  物差しのシリアル側はシナリオ W（virt）と K16（実機）で
  確認した。LCD のピクセルで秒が進むところは目視の担当
  として残る。

### 段3: ユーザープログラムの常駐【済み、2026-11-07、branch `job-control`】

- sleep の syscall 公開と、ユーザープログラムのバックグラウンド常駐。
- やるかどうかは段2 の時計が動いてから判断する。今は設計しない。
- 到達点の命名（2026-11-07、ユーザー）: 「Nish で bg ジョブに
  したプログラムが並行で走ること」。段3 に必要だった実需は
  これで生まれた。
- 実施: 設計は doc/jobs-design.md に起こし、branch
  `job-control` で実装した。形は「新しいスケジューラは
  作らない」原則のまま、trap.c の中に走者（前面の exec 鎖と
  ジョブ最大 4 本）を増やし、切り替えはトラップ境界だけ
  （タイマ割り込みのラウンドロビン＋getc の受け渡し）。
  ページ台帳・fd 表・cwd は走者ごとのまま exec 多段化の
  考え方を継いだ。コンソール仲裁は合意どおりの Linux の
  縮小形（入力は持ち主だけ、bg の getc は停止、出力は
  混ざってよい）。syscall は 20〜22（job_run / job_list /
  job_wait）を syscalls.md へ先行追記してから実装。
  sleep の syscall 公開は今回の到達点には要らなかったので
  見送った（ジョブ側の待ちは uptime のポーリングで足りた）。
  物差しは test.sh シナリオ X（virt）と test-k210.py
  シナリオ K17（実機）。

## やらないこと

- 優先度つきスケジューリング、リアルタイム保証
- プロセス間通信
- 時計以外の常駐ものの一般化（段3 で実需を見てから）

## 前提との関係

- RTC の壁時計: branch `rtc` で実装し main にマージ済み（doc/time.md）。
  段2 の時計の入力。
- uptime: syscall 化して main にマージ済み。段1 の sleep の数えの土台
  （実施では生の time CSR を直接使った）。
