# オーディオ DMA 化の設計 (2026-11-21)

## 発端

SMP 段2 (hart1 供給係) までで数字は全部そろった
(under=0、フレーム数ちょうど、FNV 一致、実時間再生)
のに、ユーザーの耳では細かいプツプツが残った。
補充の窓・キャッシュ追い出し・FIFO の猶予を詰めても
消えず、「ドラスティックに変えないとダメ」との判断で
**供給を CPU の手運びから DMA に替える** (ユーザー決定)。

K210 の実用的な音声実装 (Kendryte SDK、MaixPy) は
すべて DMAC が SRAM から I2S へ直接流す方式で、
うちだけが段1 の割り切り「DMA なし・FIFO ポーリング」
のまま来た。DMA 化で、補充の窓という問題のクラス
自体が消える。これで直らなければ残るはアナログ側
(DAC/アンプ/電源/スピーカー) と切り分けが確定する。

## ハードウェアの事実 (SDK のドライバで確認)

- DMAC は 0x50000000、64 ビットレジスタ、6 チャンネル。
  チャンネル n のレジスタ塊は 0x50000100 + n*0x100:
  sar +0x00 / dar +0x08 / block_ts +0x10 / ctl +0x18 /
  cfg +0x20 / intstatus +0x88 / intclear +0x98。
  共通: cfg +0x10 (bit0 = dmac_en)、chen +0x18
  (bit n = ch n 有効、bit n+8 = その書込許可)。
- SYSCTL: clk_en_peri (0x5044002C) の bit1 = DMA クロック。
  dma_sel0 (0x50440064) にチャンネルごとの 6 ビット欄が
  あり、I2S0 TX の選択値は 25。
- I2S0 の DMA 宛先は専用レジスタ txdma (0x502501C8)。
  LTHR/RTHR ではないので左右の宛先問題はない。
- I2S CCR (0x50250010): bit8 = dma_tx_en、bit10 =
  dma_divide_16。divide_16 を使うと 32 ビット 1 ワードが
  左右 2 つの 16 ビットに分かれて入る。つまり DMA
  バッファは「L を下位 16、R を上位 16 に詰めた
  ステレオフレーム列」そのものになる (左右の対応は
  段0 で要確認。モノラルは左右同値なので影響なし)。

- DMAC のチャンネル設定 (メモリ→周辺、32 ビット幅、
  バースト 1): ctl = dms(MASTER2) + dinc(固定) +
  src/dst_tr_width(32)。cfg = tt_fc(MEM2PRF) +
  hs_sel_src(ソフト) + hs_sel_dst(ハード) +
  src_per/dst_per = チャンネル番号。block_ts = 語数-1。
  完了判定は chen のビットが落ちること (SDK の
  dmac_is_idle と同じ)。
- キャッシュ: K210 の D キャッシュは DMA と
  コヒーレントでない (SDK 自身がコピーで回避する)。
  うちは「作り手が公開時に追い出す」既存の作法で
  リングのデータが SRAM に出ていることを使う。

## 方式: リングを直接読ませる

ピンポンのコピー段は作らない。**DMAC にリング
バッファ自体を読ませる**:

- リングの中身を「詰めたステレオフレーム列」に変える。
  モノラルの複製は取り出し側 (pop) でなく **投入側**
  (audio_write の enqueue) で行う。以後のリングは
  1 フレーム = 4 バイトのバイト列として扱う。
- 供給はブロック単位 (1024 フレーム = 約 23ms)。
  100µs の供給 tick (audio_feed、既存) が完了を
  ポーリングし、次のブロックを張り直す: SAR =
  リングの読み位置、語数 = 尾までの連続分 (リングの
  折り返しを跨がない)。張り直しはレジスタ書きだけ
  で、追い出しは要らない (データは公開時に SRAM へ
  出ている)。
- リングが空なら無音ブロック (静的な 0 の塊) を
  張り直し続け、不足分は under として数える。
- close は DMA の読み位置が尾に届くまで待ち
  (drain)、チャンネルを止めてから I2S を閉じる。
  フレーム数の帳簿は完了ブロックの合計で付ける。
- hart1 供給係は引退する (SMP 段1 の起動と心拍は
  残る)。DMA 初期化に失敗したら従来の割り込み
  フィーダへフォールバックする。

## 段立て

- 段0 (スパイク): audio_open で固定トーンのバッファを
  DMA ループ再生するだけの試しビルド (リング無視)。
  耳で「滑らかか」だけを見る。divide_16 の左右対応も
  ここで片側だけの信号を流して確かめる。
- 段1 (本実装): 上記の方式でリングと接続する。
  enqueue 側ステレオ化、tick での張り直し、無音
  ブロック、drain、フォールバック。hart1 フィーダの
  コードは消す (audio_hart1_step 等)。
- 段2 (検証): virt スイート (音声の共通層は K210 のみ
  なので影響は限定的なはず)、実機で TONE / nami MP3 /
  nami WAV (サイン波) の耳と数字 (under・frames・
  スパン)、SD 実行や file_push の回帰がないこと。

## 未確認・リスク

- divide_16 の下位 16 ビットが左か (段0 で確認)。
- S モードから DMAC の 64 ビット MMIO が素直に
  通るか (他周辺と同じ identity map のはず)。
- ブロック完了で chen ビットが落ちるのは単一
  ブロック転送の前提 (SDK が依存している)。
- DMA が読んでいる領域を作り手が上書きしないこと:
  リング満杯で待つ既存の規律がそのまま効く
  (読み位置 = 新しい head)。

## 実機で判明した前提 (段0、2026-11-21)

- DMAC (0x50000000) はカーネルの identity map に
  入っていなかった (I2S0 は FPIOA と同じ 2MB
  ブロックに同居していたので無事だった)。最初の
  DMAC アクセスで load access fault (scause=5、
  stval=0x50000010) になり、open 中の syscall の
  ためユーザー側の fault として処理されプログラム
  が落ちた = 無音の正体。mshim.c の boot 表と
  vmhook.c の両方に 0x50000000 の割り当てを追加。
- 割り当て追加後の段0 (2026-11-21 17:44): mem2mem
  自己テスト OK、ブロック完了で chen ビットが
  落ちて再装填も動作。441Hz 正弦波の DMA ループ
  再生をユーザーが聞いて「すごくいい」= **プツプツ
  は消えた**。CPU の FIFO 手運び (補充の窓) が
  一連の音質問題の正体だったと確定。段1 (リング
  統合) へ進む。

## 段1 の実装メモ (2026-11-21)

上記の方式で実装した (branch audio-dma):

- trap.c: リングをステレオフレーム列に変更
  (ring_enqueue_packed がモノラルを複製)。
  audio_dma_step が管理 (完了確認 → head 前進 →
  次の装填、空なら無音ブロック、close 中は無音を
  張らない)。装填は audio_feed (100µs tick) と
  write の待ち・close の drain から回す。
- 公開は「書く → smp_evict_cache → tail を進める」
  (DMAC はキャッシュを見ないため。2 段目は不要)。
- hart1 供給係 (audio_hart1_step 等) は削除し、
  smp.c の hart1 はハートビートだけに戻した。
  割り込みフィーダは AUDIO_DMA_OFF で選べる
  フォールバックとして残した。
- i2s.c: DMA のビット (dma_tx_en) は
  open の初期 CCR 書き込みで入れる。流れた実
  フレーム数は board_audio_dma_note_frames で
  stat_frames に合算し、close の要約行を維持。
- 実機の音出し確認はユーザーの許可待ち (音量が
  大きいため)。音量をビットシフトで下げる仕組みは
  後で入れる予定 (ユーザーの希望)。

## 段2 の検証で判明したこと (2026-11-21 夜)

段1 の統合ビルドを実機で鳴らすと、数字 (under/frames/
FNV) は合うのに音が速く・高く・震えた。切り分けの記録:

- DMAC の SAR 進みを 5ms ごとに測ると **352,800
  ワード/秒** (正規 88,200 のちょうど 4 倍) で一定。
  無音 16384 ワードが約 46ms で消費された。
- mem2mem の同じ語数は 5ms 以内に完了 (DMAC 本体や
  バスは律速でない)。TFCR を 12 → 4 に変えても
  レート不変。TXFO は立たず、FIFO は trigger 以下。
- **真因: I2S の txdma はブロック共有の口で、有効に
  なっている全チャンネルへ語が分配される**。CH1 以外
  のチャンネルの TER が立っていたため、語の 3/4 が
  他チャンネル (無接続) へ流れ、CH1 は間引かれた
  列を受け取っていた (4 チャンネル × 2 ワード =
  8 ワード/フレームの需要 = 4 倍速の消費)。
- **対処: open 時に CH0/CH2/CH3 の TER を明示的に
  0 にする**。SAR の進みは 88,200 ワード/秒 (実測
  約 88,000) になり、音程も正常に戻った。

あわせて入れた直し:

- リングの形は divide_16 の詰め形ではなく **1 ワード
  = 1 チャンネルサンプル** (SDK の 32 ビット経路と
  同じ)。リングは 64KB (8192 フレーム) に拡大。
- 無音ブロックは 1024 → **64 フレーム**。長い無音を
  張ると、その間に届いた実データがブロックの終わり
  まで待たされ、位相がずれて空転が自己持続した
  (nami 実測で 1024 フレームの無音を 206 回)。
  最初の装填だけは 1 ブロック分たまるまで待つ。
- **音量シフト**: 投入側 (ring_enqueue_packed) で
  全サンプルに右シフト 1 (半分、約 −6dB) をかける。
  基板2 のアンプが大きすぎるための一律の対処で、
  FNV の帳簿は元のバイト列のままで検証値に影響
  しない。
