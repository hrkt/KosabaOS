# exec 多段化の計画

状態: 計画 (2026-11-05 起草)。doc/future-notes.md 項目2 の
本格版。きっかけ: make 相当のドライバ Misoni (IwaC 側で
開発中) をプログラムとして書くと、Nish → Misoni →
iwac / nori という呼び出しになり、現行の「exec は 1 段
まで」の縛りに当たる。ドライバ側で動作を工夫する手も
あるが、一般の道具立て (ドライバ、将来のスクリプト的な
もの) のためには exec の多段化そのものが本筋。

## 現行の形 (1 段の実装)

- exec は「親の退避スロット 1 つ + 子の領域セット 1 つ」で
  できている。親の trapframe / sepc / sp と領域の割り当てを
  保存し、子 ELF を予備の物理領域に読み、子の exit で
  親に戻る。結果は終了ステータス (-1 = 起動できず、
  -2 = 子が落ちた)
- 領域セットは (コード, データ, スタック) の物理領域の
  3 つ組。virt は親 0x81200000〜 / 子 0x81A00000〜 に
  各 8MB。K210 は親 0x80100000〜 / 子 0x80380000〜 に
  各 2.5MB で、汎用 SRAM 6MB はこれで満杯
- exec は全 fd を閉じる (fd テーブルが大域に 1 つで、
  子の open と衝突しないための現在の割り切り)

## 多段化で考えないといけないこと

### 1. 領域セットを段数ぶんどう確保するか (メモリが本質)

同時に走るのは常に最上段の 1 プログラムだけで、下の段は
凍結されている。ここで「段ごとに現行サイズの領域セット
(virt 8MB / K210 2.5MB) を丸ごと予約する」のは無駄が
大きすぎる、というのがユーザーの指摘 (2026-11-05)。
実際のプログラムは Nish も Misoni も数十 KB で、データ
4MB を本当に使うのは iwac くらいしかいない。予約の単位を
「セット」から「ページ」に替えるのが本筋:

- **ページ単位の実需割り当て (推奨)**: ユーザープログラム
  用の物理ページをプール (ビットマップ管理) から配る。
  exec のとき ELF が実際に要る分だけコード / データの
  ページを取り、スタックは小さく始めてページ fault で
  下へ伸ばす (VA の上限まで)。exit で全部プールに返す。
  VA の配置 (コード 0x40000000、データ 0x40200000、
  スタック頂上) は今までどおりで、変わるのは裏の物理
  メモリの付き方だけ。W^X はページごとの権限で守る
- これで深さは「固定の小さな上限」ではなく「プールが
  尽きるまで」になる。深さの上限は暴走防止の sanity
  としてだけ置く (例: 16。達したら -1)
- virt: プールは数十 MB 取れるので、iwac 級 (約 4MB) の
  連鎖でも 10 段規模が現実的になる
- K210: 固定セット 2 つで満杯だった 5MB がプールに
  なると、小さいプログラムの連鎖は数段いける見込みに
  変わる (Nish 約 0.1MB + Misoni 数十 KB + shirasu
  約 0.4MB 程度)。iwac 本体級は従来どおり入らない
- 代償: ELF ローダが「連続領域へのコピー」から
  「ページごとの写像とコピー」に変わる (読みは今も
  fs_read_at の小分けなので、受け側の変更が中心)。
  スタック伸長の fault 判定 (スタック範囲内の fault は
  伸長、本物の違反は -2) が要る。K210 のドラフト版 MMU
  では fault が access fault として届く現行の癖を踏まえて
  判定すること
- なお「凍結中の親の中身を退避して同じ領域を使い回す」
  案は、退避先が結局 RAM なら節約にならない。当面は
  採らないが、SD への書き込みが実現したら話は変わる:
  exec の境界で親を丸ごと SD に書き出し、子の exit で
  戻す「一括の freeze / thaw」なら、ページ fault 単位の
  スワップと違って粒度もタイミングも exec のモデルに
  合う (数百 KB でサブ秒の見込み)。深さがプールでも
  足りなくなったときの次の一手として残す

### 2. 退避スロットを「積み重ね」にする

- 親の文脈 (trapframe、sepc、sp、領域割り当て、後述の
  fd テーブル) を固定長配列のスタックとして持つ。
  exec で push、子の exit で pop。今の 1 スロット分の
  保存処理をそのまま深さ分繰り返す形にできる
- 深さの上限に達した exec は -1 を返す (仕様として
  syscalls.md に明記する)

### 3. fd テーブルの所有権 (意味の変更が要る)

現行の「exec で全 fd を閉じる」は多段では困る:
Misoni が構築ファイルを開いたまま子を呼ぶ、という
使い方ができない (今はこれも動作の工夫が要る一因)。

- 推奨: fd テーブルを段ごとに持つ。子は空のテーブルで
  始まり、子の exit で親のテーブルがそのまま戻る。
  「親は何もなかったかのように再開する」が exec の
  約束として素直になる
- 互換性: 従来プログラムは「exec される側」として
  空テーブルから始まる点は変わらない。変わるのは親側の
  fd が保存される点だけで、壊れる利用者はいない見込み
- あわせて、これは SD の fd (段4 の is_sd 印) とも
  同じテーブルで扱える

### 4. ページ表と VA の切り替え

- VA は全段で同じ (コード 0x40000000〜等) で、段ごとに
  裏の物理ページが違う。段の切り替え = その段のページ
  写像を有効にして TLB を flush する。段ごとにページ表
  (のユーザー部分) を保持するか、切り替え時に写像を
  張り替えるかは実装時に選ぶ (保持するほうが単純で、
  ページ表自体は段あたり数 KB)
- K210 のドラフト版 MMU では sfence.vm を使う点も現行
  どおり。張り替え回数は exec / exit のときだけなので
  性能の論点にはならない

### 5. 終了ステータスと異常の伝播

- 現行の約束 (子の exit a0 がそのまま exec の戻り値、
  -1 / -2 は予約) を段ごとにそのまま適用する。中間の段が
  異常終了 (-2) した場合も、その親には -2 が返り、
  段は 1 つずつ巻き戻る (一気に根元へは飛ばない)
- Nish は木の根 (カーネルが直接起動) として今までどおり。
  Nish の exit でカーネルコンソールへ戻る現行の扱いは
  変えない

### 6. タスク / マルチタスクとの関係

- exec の積み重ねは「1 つの実行の流れの中の呼び出し」で
  あって、タスクが増えるわけではない。ps の見え方は
  変えない
- ただし退避スタックはタスク構造体側にぶら下げる形に
  しておく: 将来、複数のユーザータスクがそれぞれ exec
  できるようになっても、そのまま使える

### 7. カーネル内の大域状態の点検

1 段前提で書かれた大域変数が無いか、実装時に洗う:
- trap.c の do_exec まわり (保存スロット、結果の受け渡し)
- vm.c のユーザー写像の管理 (現在のセット番号)
- 起動経路 (kernel.c の直接起動は「深さ 0 への push」
  として同じ仕組みに載せられるか)

### 別の道との比較

- **ドライバを Nish の機能にする** (future-notes の
  もう 1 案): カーネル変更は無いが、Misoni を「プログラム」
  として育てる道が閉じる。IwaC 側の道具立てはプログラム
  として書くのが本筋なので、これは採らない
- **本物のプロセス (spawn / wait) にする**: 並行実行や
  パイプまで視野に入る大きな設計で、今の協調モデルには
  過剰。多段 exec は「呼び出しの積み重ね」に絞るから
  小さく収まる。将来プロセス化する場合も、退避スタックの
  考え方は土台として残る

## 段取り (実装するとき)

1. 退避スロットのスタック化 + fd テーブルの段ごと化
   (この段では領域は現行の 2 セットのまま。実質の
   振る舞いは不変で構造だけ替える)。既存 test.sh が
   回帰確認
2. 物理ページのプール化と ELF ローダのページ対応
   (実需割り当て + スタックの fault 伸長)。連鎖実行の
   テストプログラム (自分を exec して深さを数える、
   または 3 段で状態を返す) を test.sh に追加:
   深さ・ステータスの伝播・親のメモリと fd が無事に
   戻ること・プール枯渇と sanity 上限での -1 を確認
3. K210 でも同じプール方式で test-k210.py の回帰確認。
   小さいプログラムの連鎖が数段いけるかも実機で見る
4. syscalls.md に深さの扱い (プール次第 + sanity 上限) と
   fd の意味変更を明記する

## 決めてほしいこと

- 割り当て方式をページ単位の実需割り当てに替えること
  (深さ上限は sanity の 16、実質はプールの量で決まる)
- fd の意味変更 (段ごとに保持) をここで確定してよいか
- K210 も同じプール方式に載せること (狙いは「小さい
  プログラムの連鎖なら数段」。iwac 本体級は対象外)
