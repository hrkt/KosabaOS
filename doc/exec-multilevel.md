# exec 多段化の計画

状態: 計画 (2026-11-05 起草)。doc/future-notes.md 項目2 の
本格版。きっかけ: make 相当のドライバ Misoni (IwaC 側で
開発中) をプログラムとして書くと、Nish → Misoni →
iwac / nori という呼び出しになり、現行の「exec は 1 段
まで」の縛りに当たる。ドライバ側で動作を工夫する手も
あるが、一般の道具立て (ドライバ、将来のスクリプト的な
もの) のためには exec の多段化そのものが本筋。

## 現行の形 (1 段の実装)

- exec は「親の退避スロット 1 つ + 子の領域セット 1 つ」で
  できている。親の trapframe / sepc / sp と領域の割り当てを
  保存し、子 ELF を予備の物理領域に読み、子の exit で
  親に戻る。結果は終了ステータス (-1 = 起動できず、
  -2 = 子が落ちた)
- 領域セットは (コード, データ, スタック) の物理領域の
  3 つ組。virt は親 0x81200000〜 / 子 0x81A00000〜 に
  各 8MB。K210 は親 0x80100000〜 / 子 0x80380000〜 に
  各 2.5MB で、汎用 SRAM 6MB はこれで満杯
- exec は全 fd を閉じる (fd テーブルが大域に 1 つで、
  子の open と衝突しないための現在の割り切り)

## 多段化で考えないといけないこと

### 1. 領域セットを段数ぶんどう確保するか (メモリが本質)

同時に走るのは常に最上段の 1 プログラムだけで、下の段は
凍結されている。だから要るのは「段数 × セット」の物理
メモリそのもので、ここがボードで一番差が出る。

- virt: 1 セット 8MB、RAM 128MB。段数 4 でも 32MB で
  余裕がある
- K210: 現行サイズのセットは 2 つで SRAM が満杯。
  3 セット目は置けない。選択肢は:
  a. K210 は当面 1 段のまま (段数の上限をボード定数に
     して、仕組み自体は共通コードに載せる)
  b. 深い段ほど小さいセットにする (プロファイル制):
     Misoni や小さい道具は shirasu 級の小さい領域で
     足りる、という実情に合わせる。ただし「どの段が
     どの大きさか」の規則と、入らない ELF の扱い
     (起動時 -1) が増える
  c. 凍結中の親の領域の中身をどこかへ退避して同じ
     セットを使い回す: 退避先が RAM 内なら結局同じ量が
     要り、SD は読み取り専用の間は使えない。将来の課題
- 推奨は a で始め、b は K210 で多段が実際に要るように
  なってから。段数の上限は BOARD 側の定数
  (例: BOARD_EXEC_DEPTH) にし、共通コードは上限まで
  汎用的に書く

### 2. 退避スロットを「積み重ね」にする

- 親の文脈 (trapframe、sepc、sp、領域割り当て、後述の
  fd テーブル) を固定長配列のスタックとして持つ。
  exec で push、子の exit で pop。今の 1 スロット分の
  保存処理をそのまま深さ分繰り返す形にできる
- 深さの上限に達した exec は -1 を返す (仕様として
  syscalls.md に明記する)

### 3. fd テーブルの所有権 (意味の変更が要る)

現行の「exec で全 fd を閉じる」は多段では困る:
Misoni が構築ファイルを開いたまま子を呼ぶ、という
使い方ができない (今はこれも動作の工夫が要る一因)。

- 推奨: fd テーブルを段ごとに持つ。子は空のテーブルで
  始まり、子の exit で親のテーブルがそのまま戻る。
  「親は何もなかったかのように再開する」が exec の
  約束として素直になる
- 互換性: 従来プログラムは「exec される側」として
  空テーブルから始まる点は変わらない。変わるのは親側の
  fd が保存される点だけで、壊れる利用者はいない見込み
- あわせて、これは SD の fd (段4 の is_sd 印) とも
  同じテーブルで扱える

### 4. ページ表と VA の切り替え

- VA は全段で同じ (コード 0x40000000〜等) で、段ごとに
  PA セットが違う。段の切り替え = ユーザー VA の写像を
  対象セットへ張り替えて TLB を flush する。今の 1 段の
  張り替え処理を、セット番号を引数に一般化する
- K210 のドラフト版 MMU では sfence.vm を使う点も現行
  どおり。張り替え回数は exec / exit のときだけなので
  性能の論点にはならない

### 5. 終了ステータスと異常の伝播

- 現行の約束 (子の exit a0 がそのまま exec の戻り値、
  -1 / -2 は予約) を段ごとにそのまま適用する。中間の段が
  異常終了 (-2) した場合も、その親には -2 が返り、
  段は 1 つずつ巻き戻る (一気に根元へは飛ばない)
- Nish は木の根 (カーネルが直接起動) として今までどおり。
  Nish の exit でカーネルコンソールへ戻る現行の扱いは
  変えない

### 6. タスク / マルチタスクとの関係

- exec の積み重ねは「1 つの実行の流れの中の呼び出し」で
  あって、タスクが増えるわけではない。ps の見え方は
  変えない
- ただし退避スタックはタスク構造体側にぶら下げる形に
  しておく: 将来、複数のユーザータスクがそれぞれ exec
  できるようになっても、そのまま使える

### 7. カーネル内の大域状態の点検

1 段前提で書かれた大域変数が無いか、実装時に洗う:
- trap.c の do_exec まわり (保存スロット、結果の受け渡し)
- vm.c のユーザー写像の管理 (現在のセット番号)
- 起動経路 (kernel.c の直接起動は「深さ 0 への push」
  として同じ仕組みに載せられるか)

### 別の道との比較

- **ドライバを Nish の機能にする** (future-notes の
  もう 1 案): カーネル変更は無いが、Misoni を「プログラム」
  として育てる道が閉じる。IwaC 側の道具立てはプログラム
  として書くのが本筋なので、これは採らない
- **本物のプロセス (spawn / wait) にする**: 並行実行や
  パイプまで視野に入る大きな設計で、今の協調モデルには
  過剰。多段 exec は「呼び出しの積み重ね」に絞るから
  小さく収まる。将来プロセス化する場合も、退避スタックの
  考え方は土台として残る

## 段取り (実装するとき)

1. 退避スロットのスタック化 + fd テーブルの段ごと化
   (深さ上限は当面いまの 2 セット分 = 実質の振る舞いは
   不変のまま構造だけ替える)。既存 test.sh が回帰確認
2. 領域セットの複数化 (virt で深さ 4 まで)。連鎖実行の
   テストプログラム (自分を exec して深さを数える、
   または 3 段で状態を返す) を test.sh に追加:
   深さ・ステータスの伝播・親のメモリと fd が無事に戻る
   こと・上限での -1 を確認
3. K210 は上限 1 段のまま test-k210.py で回帰確認。
   小さいセットのプロファイル制 (選択肢 b) は実需が
   出てから別途
4. syscalls.md に深さ上限と fd の意味変更を明記する
