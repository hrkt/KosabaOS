# SMP 設計: hart1 を起こし、再生係にする

状態: 段1 を実装中 (2026-11-21、ユーザーの合図で着手。
nami の MP3 ストリーミングが 100µs フィーダ割り込みの
重さで実時間に届かなかった実測が背中を押した)。前提は doc/smp-notes.md
(branch `smp-notes` の検討メモ、2026-11-07) に置いた
とおりで、本書はその「最初の一歩の候補」と「実需が
出たときの段」を具体化する。実需はオーディオ再生:
I2S FIFO が 8 フレーム (約 0.18ms) しかなく、hart0 側の
毎秒の仕事 (時計帯の再描画・tick 印字) で供給が止まり
音が周期的に欠ける。応急対処 (再生中は再描画と印字を
後回し、branch `audio-fifo-starve`) は入れたが、根本は
「供給係を hart0 のスケジューリングから切り離す」こと
であり、それが hart1 の最初の仕事になる。

本格的な SMP スケジューラ (両ハートでタスクを回す) は
本書の範囲外。メモの「やらないこと」を維持する。

## 現状の確認 (2026-11-20、ソースで確認)

- virt: OpenSBI が boot hart だけを S モードで渡す。
  start.S は hart 番号を見ていない。QEMU は -smp の
  指定なし = 1 ハート
- K210: ROM の ISP スタブが両ハートを M モードで
  boards/k210/start.S の _start へ入れる。hart1 は
  その場で park (wfi ループ) に落ち、二度と起きない。
  mtvec は hart0 が park へ向ける (hart1 側は未設定)
- カーネルのページ表は 1 枚 (メモの前提どおり共有する)
- hart ごとの状態という概念はまだ無い。tp は未使用

## 段1: hart1 を起こす (スパイク)

目的は「生きていることの確認」と「キャッシュの振る
舞いの実測」を兼ねる。機能は持たせない。

実装の記録 (2026-11-21):
- 段1a (virt) は実装とスモーク確認まで完了。SBI HSM
  で起きた hart1 が satp を hart0 の値で共有し、専用
  スタックと tp (hart1_state) で hart1_main に入り、
  ps の「hart1: alive=1 beat=...」が増え続けることを
  確認した (約 4.7 億 / 2 秒)。共通部は smp.c / smp.h、
  起こし方は boards 層の board_start_hart1() に分離
- 段1b (K210) は実装まで完了、実機確認が残る。park は
  解放ワードのポーリングになり、hart0 の S カーネルが
  satp ワード→解放ワードの順に書く。hart1 は M の
  k210_hart1_m_entry で mshim_boot と同じ段取り
  (sptbr + mstatus.VM、MPP = S、FS = Initial) を踏み、
  S の hart1_entry へ mret で降りる。事故止めは S/M
  両レベルで scause / mcause をメールボックスに残す
- どちらのボードでも、hart1 が起きなければ klog に
  「smp: hart1 not started」が出て hart0 だけで起動が
  続く (受け入れ条件)

### 起こし方

- virt: hart0 のカーネルが SBI HSM (EID 0x48534D,
  FID 0 = hart_start) で hart1 を起こす。入口は
  start.S に置く hart1_entry: 専用スタックを張り、
  共通 C の hart1_main を呼ぶ。ページ表 (sptbr) は
  hart0 と同じ値を入れる
- K210: hart1 は M モードの wfi にいる。割り込みの
  個別有効化をしていないので、起こす合図は割り込み
  ではなく共有メモリの「解放ワード」にする。hart1 の
  park を「解放ワードが立つまで回る (wfi 併用可)」
  形に変え、hart0 側 (M シム経由の起動後、S の
  カーネルから書ける通常メモリ) がワードを立てると
  hart1 が自前の入口へ進む。入口では自分のスタックと
  mtvec (事故止め = park + 印) を用意し、M シムの
  助けで hart0 と同じ sptbr を持って S モードへ
  降り、hart1_main へ入る。実行モデルを hart0 と
  揃える (M モード常駐の供給係は K210 だけの形に
  なるので採らない)

### hart1 の世界 (段1〜段2 共通の規律)

- 割り込みは受けない (S: sie=0 / sstatus.SIE=0)。
  トラップベクタは「印を残して park」するだけの
  最小ハンドラへ向け、hart1 の事故が hart0 を
  巻き込まないようにする
- 触ってよいのは、専用スタック、ハートビートと
  報告用のメールボックスワード、段2 ではリングと
  I2S レジスタだけ。スケジューラ、ページプール、
  FS、klog には触らない (klog は複数書き手の前提が
  無い)。ログに出したいことはメールボックスへ書き、
  hart0 が dmesg へ写す
- ハート別状態は tp → ハート別構造体 (メモの約束)。
  段1 では構造体の中身はスタック番地とハート番号
  だけでよい
- ウォッチドッグの餌やりは従来どおり hart0 の時計
  タスクの仕事。hart1 は与らない

### ハートビート = キャッシュ実測

hart1_main はメールボックスのハートビートワードを
ひたすら増やし続ける。hart0 は dmesg か ps でその値を
読める。K210 の D キャッシュはハート間でコヒーレント
でない (メモの前提 3) ので、この単純な受け渡しが
「通常のキャッシュされる SRAM で、書いた値が相手に
見えるか」の実測そのものになる。見えない/化ける場合は
段2 のリングの置き場と規約を決める材料にする:

- 候補 A: リングと索引をキャッシュされない置き場に
  する (K210 にそういう窓があるかは要確認)
- 候補 B: 受け渡しの点で明示的にキャッシュ保守を
  する規約 (作り手と食べ手、それぞれの境界で)

段1 の合否: virt と実機の両方で、hart1 起動の klog が
1 行出て、ハートビートが増え続け、hart0 側の従来動作
(virt スイート、実機の通常操作) が壊れないこと。

## 段2: hart1 を再生係にする (K210)

### 形

- 共有リングバッファ (ステレオ int16、8192 フレーム
  = 32KB、44.1kHz で約 186ms 分) を 1 本。作り手は
  hart0 の board_audio_write、食べ手は hart1 の
  常駐ループだけ (単一作り手・単一食べ手なので
  ロックは持たない)
- 索引は head (hart0 だけが書く) と tail (hart1 だけ
  が書く) の 2 ワード。データ本体を書いてから head を
  進める / head を読んでからデータを食べる、の順序を
  fence で守る
- hart0 側: board_audio_write はリングへ積む仕事に
  なる。満杯なら待つ (sched_poll で譲ってよい。食べる
  のは hart1 なので、hart0 が何をしていても FIFO は
  枯れない)。I2S の初期化 (PLL2、FPIOA、レジスタ設定)
  と open/close の管理は従来どおり hart0
- hart1 側: 再生中フラグが立っていてリングが空で
  なければ、ISR の txfe を見て FIFO へフレームを
  流し続ける。空で見つけた回数 (underrun) を数えて
  メールボックスに置き、close の要約行に hart0 が
  合流させる (今の over= と同じ席)
- close: hart0 は「積み終わり」を立て、hart1 が
  リングを食べ切ってから hart0 が TER を落とす
  (待ち合わせはメールボックスの drain 印)

### 置き場とキャッシュ

リングと索引の置き場は段1 の実測で決める。索引だけ
でも素通しで見えるなら、データ本体は「書いた直後に
食べ手が読む」一方向の流れなので、候補 B の規約
(作り手は head を進める前に書いた範囲を保守、食べ手
は食べる前に読む範囲を保守) で足りる可能性が高い。
いずれにせよ virt では再現しない論点なので、判断は
実機の実測で下す。

### virt の扱い

virt の audio はダミー (FNV を取るだけ) なので再生係
は要らない。hart1 の常駐ループと起こしの骨格は共通
コードに置き、再生係の実体は boards/k210 側に置く。
virt では hart1 はハートビートだけを回し、スイートは
「2 ハートで起動しても従来どおり」を保証する。

## 段の区切りと判断

- 段1 が済むまで段2 に入らない。段1 の実測 (特に
  キャッシュ) が段2 の置き場を決めるため
- 段2 の合否は実機の耳: 再生中に時計の秒が進んでも
  (再描画が走っても) 周期ノイズが出ないこと。
  audio-fifo-starve の応急対処は、段2 が入れば
  役目を終えるが、害がないので当面は併存させる
- 実装は各段とも branch を切って、virt スイートと
  実機確認を通してから main へ (通常の進め方)

## 段2 の実装と実測 (2026-11-21、branch smp-stage2)

実装 (trap.c、K210 のみ。virt は従来どおり FNV 計算
だけ):

- リングは SPSC に作り替え: 占有量は共有カウンタで
  なく (tail − head) から求め、head は食べ手だけ、
  tail は作り手だけが書く。満空の曖昧さを避けるため
  容量は BYTES−4 に制限
- 公開は段1 の実測どおり「データ → 追い出し → 索引
  前進 → 追い出し」。open も 2 段で公開し、close は
  feed_state=2 で係に知らせて drained を待つ
  (2 秒で従来ポンプへフォールバック)
- 係 (hart1) は 256 フレームの塊を持ち、補充のたび
  に追い出して索引とデータを読み直す。hart1 が
  死んでいれば open の時点で従来のタイマ割り込み
  フィーダへ落とす (ストリーム単位で選択)
- 再生中はハートビートが進まない (係の仕事を優先。
  alive の印は落ちない)

実機の結果:

- TONE.ELF: under=0、frames=132300 (3.0 秒分ぴったり)
- MP3DEC2 (2 フェーズ): デコード 2.1 秒、再生
  under=0、frames=170496 ぴったり。初の完全実時間
- nami の SD ストリーミング: 当初は約 7 倍遅く、
  供給係のせいに見えたが、真因は nami.elf 自身の
  配置ずれによる misaligned トラップの洪水だった
  (doc/nami-design.md 追補)。修正後は under=0、
  frames=170496、壁時間も曲の長さどおりで実時間に
  到達。「100µs フィーダ割り込み税」説は誤りだった
  とここに訂正する

補充の窓という教訓: 当初、再生全体に周期的な
「ががが」というノイズが乗った。原因は補充 1 回の
窓 (追い出し 128KB × 2 + 取り出し) が、I2S FIFO
の持ち時間 (TXFE 基準で約 12 項 = 6 フレーム =
約 136µs) を超えていたこと。対処は 3 点: 係専用の
追い出しを 64KB に短縮、head の公開を次の補充へ
相乗りさせて追い出しを 1 回に、書き手の待ちループ
の追い出しを 256 回に 1 回へ間引き (書き手の洪水が
係の補充を遅らせていた)。耳で「ががが」が消えた
ことを確認済み。
