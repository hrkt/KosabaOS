KosabaOS ステップ 6 まとめ

ELF ローダ、ファイルシステム、ユーザー空間のシェルを積み上げて、 自作コンパイラ IwaC が OS の上で動き、Hello World を コンパイル・実行するところまで。

ステップ 6 のテーマは「全体ゴールへの接続」。 前のステップまでで、OS は「プログラムを守って動かす」土台が できていました。このステップでは、プログラムを名前で扱い、 ファイルに読み書きし、シェルから別のプログラムを実行 できるようにします。最後に、もう 1 つの自作プロジェクトである C コンパイラ IwaC がこの OS の上で走り、ゴールだった 「OS のシェルからコンパイラで Hello World」が QEMU 上で 成立しました。

6-1ELF ローダ — ファイルが自分の配置を申告する

それまでユーザープログラムは「平らなバイナリを先頭から実行」 する形でした。これを ELF という標準のプログラム形式で 扱うように変えました。ELF ファイルの先頭には「入口はここ」 「この部分をメモリのこの住所へ置く」という申告が書いてあり、 OS 側のローダ（elf.c）はそれを読んで配置します。

  • ヘッダを検証する（形式、64 ビット、RISC-V 用か）
  • セグメントごとにコピーし、足りない分はゼロ埋め（.bss）
  • ユーザー領域の範囲外を指すセグメントは拒否する

効能：プログラムの置き場所が「OS 側の決め打ち」から 「ファイル側の申告」に変わり、コンパイラが作った ELF を そのまま受け取れるようになりました。これが IwaC との 合流の前提です。

6-2RAM ファイルシステム — 名前で引けるファイル

ディスクはまだ無いので、ファイルは全部メモリの中に置く 一番単純なファイルシステム（fs.c）を作りました。 「名前 → データとサイズ」の表と、実体を詰める大きな バイト配列（arena）の組み合わせです。

  • 初期ファイル：hello.txt と、実行プログラム uprog.elf
  • プログラム実行は、埋め込みの直参照から 「ファイルシステムから名前で引く」形に
  • l キーでファイルの一覧（名前とサイズ）が見える

6-3シェル — OS を「使う」場所ができた

システムコール仕様を v1 に拡張し、ファイルを開く・読む 操作（open / read / close / readdir）を足しました。 その上で、ユーザーモードで動く対話プログラムとしての シェル（shell.c）を実装しました。

help — コマンド一覧
→
ls — ファイル一覧
→
cat — ファイル表示
[kernel] starting shell.elf
KosabaOS shell. Type 'help'.
kosaba> ls
  hello.txt
  uprog.elf
  shell.elf
kosaba> cat hello.txt
Hello from the KosabaOS RAM filesystem.

シェル自体も「ただのユーザープログラム」で、文字の 出し入れもファイル読みも、全部システムコール経由です。

6-4exec — シェルからプログラムを実行して戻る

シェルの run <名前> を支える仕組みが exec（システムコール 8 番）です。山場は「親（シェル）の 途中状態を壊さずに、子を実行して、子の終了後に親の続きへ 戻る」ことで、こう実現しました：

親のレジスタ・sepc・sp
を退避
→
同じ仮想アドレスに
子の物理領域を差し替え
→
子を実行
→
子の exit / 保護違反で
退避した親の文脈に戻す

親と子は同じ仮想アドレス（0x40000000）を使うので、どちらの プログラムも同じ前提で作れます。割り切りとして「exec は 1 段まで」「exec で開いていたファイルは閉じる」を 仕様に明記しました。

kosaba> run uprog.elf
hello from user mode!
kosaba>

6-5書く系システムコール — コンパイラの出口

コンパイラは「ソースを読んで、生成物を書く」プログラム です。読みの窓口に続いて、書きの窓口を足しました：

  • create（9 番）：ファイルを作る（同名は空に）。 作ったファイルは 32KB まで書ける
  • write（10 番）：末尾へ書く。入る分だけ書いて 書けたバイト数を返す
  • fd には読み用／書き用の区別があり、逆向きはエラー

シェルにも write memo.txt hello のような コマンドが付き、その場でファイルを作って cat で 読み戻せるようになりました。

6-6データ専用領域 — IwaC の指摘で見つかった食い違い

IwaC を OS に載せる作業の中で、本物の不具合が見つかり ました。コード領域は「読み + 実行のみ」だったのに、 .data / .bss（書き換える静的変数）もそこに置く約束に なっていたため、静的変数に書くプログラムは store page fault で落ちていたのです。自前のプログラムは 全部スタックで済ませていたので踏んでいませんでした。

直し方は 2 案から検討して、(b) を採用：

  • (a) コード領域を読み書き実行可にする — 簡単だが W^X（書ける場所では実行できない守り）を手放す
  • (b) データ専用の読み書き領域をもう 1 枚足す — 本筋の形。ユーザーの住所は 3 領域構成になりました： コード 0x40000000（読み + 実行）、データ 0x40200000 （読み書き）、スタック 0x40400000（読み書き）。ELF ローダはセグメントの住所で行き先を振り分けます

回帰防止に、uprog が静的変数を書き換えて data probe: 8 x と表示する確認を 自動テストへ組み込みました。

到達点OS の上でコンパイラが回った

IwaC 側が新しい配置に追随し、OS 本線は無改造のまま、 両方を組み合わせて検証した結果がこれです：

kosaba> run iwac.elf
kosaba> run hello.elf
Hello, World!
kosaba>

自作 OS のシェルから、自作コンパイラを実行し、 ソース（hello.c）から生成された Hello World が OS の上で 動き、シェルに戻ってくる。プロジェクト開始時に描いた 成功イメージの中心が、QEMU の上で成立しました。

✓ ELF ローダ（6-1）　✓ RAM ファイルシステム（6-2）　✓ シェルと exec（6-3 / 6-4）　✓ 書く系 syscall（6-5）　✓ データ領域（6-6）　✓ IwaC 合流

検証のしかた — 自動テスト全 7 件

test.sh がビルドから QEMU 起動、キー入力の 脚本実行、出力の順序チェックまでを行います。シナリオは A（起動）/ B（echo とフォルト）/ C（ユーザープログラム、 静的変数の probe 含む）/ D（マルチタスク）/ E（FS 一覧）/ F（シェルの ls・cat・run・exit）/ G（シェルの write → cat 往復）で、現在 ALL PASS です。自分の WSL2 環境でも 同じ脚本で確認できます。

運用の決め事と、残っていること

  • clone は KosabaOS と IwaC をセットで実施する （現時点の運用。OS 側の ABI 定義と、ABI 向けバイナリを ツールとして置く話は別途検討）
  • 残る大きな工程は実機移植：ボード選定・購入と、 起動方式・UART・メモリ配置の実機差分への対応
