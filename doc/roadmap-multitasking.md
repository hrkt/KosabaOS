# 計画案: メモリ保護付きマルチタスク OS への道のり

状態: **計画案**（2026-11-01 作成）。確定した仕様ではなく、
進めながら見直す前提の路線図。

## 現在地（2026-11-01 時点）

- `arch/riscv64/start.S` の単一ファイル、アセンブラのみ
- OpenSBI から S モードで起動し、物理アドレスを直接触っている
- UART ドライバは自前（出力 `uart_putc` / 入力 `uart_getc`、
  どちらもポーリング方式）で、hello の表示と echo ができる
- メモリ保護なし、割り込みなし、プロセスなし

## ゴール像（この計画案の範囲）

- ページング（Sv39）でメモリを保護できる
- ユーザーモードでプログラムを動かせて、システムコールで OS に頼める
- 複数のタスクをタイマで切り替えて同時に動かせる
  （メモリ保護付きマルチタスク）

その先（この計画案の範囲外、全体ゴールの続き）: ELF ローダ、
RAM ファイルシステム、ユーザー空間のシェル、自作 OS 上での
コンパイラ実行、実機移植。

## 進め方の考え方

- 各ステップの終わりに「画面で見える成果」を 1 つ置く
- 順番には依存関係があるので、原則この順に進める:
  トラップの受け口がないとページフォルトもタイマ切替もできず、
  ページングがないとメモリ保護ができない

## ステップ

### ステップ 0（寄り道・任意）: 行編集とミニコマンド

- やること: Backspace と Enter を扱えるようにし、行をためてから
  解釈する。`help` など小さなコマンドに応答する
- 見える成果: プロンプトにコマンドを打って反応が返る「OS 感」
- 位置づけ: 本筋の部品ではないが、対話の手触りを先に楽しむ寄り道

### ステップ 1: C 言語化（最大の分岐点）— 実施済み (2026-11-01)

実施内容: start.S はブート専用（スタック、.bss ゼロ埋め、kmain 呼び出し）
になり、本体は kernel.c、UART ドライバは uart.c / uart.h に分かれた。
置き場所は当面 arch/riscv64/ の中。hello と echo の動作は
アセンブラ版と同一であることを QEMU で確認済み。

- やること: `start.S` を「スタックを用意して C の `main`
  （kmain）を呼ぶ」だけに縮め、カーネル本体を C で書き始める。
  ついでに .bss のゼロ埋めも起動時に自分でやる（現状は環境の
  初期ゼロに甘えている）
- 見える成果: C で書いたコードから hello が出る
- なぜ今か: この先の仕組み（トラップ時のレジスタ退避、
  ページテーブル、プロセスの一覧表）はデータ構造の管理が中心で、
  アセンブラだけだと苦行になる
- 補足: ファイル分割や置き場所はこのときに再検討する
  （ドライバは将来 `arch/` の外へ、など）

### ステップ 2: トラップとタイマ割り込み — 実施済み (2026-11-01)

実施内容: trap.S がレジスタ退避・復元と sret の入口になり、
trap.c が stvec 初期化とハンドラを持つ。タイマは OpenSBI の
Timer 拡張 (sbi_set_timer、ecall) で予約し、1 秒ごとに
`tick N` を表示。echo が割り込まれても続きが動くことを確認。
例外は scause/sepc/stval を表示して止める形が入った
(ステップ 3 のフォルト表示の土台)。ビルド側の学び:
CSR 命令には `-march=rv64i_zicsr` が要り、64 ビットの割り算は
M 拡張なしでは libgcc の仕事になるので `-lgcc` をリンク。

- やること: 例外・割り込みの受け口（stvec とトラップハンドラ）を
  作り、タイマ割り込みを有効にする
- 見える成果: 1 秒ごとに `tick` と表示される。何もないときは
  `wfi` で眠れるようになる（駐車用だった命令が現役復帰）
- なぜこの順か: ページフォルトの処理も、プリエンプティブな
  タスク切替も、この受け口が土台になる

### ステップ 3: ページング（Sv39）— メモリ保護の心臓

実施済み (2026-11-01): vm.c / vm.h を追加。gigapage 2 本の
恒等マッピング（エントリ 0 = デバイス領域 RW、エントリ 2 =
RAM RWX）で satp を設定し、`vm: Sv39 paging on` の後に
hello / tick / echo が従来通り動くことを確認。echo 中に
'x' キーを押すと未マップ住所 0x40000000 を触るデモが走り、
load page fault (scause=13)、stval=0x40000000 が表示されて
止まることも確認した。

設計メモ（2026-11-01）: 最初のマッピングは gigapage（1GB ページ）
で恒等マッピングする最小形にする。gigapage は高級ボード向けの
追加機能ではなく Sv39 の仕様の一部なので、Linux が動くクラスの
ボード（数千円台の Milk-V Duo の C906 や VisionFive 2 の U74
を含む）はすべて扱える。制約は「1GB で割り切れる住所から
1GB 分」という形だけのことで、恒等マッピング（0x0 のデバイス
領域と 0x80000000 の RAM）はその形に合っている。

- やること: ページテーブルを作り、アドレス変換を有効にする。
  まず恒等マッピング（変換しても住所が同じ）で「今まで通り
  動く」ことを確認し、そのあと意図的にマップされていない
  住所を触るテストでページフォルトを起こす
- 見える成果: フォルト時にトラップハンドラが原因（scause）と
  触った住所（stval）を表示する。「保護が働く」瞬間が見える
- この先の広がり: カーネルとユーザーの住所空間を分ける、
  書き込みと実行の権限を分ける（W^X）、タスクごとに別の
  ページテーブルを持つ

### ステップ 4: ユーザーモードとシステムコール

実施済み (2026-11-01): システムコール仕様 v0 を doc/syscalls.md
に定めた (a7 = 番号、a0 = 引数・戻り値。1=putc、2=getc、
3=exit、未知の番号は -1 を返して続行)。ユーザープログラム
(uprog.c) はカーネルに埋め込んで運び (embed.S)、0x80400000 へ
コピーして VA 0x40000000 (U 付き megapage) から U モードで
実行する。入る時は user.S の user_launch がカーネルの文脈を
退避し sret で降下、exit では user_exit_jump が文脈を復元して
戻る。ユーザーからのトラップは trap_entry_user が sscratch
交換でトラップ専用スタックに乗り換えて受ける。検証: 挨拶表示、
ユーザー側 echo、実行中の tick 継続、'q' で exit してカーネルの
echo に復帰、まで一通り確認した。ユーザーの例外はその
プログラムだけを終了させる。実バグの学び: (1) trapframe の
a7 の位置を数え間違えた、(2) バイナリ先頭に _start が来るよう
.text.start での明示が必要だった (リンカは関数を宣言順に
並べるとは限らない)。

- やること: U モードで小さなプログラムを動かし、`ecall` で
  OS に処理を頼む。システムコールの仕様（番号、引数の渡し方）は
  この開発の中で自分たちで決める
- 見える成果: ユーザープログラムが自分の権限では直接触れない
  UART を、システムコール経由で使って文字を出す

### ステップ 5: マルチタスク

実施済み (2026-11-01、カーネル内タスクの形で): proc.c /
proc.h / switch.S を追加。タスクは自分のスタックと文脈
(ra・sp・s0〜s11) を持ち、schedule() がラウンドロビンで
switch_context する。タイマ割り込みは 100ms 間隔に変え
(tick 表示は 10 回に 1 回で 1 秒 cadence を維持)、トラップを
またぐ切り替えのために sepc / sstatus をタスクごとに退避・
復元する。デモは 'm' キー: 第 1 幕は協調 (1 文字ごとに
yield → ABAB…の完全な交互)、第 2 幕はプリエンプティブ
(yield なし、100ms の量子で AAA…BBB…と塊で交互)。両幕とも
タスクが終わると kmain の echo に戻る。test.sh のシナリオ D
でも検証する。実バグの学び: トラップ処理の中から初めて
起動されたタスクは sstatus.SIE = 0 のまま走り出して割り込みを
受けられなかった → yield の出口とタスク入口 (トランポリン) で
SIE を立て直す決まりにした。残り: タスクごとのページテーブル
(下の「仕上げ」) と、ユーザータスク化はステップ 6 側の発展。

- やること: タスク（プロセス）の構造と、実行状態の保存・復元
  （コンテキストスイッチ）を実装する。最初は協調的切替
  （タスクが自分から譲る）、次にステップ 2 のタイマ割り込みで
  強制的に切り替えるプリエンプティブ方式にする
- 見える成果: 2 つのタスクが A と B を交互に出し続ける
- 仕上げ: タスクごとにページテーブルを分ければ、
  メモリ保護付きマルチタスクの完成形になる

### ステップ 6: 全体ゴールへ接続

進行中 (2026-11-01): 最初の一歩として ELF ローダを実施
(elf.c / elf.h)。ユーザープログラムは平らなバイナリではなく
ELF のまま埋め込み、ローダがヘッダを検証 (マジック・64bit・
LE・ET_EXEC・RISC-V) して PT_LOAD を配置し、.bss をゼロ埋め
して e_entry から起動する形に変えた (この user.elf は
PT_LOAD 1 本、入口 0x40000000)。範囲外セグメントは拒否する。
振る舞いは従来と同一で、test.sh 全シナリオ PASS。
続いて RAM ファイルシステムも実施 (fs.c / fs.h): 名前→
データの表と arena 方式の最小実装。初期ファイルは hello.txt
と uprog.elf で、'u' の実行はファイルシステムから名前で
引いて ELF ローダに渡す形になり、'l' キーで一覧が見える
(test.sh シナリオ E)。ユーザー側からファイルを読む
システムコールはシェルの段階で足す。
残り: ユーザー空間のシェル → OS 上でのコンパイラ実行
→ 実機移植。

- ELF ローダ → RAM ファイルシステム → ユーザー空間のシェル
  → OS 上でのコンパイラ実行 → 実機移植
- ストレージ（SD/eMMC）は最後まで後回し、という既存方針は維持

## 決定事項

### ターゲット ISA は RV64G を前提にする（2026-11-01 決定）

- G は I + M + A + F + D の略記。つまり掛け算・割り算命令
  （M 拡張）がある前提で設計してよい
- 根拠: 実機候補はすべて RV64GC 系で、Linux が動くクラスの
  RISC-V ボードは G 前提が事実上の標準。M が無いのはマイコン級の
  一部だけで、KosabaOS の土俵ではない
- 帰結: KosabaOS のビルドは `-march=rv64gc` に切り替え、
  割り算・掛け算は命令で実行されるため libgcc の補助関数
  （__udivdi3 など）は不要になる。IwaC のコード生成も
  G 前提で揃える
- それまでの経緯: ステップ 2 までは「最小構成」として rv64i のみを
  前提にし、割り算は libgcc をリンクして賄っていた
