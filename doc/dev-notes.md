# 開発ノート

日々の活動の記録。仕様は各設計ドキュメントに、概念の解説は
学習用ドキュメントに分けてあるので、ここは「その日に何が
あって、どう考えて、どう決着したか」の物語の置き場。
後から読み返して思い出すためのもの。

## 2026-10-31: 始まり

最小の RISC-V 64 カーネルで初回コミット (1b5c9ab)。
QEMU virt で起動し、その日のうちに SBI の putchar から
自前の UART ドライバ (NS16550A) へ移行した。

名前はユーザーが **KosabaOS** に決定。GitHub リポジトリ
を作り、デプロイキーを登録。以後の変更はこのリポジトリに
コミットして push する運用になった。

最初に決めた作法が今も生きている:

- 「作るもの」と「作るために使うツール」は別ディレクトリ
  に分ける。他人のコードを自分のリポジトリに入れない
- ツール一式 (コンパイラや QEMU) は tools/ に常駐させる
- 将来 Arm や x86 でも動かしたいので、アーキテクチャ別の
  ディレクトリに分け、共通コードは外に置く
- start.S には「何をやっているか」のコメントを多く書く。
  学びながら作るのがこのプロジェクトの前提

## 2026-11-01: virt で一気に積み上げた日

QEMU virt の上で、カーネルの階段を一気に登った:

- 命令早見表 instructions.md を開始 (使った命令はその
  都度解説を足す運用。技術用語は無理に訳さず英語のまま)
- Step 1: カーネルを C へ。Step 2: トラップとタイマ
  割り込み。Step 3: Sv39 ページング (identity map、
  ギガページ、fault のデモ)
- ターゲット ISA のベースラインを RV64G に決定
- Step 4: ユーザーモードとシステムコール (仕様 v0)。
  Step 5: マルチタスク (協調とプリエンプティブの両方)
- 自動検証 test.sh を整備し、Step 6 (ELF ローダ、最小の
  RAM ファイルシステム) に着手

ドキュメントを残す文化もこの日から: WSL2 ガイド、
steps の HTML まとめ、概念は学習用ドキュメントとして
独立させる方針。

並行して、将来 KosabaOS の上で使いたい自作コンパイラ
IwaC が別チャットで産声を上げた。OS とコンパイラを
協業させながら進める体制の始まり。

## 2026-11-02: シェル Nish の日

Step 6 の続き: 書き込み系のシステムコール (create /
write)、ユーザ空間のシェル、ファイル操作と exec。
シェルの名前は **Nish**。

"Nish: the shell takes the lead" — 起動したらカーネルの
コンソールではなくシェルが主役になる形へ寄せた日。
ユーザプログラム用の書き込み可能なデータ領域もこの日。

運用の決め事として、KosabaOS と IwaC は「セットで
clone する」ことを README に明記した。

## 2026-11-03: 実機で Hello World の日

このプロジェクトの登録ゴール「RISC-V 実機で自作 OS
から Hello World」を達成した日。

- ボード層を切り (BOARD=virt|k210)、Sipeed Maix Dock
  (Kendryte K210) の実機で KosabaOS が起動
- K210 の癖との格闘: MMU は特権仕様 v1.9 ドラフト版の
  Sv39 (ページテーブルは sptbr、TLB フラッシュは
  sfence.vm)。自前の M モードシム (案b) で点火して
  S モードのカーネルに入る。CLINT タイマで tick
- LCD ドライバを移植し、起動ステージと tick を出す
  「ステータスボード」に育てた
- exec 失敗時に割り込みへ戻れず無限 ecall ループに
  なるバグ (f134432) のような、実機級の踏み方もした
- virt のデータ領域を 4MB に拡大 (IwaC セルフホスト
  の前提)。K210 でのセルフホストは狙わないと決めた
  (汎用 SRAM 6MB に入らないため)
- 実機の自動検証 test-k210.py を開始
- exec の引数 (argv) 対応、子の終了ステータスの伝播、
  「ベーシックな仕様として十分」という基本仕様の合意
  と、残論点の future-notes への記録

到達点: 実機の Nish から `run iwac.elf` で hello.c を
コンパイルして hello.elf を生成し、`run hello.elf` で
「Hello, World!」が表示され、プロンプトへ復帰した。
鍵は容量を絞った小容量 iwac (後に **shirasu** と命名)。
標準ビルドは K210 のデータ領域 1MB を超えたため、
表を縮小したビルドが要った。

## 2026-11-04: 設計の日 (FS 再設計・SD・Ikesu)

実装より設計が大きく動いた日。

- FS 再設計: ブロックチェーン方式 (案A、FAT 風) で
  確定し、段1 を同日実装。create の事前予約を廃止して
  書いた分だけ鎖が育つ形にし、読みは位置指定の
  fs_read_at に統一。実機確認まで完了
- 「ls を考えるとディレクトリが欲しい」というユーザーの
  意向から、名前空間は UNIX 型の単一の木に統一する
  方向へ。`sd:` 接頭辞はやめ、SD は `/sd` に mount する。
  RAM FS 側にもディレクトリと cwd の見え方を持たせる
  (FS 段4)。mount は最初は固定で、徐々に UNIX のように
  mount/unmount できる姿が望ましい、という将来像も記録
- SD カード + MP3 再生のロードマップを承認 (段0〜段5)。
  動機は K210 の RAM FS が 256KB しかなく、普通の曲が
  入らないこと。SD 設計も確定
- Wasm ランタイム **Ikesu** のプロジェクトが別チャット
  で開始。KosabaOS 上で OSS の MP3 デコーダを動かして
  実機のスピーカーから音を出すのがゴール
- マルチボードの前提を再確認: K210 は第一ターゲットで、
  ボード差分はボード層に隔離する。Milk-V 級のボードに
  小さいディスプレイとキーボードとイヤホンジャックを
  付けた「目の前に座れる自作コンピュータ」の夢も、
  この頃に言葉になった

## 2026-11-05: 実装が一斉に進んだ日

- FS 段2 完了: ファイル数を 64 に増やし、unlink

  両方で全シナリオ ALL PASS
- SD は virt 側のスタックが完成 (blkdev 抽象、FAT32

  なくてもシェルが死なない」K7 まで確認
- VM の土台整理: ページアロケータを部品として切り出し
  (page.c)、学習用ドキュメント vm-overview.md を作成。
  仮想メモリには「変換と保護」(実装済み) と「物理
  メモリの管理」(これから) の 2 つの顔がある、という整理
- exec 多段化の計画: IwaC 側の Misoni (ビルドドライバ)
  の連鎖が現行の 1 段 exec に当たる。Nish 組み込み
  コマンドにする案はユーザーが「密結合すぎる」と
  見送り、OS 側の多段化として計画書を作成。当初の

  実需割り当て (プール + スタックは fault で伸長、
  深さはプール次第) に改訂した。凍結した親を SD へ
  追い出す freeze/thaw も、SD 書き込みの先の手として記録
- SD 段1 スパイク開始。そして最初の測定から「基板
  1 台目の IO28 (SCLK) は物理故障」という結論を出して
  しまった。この測定が壊れた FPIOA パッド設定に基づく
  誤りだったと分かるのは翌日。この日の判断が、翌日の

## 2026-11-06: SD カードの謎が解けた日

### 朝:「検証し尽くして未解決」

前日から続く SD カード読み取りの調査。KosabaOS のカーネル
ドライバ (段2 で実装済み) も、ベアメタルのスパイクも、
Maix Dock の実カードを相手にすると CMD0 に完全無応答。
対して MaixPy は起動時にだけカードと話せる。

この朝までに潰した仮説は数え切れない: カード個体・固着・
電源リセット、配線の全順列、ビットバンギング、SPI0/SPI1、
パッド値、クロックと PLL、Maixduino (2台目) での ESP32
干渉説、起動後 20 秒待ってから触るタイミング説、そして
2019 年版 spi.c とのレジスタ単位の照合。フラッシュに
プローブを焼く実験 (ユーザーの承認で MaixPy を消去) まで
やって、それでも無応答。09 時過ぎに「未解決のまま区切り」
と記録した。

作業環境のほうも事件が続いた: 基板操作デーモン (Hatoba)
が 2 度応答しなくなり、どちらも原因は ThinkPad の
アイドルスリープによる WSL 凍結だった (デーモンは死なず、
目覚めれば勝手に復帰する)。ユーザーが ThinkPad を
スリープなしに設定して決着。

### 転機:「マネれば動くはずだよね」

ユーザーの一言で方針が変わる。「MaixPy で読めていて、
GitHub のファームで動いているはずだから、それをマネれば
動くはずだよね」「GitHub からコード落としてきて、二分
探索的にコード分解して探すのもありでは」。

最もな指摘だった。私の「再実装が本物と一致しているはず」
という前提のほうが疑わしい。そこで GitHub から sipeed 版
SDK (Maixpy-dev) と 2019 年版 sdcard.c を落としてきて、
ドライバ本体は無改変のままベアメタルでビルドし、実機に
流した。**動いた。** sd_init 成功、セクタ 0 読み取り、
MBR 署名まで確認。

本物を動かすまでにも地雷が 2 つあった (どちらも SRAM
起動環境ならでは):

- ROM が fcsr に丸めモード 111 (動的) を残しており、
  K210 では double の算術命令が全部 illegal instruction
  になる。SDK のクロック計算が踏む。start で fcsr=0。
- FPIOA の volatile ビットフィールド読みがバイト幅に
  なると APB 周辺が正しく読めない。ビルドに
  -fstrict-volatile-bitfields が要る。

### 二分探索: 犯人は oe_inv

動く本物を起点に、部品を 1 つずつ自作側へ寄せていく
前方二分探索で、最後の差分を特定した。

**真因は FPIOA パッドフラグの oe_inv (bit13)。** スパイク
系は全ピンに一律の値を書いていたが、SDK の正規テーブル
では oe_inv は信号ごとに違い、SCLK (IO27) と CS (IO29)
は oe_inv=0 が正規。1 を書くとパッド出力が反転し、
クロックと CS がカードに正しく届かない。D0/D1 は
oe_inv=1 が正規なので、間違っていたのは 2 ピンだけ。
最小スパイク (その 2 ピンの oe_inv を落とすだけ) で
CMD0 R1=0x01 と読み取り成功を確認した。

重なっていた毒も 2 つ判明した (それぞれ単独変異で本物
ドライバが死ぬことを確認):

- MISO へのプルアップ追加 (朝の時点では「プルアップが
  要る」と逆に結論づけていた。あれは浮いた入力の読みが
  0 に張り付くのを 0xFF に変えただけで、実は毒だった)
- SYSCTL power_sel bit4 の書込み

そして配線は、2019 年版ドライバの順 (IO27=SCLK /
IO28=MOSI / IO26=MISO) が正解だった。2026-11-05 に
「段1 スパイクで確定」とした並びと、「基板 1 台目の
SCLK 物理故障」という結論は、どちらも毒入りの計測に
基づく誤りとして撤回した。

計測の教訓も 1 つ: デーモンのシリアル読みは 1MB の回転
窓で、窓内の出現回数で合否を数えると前のバイナリの出力
に汚染される。途中の判定いくつかはこれで誤読だった。
今後は cursor 基点の増分読みで数える。

### 午後: カーネルで読めた、そしてフラッシュへ

カーネルの sd_hw.c を直した (配線順、oe_inv、spi_ctrlr0=0、
SER=2、IO45 の競合クリア、threshold 0)。実機で Nish から
`cat /sd/BOOT.PY` を叩くと、実カードの boot.py の中身が
返ってきた。test-k210.py 全 7 ALL PASS、virt の test.sh
も全 14 ALL PASS。コミット 358c0c6。SD ロードマップの
段2 がこれで完了。

最後にユーザーが「フラッシュに焼いていきたい」と決断。
KosabaOS カーネル (358c0c6) を基板のフラッシュに焼き、
リセットで単独起動すること、フラッシュ起動のままでも
SD が読めることを確認した。移植チェックリストの step 7
(Flash ブート化) も完了。

電源を入れれば自作 OS が立ち上がり、実物の SD カード
からファイルを読み、シェルが使える。MP3 の曲ファイルを
置く場所ができたので、Ikesu で実曲を鳴らす道も、
ストレージ側は通った。

朝「未解決」と書いた問題が、その日のうちに「大きな
一歩」になった日。分岐点は、自分の再実装への信頼を
捨てて本物を持ってきたことと、それを言い出した
ユーザーの直感だった。

### 夕方: ファイルシステム段4 (ディレクトリと単一名前空間)

実機で外部ストレージに触れるようになった勢いで、FS
再設計の段4 を一気に実装した (2026-11-04 に方向を
確定していた分)。

- 段4-1: ディレクトリを明示的な項として実装し、パス
  解決と正規化をカーネル側の共通処理にした。cwd は
  タスクごとに持ち、exec で子へ引き継がれる。新規
  syscall は mkdir = 13、rmdir = 14、chdir = 15、
  getcwd = 16
- syscall の番号付けには方針も明文化した: 一度割り
  当てた番号は振り直さない・再利用しない、意味の
  ブロックで割り当てる、一覧 (doc/syscalls.md) が
  正本で、追記してから実装する。ブロックは 1〜9 基本、
  10〜19 名前空間とファイル管理、20〜29 プロセスと
  メモリ (予約)、30〜39 時刻とその他 (予約)、40〜49
  デバイス (40〜42 はオーディオ用に予約)。ユーザーの
  「何となく並びに意味があるとカッコよくない?」が
  発端で、Linux は歴史的経緯で付けた番号の寄せ集め、
  FreeBSD はセクション見出しつきの表で育ててきた、
  という対比も判断材料になった
- 段4-2: readdir を「指定したディレクトリの子を返す」
  に拡張し、Nish に cd / pwd / mkdir / rmdir が付いた。
  ls /sd で実カードの一覧が出て、DCIM のような
  サブディレクトリにも入れる
- 検証は virt 全15シナリオ、実機全8シナリオとも
  ALL PASS。RAM FS と SD が 1 本の木に見える形が、
  実機の上でも揃った
