# 開発ノート

日々の活動の記録。仕様は各設計ドキュメントに、概念の解説は
学習用ドキュメントに分けてあるので、ここは「その日に何が
あって、どう考えて、どう決着したか」の物語の置き場。
後から読み返して思い出すためのもの。

## 2026-10-31: 始まり

最小の RISC-V 64 カーネルで初回コミット (1b5c9ab)。
QEMU virt で起動し、その日のうちに SBI の putchar から
自前の UART ドライバ (NS16550A) へ移行した。

名前はユーザーが **KosabaOS** に決定。GitHub リポジトリ
を作り、デプロイキーを登録。以後の変更はこのリポジトリに
コミットして push する運用になった。

最初に決めた作法が今も生きている:

- 「作るもの」と「作るために使うツール」は別ディレクトリ
  に分ける。他人のコードを自分のリポジトリに入れない
- ツール一式 (コンパイラや QEMU) は tools/ に常駐させる
- 将来 Arm や x86 でも動かしたいので、アーキテクチャ別の
  ディレクトリに分け、共通コードは外に置く
- start.S には「何をやっているか」のコメントを多く書く。
  学びながら作るのがこのプロジェクトの前提

## 2026-11-02: シェル Nish の日

## 2026-11-03: 実機で Hello World の日

このプロジェクトの登録ゴール「RISC-V 実機で自作 OS
から Hello World」を達成した日。

- ボード層を切り (BOARD=virt|k210)、Sipeed Maix Dock
  (Kendryte K210) の実機で KosabaOS が起動
- K210 の癖との格闘: MMU は特権仕様 v1.9 ドラフト版の
  Sv39 (ページテーブルは sptbr、TLB フラッシュは
  sfence.vm)。自前の M モードシム (案b) で点火して
  S モードのカーネルに入る。CLINT タイマで tick
- LCD ドライバを移植し、起動ステージと tick を出す
  「ステータスボード」に育てた
- exec 失敗時に割り込みへ戻れず無限 ecall ループに
  なるバグ (f134432) のような、実機級の踏み方もした
- virt のデータ領域を 4MB に拡大 (IwaC セルフホスト
  の前提)。K210 でのセルフホストは狙わないと決めた
  (汎用 SRAM 6MB に入らないため)
- 実機の自動検証 test-k210.py を開始
- exec の引数 (argv) 対応、子の終了ステータスの伝播、
  「ベーシックな仕様として十分」という基本仕様の合意
  と、残論点の future-notes への記録

到達点: 実機の Nish から `run iwac.elf` で hello.c を
コンパイルして hello.elf を生成し、`run hello.elf` で
「Hello, World!」が表示され、プロンプトへ復帰した。
鍵は容量を絞った小容量 iwac (後に **shirasu** と命名)。
標準ビルドは K210 のデータ領域 1MB を超えたため、
表を縮小したビルドが要った。

## 2026-11-04: 設計の日 (FS 再設計・SD・Ikesu)

実装より設計が大きく動いた日。

- SD カード + MP3 再生のロードマップを承認 (段0〜段5)。
  動機は K210 の RAM FS が 256KB しかなく、普通の曲が
  入らないこと。SD 設計も確定
- Wasm ランタイム **Ikesu** のプロジェクトが別チャット
  で開始。KosabaOS 上で OSS の MP3 デコーダを動かして
  実機のスピーカーから音を出すのがゴール
- マルチボードの前提を再確認: K210 は第一ターゲットで、
  ボード差分はボード層に隔離する。Milk-V 級のボードに
  小さいディスプレイとキーボードとイヤホンジャックを
  付けた「目の前に座れる自作コンピュータ」の夢も、
  この頃に言葉になった

## 2026-11-06: SD カードの謎が解けた日

### 朝:「検証し尽くして未解決」

前日から続く SD カード読み取りの調査。KosabaOS のカーネル
ドライバ (段2 で実装済み) も、ベアメタルのスパイクも、
Maix Dock の実カードを相手にすると CMD0 に完全無応答。
対して MaixPy は起動時にだけカードと話せる。

この朝までに潰した仮説は数え切れない: カード個体・固着・
電源リセット、配線の全順列、ビットバンギング、SPI0/SPI1、
パッド値、クロックと PLL、Maixduino (2台目) での ESP32
干渉説、起動後 20 秒待ってから触るタイミング説、そして
2019 年版 spi.c とのレジスタ単位の照合。フラッシュに
プローブを焼く実験 (ユーザーの承認で MaixPy を消去) まで
やって、それでも無応答。09 時過ぎに「未解決のまま区切り」
と記録した。

作業環境のほうも事件が続いた: 基板操作デーモン (Hatoba)
が 2 度応答しなくなり、どちらも原因は ThinkPad の
アイドルスリープによる WSL 凍結だった (デーモンは死なず、
目覚めれば勝手に復帰する)。ユーザーが ThinkPad を
スリープなしに設定して決着。

### 転機:「マネれば動くはずだよね」

ユーザーの一言で方針が変わる。「MaixPy で読めていて、
GitHub のファームで動いているはずだから、それをマネれば
動くはずだよね」「GitHub からコード落としてきて、二分
探索的にコード分解して探すのもありでは」。

最もな指摘だった。私の「再実装が本物と一致しているはず」
という前提のほうが疑わしい。そこで GitHub から sipeed 版
SDK (Maixpy-dev) と 2019 年版 sdcard.c を落としてきて、
ドライバ本体は無改変のままベアメタルでビルドし、実機に
流した。**動いた。** sd_init 成功、セクタ 0 読み取り、
MBR 署名まで確認。

本物を動かすまでにも地雷が 2 つあった (どちらも SRAM
起動環境ならでは):

- ROM が fcsr に丸めモード 111 (動的) を残しており、
  K210 では double の算術命令が全部 illegal instruction
  になる。SDK のクロック計算が踏む。start で fcsr=0。
- FPIOA の volatile ビットフィールド読みがバイト幅に
  なると APB 周辺が正しく読めない。ビルドに
  -fstrict-volatile-bitfields が要る。

### 二分探索: 犯人は oe_inv

動く本物を起点に、部品を 1 つずつ自作側へ寄せていく
前方二分探索で、最後の差分を特定した。

**真因は FPIOA パッドフラグの oe_inv (bit13)。** スパイク
系は全ピンに一律の値を書いていたが、SDK の正規テーブル
では oe_inv は信号ごとに違い、SCLK (IO27) と CS (IO29)
は oe_inv=0 が正規。1 を書くとパッド出力が反転し、
クロックと CS がカードに正しく届かない。D0/D1 は
oe_inv=1 が正規なので、間違っていたのは 2 ピンだけ。
最小スパイク (その 2 ピンの oe_inv を落とすだけ) で
CMD0 R1=0x01 と読み取り成功を確認した。

重なっていた毒も 2 つ判明した (それぞれ単独変異で本物
ドライバが死ぬことを確認):

- MISO へのプルアップ追加 (朝の時点では「プルアップが
  要る」と逆に結論づけていた。あれは浮いた入力の読みが
  0 に張り付くのを 0xFF に変えただけで、実は毒だった)
- SYSCTL power_sel bit4 の書込み

そして配線は、2019 年版ドライバの順 (IO27=SCLK /
IO28=MOSI / IO26=MISO) が正解だった。2026-11-05 に
「段1 スパイクで確定」とした並びと、「基板 1 台目の
SCLK 物理故障」という結論は、どちらも毒入りの計測に
基づく誤りとして撤回した。

計測の教訓も 1 つ: デーモンのシリアル読みは 1MB の回転
窓で、窓内の出現回数で合否を数えると前のバイナリの出力
に汚染される。途中の判定いくつかはこれで誤読だった。
今後は cursor 基点の増分読みで数える。

### 夕方: ファイルシステム段4 (ディレクトリと単一名前空間)

実機で外部ストレージに触れるようになった勢いで、FS
再設計の段4 を一気に実装した (2026-11-04 に方向を
確定していた分)。

- 段4-1: ディレクトリを明示的な項として実装し、パス
  解決と正規化をカーネル側の共通処理にした。cwd は
  タスクごとに持ち、exec で子へ引き継がれる。新規
  syscall は mkdir = 13、rmdir = 14、chdir = 15、
  getcwd = 16
- syscall の番号付けには方針も明文化した: 一度割り
  当てた番号は振り直さない・再利用しない、意味の
  ブロックで割り当てる、一覧 (doc/syscalls.md) が
  正本で、追記してから実装する。ブロックは 1〜9 基本、
  10〜19 名前空間とファイル管理、20〜29 プロセスと
  メモリ (予約)、30〜39 時刻とその他 (予約)、40〜49
  デバイス (40〜42 はオーディオ用に予約)。ユーザーの
  「何となく並びに意味があるとカッコよくない?」が
  発端で、Linux は歴史的経緯で付けた番号の寄せ集め、
  FreeBSD はセクション見出しつきの表で育ててきた、
  という対比も判断材料になった
- 段4-2: readdir を「指定したディレクトリの子を返す」
  に拡張し、Nish に cd / pwd / mkdir / rmdir が付いた。
  ls /sd で実カードの一覧が出て、DCIM のような
  サブディレクトリにも入れる
- 検証は virt 全15シナリオ、実機全8シナリオとも
  ALL PASS。RAM FS と SD が 1 本の木に見える形が、
  実機の上でも揃った

### 続いて: exec の多段化

IwaC 側で「ファイルを別々に分けて動かしたい」という
話になり、Nish → Misoni → iwac / nori の連鎖に要る
exec 多段化を、計画書 (doc/exec-multilevel.md) の
改訂案どおりに実施した。保留になっていた 3 つの決定
(ページ単位の実需割り当て + 深さの sanity 上限 16、
fd テーブルは段ごと、K210 も同じプール方式) は、
ユーザーがまとめて承認して確定。

- 段A: 退避スロットを「積み重ね」にし、fd テーブルを
  段ごとに持つ形へ。目に見える変化として、親が開いた
  ファイルが exec を越えて生きるようになった
- 段B: 物理メモリを「段ごとの固定セット」から
  ページプール + 段ごとの台帳に替え、ELF は要る
  ページだけを取る形に。スタックは fault で伸びる。
  検証用の chain.elf (自分を exec して段を重ねる
  プログラム) で、3 段の連鎖・ステータスの伝播・
  fd とメモリの生存・深さ上限での -1 を確認。
  virt は全 16 シナリオ ALL PASS
- 段C: K210 の 5MB もプール化して同じ方式に。
  実機で chain の 3 段と深さ上限を確認し、テストは
  K1〜K9 ALL PASS。ドラフト仕様のアクセスフォルト
  経由でもスタック伸長が効くことが実機で確かめられた

これで、Misoni を Nish の組み込みではなく「普通の
プログラム」として書くための OS 側の前提が揃った。
残る大物は、深さがプールでも足りなくなったときの
SD への追い出し (SD 書き込みが前提) と、実需が出たら
の stat / seek (FS 段3)。

### 夜: カーネルログ (dmesg 式)

exec 多段化の宿題だった「プールが枯渇したら分かる
ように」を片付けた。ユーザーの選択は dmesg 式:
カーネルにログのリングバッファを持ち、Nish の
`dmesg` コマンドで読む。OS 自体のログもこの基盤に
載せることにした。

- 仕様の作法どおり、まず syscalls.md に追記してから
  実装: **30 = klog_read** (30〜39「時刻とその他」
  ブロックの先頭)。読みは fs_read_at と同じ位置指定
  (オフセット = 起動以来の通し位置) で、古すぎる
  位置は最古の残存位置に丸める
- klog.c: 16KB のリングバッファ (1 行 50 バイト
  前後で約 300 行、K210 のカーネル置き場にも収まる
  大きさ)。行頭に `[秒]` の接頭辞が付くのはログの
  中だけで、コンソールの見た目は変えていない。
  カーネルのメッセージは kputc/kputs 経由にして
  コンソールとログの両方へ。毎秒の tick 表示は
  ログに残すと埋まるのでコンソール専用のまま
- 必ず残す出来事: 起動時のプール総数、exec の失敗
  理由 (深さ上限の拒否、プール枯渇は残量つき)、
  プログラムの異常終了、/sd のマウント。戻り値の
  -1 だけでは区別できなかった理由が、dmesg で
  追えるようになった
- 検証: virt はシナリオ Q を足して全 17 ALL PASS。
  実機は K10 (dmesg で起動記録と上限拒否) と
  K11 を足して全 11 ALL PASS。K11 は検証用の
  eat.elf (約 1000KB の .bss で 1 段約 250 ページ
  食べる) で **実際にプールを枯渇させ**、dmesg に
  `vm: out of pages (stack prepare, pool free 0)`
  が残ることを確認した。枯渇箇所が ELF のセグメント
  確保ではなくスタック準備だったのは端数の運で、
  テストの照合は行の共通部分に緩めた

### 夜の続き: 起動以来の時間 (uptime syscall)

「この OS に時間ってあるんだっけ？」という問いから。
あったのはカーネル内部の tick (起動以来の秒) だけで、
プログラムが経過を測る口は無かった。

- まず syscalls.md に追記: **31 = uptime**、起動以来の
  ミリ秒を返す。タイマ割り込みが 100ms 間隔なので
  実分解能は 100ms で、その旨を仕様に正直に書いた。
  実装は ticks (秒) と tick_divider (100ms 単位の
  端数) の組み立て。壁時計 (何時何分) は RTC の話
  として分けた
- 作業はブランチ `uptime` で進めた。検証用に
  uptime.elf を用意し、プログラム側で単調 (減ら

### 夜 (続き): 壁時計 (RTC)

「いま OS に時間ってあるんだっけ」という問いから。
起動以来の秒数 (tick) しか無かったところへ、uptime
syscall (ブランチ `uptime`) に続いて、ハードウェア
RTC から壁時計を読む機能をブランチ `rtc` で足した
(設計は doc/time.md)。

- 階層はいつもの形に分けた: ボード層が RTC の生
  読み書き (virt = Goldfish RTC、k210 = 内蔵 RTC)、
  共通層が日時構造体と epoch との変換・検証、
  消費者はカーネルコンソールの 't' キー。設定の口は
  ユーザーランドではなくカーネル内 API と決めた
  ので、syscall は足していない
- virt はホストの時刻がそのまま読めた (書く口は
  無いので read-only)。K210 の実測: 未設定時は
  全レジスタ 0 で「未設定」と判定でき、初期化
  (クロック有効化・保護解除・initial_count に
  26MHz・RUNNING 化) をすると設定と読み戻しが
  一致し、実時間の速さで進む
- 肝心の保持は、やはり無かった。設定後にリセット
  (kflash の SRAM 起動のやり直しでも、基板リセット
  でも) を挟むと全レジスタが 0 に戻る。MaixPy が
  起動のたびに NTP 等で合わせ直すのはこのためで、
  置き時計にするなら「起動時に合わせる」が前提に
  なることが実測でも裏付けられた
- 検証: virt はシナリオ S (ブランチ作業時は R、
  main 統合時に uptime の R と重なるため振り直し)
  を足し、実機は K13 (K12 から振り直し、設定 →
  読み戻し) を足して ALL PASS。
  実機の K5 が一度だけ落ちたのは tick 表示が応答の
  真ん中に入ったハーネス側のフレークで、再実行で
  通過した

## 2026-11-07: bg ジョブが並行で走るようになった日

- スケジューラ計画の段3 を branch `job-control` で実装した
  (土台は branch `scheduler` の段1・段2)。到達点は
  ユーザー命名の「Nish で bg ジョブにしたプログラムが
  並行で走ること」。設計は doc/jobs-design.md に先に起こし、
  syscall 20〜22 (job_run / job_list / job_wait) を
  doc/syscalls.md へ先行追記してから実装した
- 表面は `run <名前> &` / `jobs` / `fg [番号]`。コンソール
  仲裁はユーザーと合意した Linux の縮小形: 入力 (getc) は
  コンソールの持ち主だけ、bg ジョブが getc したら入力待ちで
  停止 (stopped)、出力 (putc) は混ざってよい。終わった
  ジョブはプロンプトのタイミングで Done 通知が 1 回出て、
  次のプロンプトで回収される
- 実行モデルは「走者 (runner)」: 前面の exec 鎖が走者 0、
  ジョブが走者 1〜4。ページ台帳・fd 表・cwd は走者ごと
  (exec 多段化の台帳の考え方をそのまま横へ広げた)。
  切り替えはトラップ境界だけ: タイマ割り込み (100ms の
  ラウンドロビン) と、getc の受け渡し (持ち主が文字待ちの
  間は走れるジョブに番を回す)。新しいスケジューラは
  作らず、カーネルタスクの切替 (proc.c) とは層を分けた
- ハマりどころ: ユーザーモードから来た割り込みかの判定に
  from_user (入口の別) は使えない。段2 でカーネルタスクが
  ユーザー用入口を踏むことがあるためで、本当にユーザー
  モードから来たかは sstatus の SPP で判定する。ここを
  間違えると時計タスクの割り込みでユーザーの文脈を
  退避してしまう
- 障害の分離: ジョブがフォルトしたらそのジョブだけが
  status=-2 で終わり、ページと fd は片付けられ、Nish と
  他のジョブは無事。逆に根 (Nish) が終わる/落ちるときは
  ジョブを全部終わらせる (セッションと運命共同体)
- 検証用に slow.elf (ゆっくり進む) と crash.elf
  (踏んで落ちる) を足した。virt は test.sh にシナリオ X
  (bg 起動 → プロンプト即戻り → 実行中に echo → jobs →
  fg で待つ → Done 通知と回収 → フォルトの分離 →
  stopped の fg 再開) を足し、全 24 シナリオで D を除き
  PASS。D (プリエンプティブデモの文字塊の密度を見る
  既知のタイミング揺れ) は、土台の scheduler tip 単体でも
  同じ分布で落ちることを対照実験で切り分けた (デモ自体は
  毎回完走する)。実機は test-k210.py に K17 を足して
  K1 〜 K17 ALL PASS。K17 は最初 slow 12 回で作ったら、
  実機のコマンド往復 (デーモン経由の刻み送信で 1 本
  数秒) の間にジョブが終わってしまい jobs の照合が
  間に合わなかった。OS 側はログ上すべて正しく動いて
  おり、テスト側を 80 回 (約 24 秒) に伸ばして解決
- 残した割り切り (doc/jobs-design.md に明記): ジョブは
  最大 4 本で kill はなし、bg ジョブからの exec は -1、
  sleep の syscall 公開は見送り、FP レジスタは走者の
  切り替えをまたいで保存しない、入力の保持は UART の
  FIFO の範囲だけ (実機は特に浅いので、先行入力は
  実質効かない)

## 2026-11-08: SD の rmdir が埋まった日

SD 書き込み対応 (11-07) で 1 つだけ見送っていた穴、
rmdir の SD 対応を埋めた (branch `sd-rmdir`)。fat_rmdir を
足して SYS_RMDIR (14) の /sd 経路を生かしただけで、新しい
口は作っていない。意味づけは RAM FS の fs_rmdir と同じ
(空のときだけ)、手を動かす順序は fat_unlink に揃えた
(項を 0xE5 で無効化 → 鎖を解放 → FAT 書き戻し → FSInfo)。

決め事として残したのは 2 点 (doc/sd-write-design.md 追補):

- 開いているファイルとの関係: ディレクトリ自体を開く fd
  は現行ない。中身のファイルが開かれている間はその項が
  在るので「空でない」で弾かれ、空チェックが unlink の
  「開いている間は消せない」を兼ねる。fd 照合は足さなかった
- cwd: 自分の cwd は trap.c の既存チェックが SD にも
  そのまま効く (共通経路に置いた)。他の走者の cwd や
  祖先ディレクトリは RAM FS と同じく未対策の割り切り

検証: ホスト側ハーネス (fat.c を実ファイル blkdev で駆動)
で「mkdir → 中にファイル → rmdir は -1 → ファイル削除 →
rmdir 成功」の往復と、入れ子・失敗系 (無い名前、ファイル、
ルート) を確認。独立チェッカ check_sd_image.py で整合
(FSInfo の空き数 = 実態 7084、迷子・クロスリンクなし、
既存 SUB/INNER.TXT はバイト不変)。virt は test.sh に
シナリオ AA を追加 (A〜X の次が空いていなかったので
AA から。Y・Z は gfx-windows が使用中) し、AA を含め
D 以外 PASS。D は既知のタイミング揺れで、未変更の main
でも同じ落ち方 (塊が 5〜7 文字止まり、デモ自体は完走)
を対照で確認した。実機は test-k210.py に K19 を追加した
が、Hatoba デーモンが無応答 (2 回 probe して応答なし)
のため実機ランは残件。K210 ビルドは通過済み。
フラッシュは触っていない。
